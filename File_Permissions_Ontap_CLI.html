File Permissions on ONTAP CLI

A walkthrough of diagnosing file identity, inode mapping, and NTFS/UNIX security attributes for a file in a NetApp ONTAP cluster, using test.txt in the window volume as a running example.

Contents

  1. Explore the inode from a file path
  2. Get the file handle identifiers
  3. Resolve a path from an inode number
  4. Inspect security style and ACLs
Why these commands are used together: each command answers a different question about the same object — "where does this path live on disk," "what unique IDs identify this file cluster-wide," "what path does this inode belong to," and "what permissions actually protect it." Chaining them lets you fully diagnose a file access or permissions issue.
  1. Start from a known path → find its inode (vol explore)
  2. Get durable identifiers for that file (vol file show-filehandle)
  3. Go the other direction: inode → path (vol file show-inode)
  4. Check the actual permission model — NTFS/UNIX/ACLs (vserver security file-directory show)

1Explore the Inode of a File Path

Walks the volume's file system tree from a given path and reports low-level inode metadata — useful for confirming exactly which inode backs a file and inspecting its raw attributes (size, timestamps, ownership, block pointers).
cluster1::*> vol explore -format inode -scope window/Q1_Windows/test.txt
found 1026.64/Q1_Windows to be inode 1026.97
found 1026.97/test.txt to be inode 1026.99
inode 1026.99 generation 1509628 at location 1026@261434b+352:288
   type 1.0, flags 0x02
   size 7, blockcount 0, future_blocks 0, level 0
   umask 010777, uid 0, gid 1, xinode 100, sinode 0, nlink 1, av-gen-num 0
   metadata_len high 0, low 0, bucket_id 0
   ctime 09-Jul-2026 17:10:02, mtime 09-Jul-2026 17:10:02, atime 09-Jul-2026 17:10:27
   parent inode 97, generation 1481920, FSA rulegen 1
   ptr[0]: pvbn 120325176845687, vvbn 101
  • -format inode tells the tool to render output as raw inode metadata rather than block or buftree layout.
  • -scope takes a volume/path value — ONTAP resolves each path component to its inode in turn, shown in the "found ... to be inode ..." lines.
  • The resolved inode here is 1026.99 (inode number 99, generation 1509628).
  • uid 0, gid 1 and umask 010777 reflect the UNIX-style ownership bits that coexist with the file's NTFS security style.
  • parent inode 97 confirms this file lives directly under the folder inode found in the first tree-walk line.
This is a diagnostic/support-level command (note the * in the advanced prompt) — typically used with NetApp support to debug low-level file system issues, not for routine administration.

2Show the File Handle

Returns the durable, cluster-wide identifiers (file ID, generation, FSID, MSID, DSID) that make up a file's NFS file handle — useful for correlating a file across protocols, replication, or support cases.

3Resolve a Path from an Inode Number

The reverse lookup of Step 1: given a volume and an inode number, returns the full file path. Useful when you only have an inode number (e.g., from a log, a quota report, or corruption alert) and need to know which file it belongs to.
cluster1::*> vol file show-inode -vserver svm1 -volume window -inode-number 99
                       Inode
Vserver   Volume       Number   File Path
--------- ------------ -------- ----------------------------------
svm1      window       99       /vol/window/Q1_Windows/test.txt
  • Inode number 99 resolves back to /vol/window/Q1_Windows/test.txt, confirming consistency with Steps 1 and 2.
  • This command is especially handy for FlexGroup volumes or after a restore, where a file's path may not be immediately obvious.

4Inspect Security Style and ACLs

Displays the full effective permissions model for a file or directory — security style, DOS attributes, UNIX mode bits, and (for NTFS) the owner, group, and DACL entries. This is the command you reach for when troubleshooting "access denied" issues.
cluster1::*> vserver security file-directory show -vserver svm1 -path /windows/Q1_Windows/test.txt
                  Vserver: svm1
Dummy index for tree walk: -
                File Path: /windows/Q1_Windows/test.txt
        File Inode Number: 99
           Security Style: ntfs
          Effective Style: ntfs
           DOS Attributes: 20
   DOS Attributes in Text: ---A----
  Expanded Dos Attributes: -
             UNIX User Id: 0
            UNIX Group Id: 1
           UNIX Mode Bits: 777
   UNIX Mode Bits in Text: rwxrwxrwx
                     ACLs: NTFS Security Descriptor
                           Control:0x8004
                           Owner:BUILTIN\Administrators
                           Group:DEMO\Domain Users
                           DACL - ACEs
                             ALLOW-Everyone-0x1f01ff-(Inherited)
  • Security Style / Effective Style: ntfs — access is enforced using Windows ACLs, not UNIX mode bits, even though UNIX ownership (uid 0, gid 1) is still tracked for NFS interoperability.
  • DOS Attributes: ---A---- — the Archive bit is set; no Read-only, Hidden, or System flags.
  • UNIX Mode Bits: rwxrwxrwx (777) — irrelevant to access enforcement here since the effective style is NTFS, but still stored on the inode.
  • DACL - ACEs: ALLOW-Everyone-0x1f01ff-(Inherited) — a single inherited ACE grants full control (0x1f01ff) to Everyone, inherited from the parent folder rather than set explicitly on the file.
  • File Inode Number: 99 ties this permissions view directly back to the same inode explored in Steps 1–3.
If a user reports unexpected access to or being blocked from this file, this is the single command that shows the real, effective permission model — check Effective Style first, then the DACL.
