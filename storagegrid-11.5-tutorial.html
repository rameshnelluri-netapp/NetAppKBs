Section 01

What is StorageGRID?

NetApp StorageGRID is a software-defined, object-based storage solution that supports industry-standard object APIs — principally the Amazon S3 API and the OpenStack Swift API. It provides secure, durable storage for unstructured data at scale, with integrated metadata-driven lifecycle management policies that optimize where data lives throughout its life.

StorageGRID is composed of geographically distributed, redundant, heterogeneous nodes that can be integrated with both existing and next-generation client applications. Nodes can run on VMware virtual machines, Docker containers on Linux hosts, or purpose-built NetApp hardware appliances.

Core Capabilities

  • Amazon S3 API
  • OpenStack Swift API
  • Policy-based ILM
  • Replication & Erasure Coding
  • Multi-site geodistribution
  • Cloud Storage Pools (AWS, Azure)
  • Platform Services (Mirror, SNS, Search)
  • FabricPool tiering
  • S3 Object Lock / WORM
  • Identity federation (LDAP / AD / SSO)
  • Prometheus metrics & Grafana
  • SNMP monitoring

Deployment Flexibility

Software-based nodes
  • VMware vSphere VMs
  • Docker containers on RHEL, CentOS, Ubuntu, Debian
Hardware appliances
  • SG6000 — Storage Node (NL-SAS / SSD)
  • SG5700 — Integrated Storage Node
  • SG100 / SG1000 — Admin / Gateway services
ℹ️

StorageGRID supports non-disruptive operations: clients can continue ingesting and retrieving objects during software upgrades, expansion, decommission, and most maintenance procedures.

Section 02

Architecture & Network Topology

A StorageGRID system consists of one or more sites, each containing one or more grid nodes. All nodes communicate over the internal Grid Network. An optional Admin Network serves management traffic, and an optional Client Network carries S3/Swift client traffic in an isolated network plane.

Four Node Types

Admin Node
🖥️

Admin Node

Hosts the Grid Manager UI, management API, audit logging, Prometheus metrics, and Grafana. One primary Admin Node per grid; additional non-primary nodes add redundancy. Also supports load balancing S3/Swift traffic.

Storage Node
🗄️

Storage Node

Stores and manages object data and metadata. Hosts the LDR, Cassandra metadata store, DDS, Chunk (erasure coding), and Data Mover services. Minimum three per site.

Gateway Node
⚡

Gateway Node

Optional. Provides Layer 7 load balancing (Load Balancer service) for S3 and Swift client connections, distributing requests to optimal Storage Nodes. Supports High Availability groups with virtual IPs.

Archive Node
📼

Archive Node

Optional. Provides an interface to external archival storage such as tape (via Tivoli Storage Manager middleware) or older cloud endpoints via S3.

Networks

NetworkPurposeRequired?
Grid Network All internal StorageGRID traffic — node-to-node replication, metadata propagation, ILM engine communication, heartbeats. ✅ Required
Admin Network Closed private network for system administration, maintenance, audit log access, and management API. Optional
Client Network Open network for S3 and Swift client applications. Isolates client protocol access from internal grid traffic so the Grid Network remains secured. Optional

High Availability Groups

Admin Nodes and Gateway Nodes can be grouped into HA Groups. Each group exposes one or more virtual IP addresses (VIPs). If the active node fails, keepalived automatically migrates the VIP to a healthy node within seconds. HA Groups ensure that load-balancing endpoints remain reachable even during node failures.

Section 04

Data Flows — Ingest, Retrieve & Delete

Every object in StorageGRID has two independent parts: object data (the payload bytes) and object metadata (UUID, object name, bucket/container, tenant, logical size, timestamps, user metadata, tags). These are stored and managed separately — data by LDR to disk, metadata by Cassandra to three distributed copies.

Ingest Flow (PUT Object)

PUT Object → LDR → Metadata Store → Client 200 OK
1
Client HTTP PUT. An S3 or Swift client sends a PUT request through the load balancer (Gateway Node or Admin Node) to a Storage Node's LDR service.
2
ILM Policy evaluation. The LDR evaluates the object against the active ILM policy to determine data protection instructions (replicated copies, erasure coding scheme, placement locations, ingest behavior).
3
Object data stored. The LDR saves the object data as a replicated copy or initiates erasure coding (see below). For the Balanced ingest option, synchronous placement is attempted; if unavailable, interim copies are made and corrected later by background ILM.
4
Metadata written. The LDR sends object metadata (location, UUID, user metadata) to the Cassandra metadata store on the same node.
5
Metadata propagated. Cassandra automatically replicates the metadata to other Storage Nodes across sites (three copies total per site) for durability.
6
Client acknowledgment. The LDR returns HTTP 200 OK to the client, confirming successful ingest.

Ingest Behavior Options

Balanced (recommended default)

StorageGRID attempts to make all copies specified by the ILM rule at ingest time. If a target site is unavailable, interim copies are stored locally and ILM corrects placement as soon as the site becomes available. Best for most workloads.

Strict

The PUT fails unless all copies can be made exactly as specified at ingest time. Use when regulatory requirements mandate precise placement from the moment of write. More ingest errors during site outages.

Dual Commit

Two interim copies are immediately stored on two different Storage Nodes (even on the same site), then ILM eventually moves copies to their final locations. Reduces ingest latency but may temporarily have non-compliant copy counts.

Retrieve Flow (GET Object)

GET Object → Metadata lookup → LDR → Object returned
1
Client GET request. The client sends a GET to the load balancer, which routes it to the nearest available Storage Node LDR.
2
Metadata query. The LDR queries the Cassandra metadata store to find the object's location(s) — which Storage Node(s), Cloud Storage Pool, or Archive Node hold copies.
3
Data retrieval. If the data is on a local or remote Storage Node, the LDR fetches it directly. If on a Cloud Storage Pool that uses Glacier storage, the client must first restore the object via POST Object restore.
4
Object returned. The LDR streams the object data back to the client in the HTTP response body.

Delete Flow

StorageGRID enforces a strict deletion hierarchy. The system always respects this priority order:

Highest priority

S3 Object Lock legal hold / retain-until-date. Cannot be overridden.

Second

Client DELETE request removes all copies immediately.

Third

S3 Bucket Lifecycle Expiration action (overrides ILM).

Lowest

ILM placement expiration — last period ends with no further placements.

⚠️

The S3 bucket lifecycle Expiration action always overrides ILM settings. An object can be retained on the grid after ILM placement instructions have lapsed if the bucket lifecycle has not yet triggered deletion.

Object Lifecycle Stages Summary

StageDescription
IngestClient saves object via HTTP PUT; StorageGRID begins managing it.
Copy ManagementILM engine creates and maintains specified replicated or erasure-coded copies across Storage Nodes, Cloud Storage Pools, or Archive Nodes over the object's lifetime.
RetrieveClient reads the object; LDR locates and returns it from the best available copy.
DeleteAll copies removed by client request, bucket lifecycle expiration, or ILM expiration.
Section 05

Information Lifecycle Management (ILM)

ILM is the policy engine at the heart of StorageGRID. It determines where objects are stored, how many copies exist, what type of protection is used (replication vs. erasure coding), and for how long — all without any application-level awareness.

ILM Rules

An ILM rule is the fundamental unit of policy. Each rule specifies:

  • Filters — which objects it applies to: by tenant account, S3 bucket/Swift container, object size, user metadata, or tags. The default rule has no filters and matches everything.
  • Storage type — replicated copies, erasure-coded copies, Cloud Storage Pool, or Archive Node.
  • Copy count & placement — how many replicas, on which storage pools (sets of Storage Nodes defined by site or node tags), and for what duration.
  • Time periods — placement instructions that change over time (e.g., 3 replicas for 1 year, then transition to 2+1 erasure coding forever).
  • Ingest behavior — Balanced, Strict, or Dual Commit.

ILM Policy

An ILM policy is an ordered list of ILM rules. StorageGRID evaluates each incoming object against the rules in order. The first rule whose filters match is applied; if no rule matches, the mandatory default rule (last in the list, no filters) applies.

ℹ️

Object metadata is not managed by ILM rules. Cassandra automatically maintains three copies of all object metadata at each site and distributes them evenly across all Storage Nodes at that site.

Example ILM Policy with Three Rules

Rule 1 — Tenant A: 3 replicated copies across 3 sites (forever)

Filter: Tenant account = "Tenant A". Placement: one replicated copy at Site 1, Site 2, and Site 3 for all time. Ingest: Balanced.

Rule 2 — Large objects (>1 MB) from all other tenants: 6+3 erasure coding

Filter: object size > 1 MB AND not Tenant A. Placement: 6+3 erasure coding across three sites. Objects not matched fall to Rule 3.

Rule 3 — Default: 2 replicated copies (any node, forever)

No filter (default rule). All objects not matched by Rules 1 or 2 get two replicated copies on any available Storage Nodes.

ILM Evaluation & Background Scanning

ILM evaluation happens at two times:

  • At ingest — the active ILM policy is evaluated immediately as each object is stored.
  • Background scanning — the ILM engine continuously scans all stored objects to ensure they conform to the current active policy. This corrects drift caused by node failures, site outages, policy changes, or objects that have entered a new time period.

Storage Pools

A storage pool is a logical grouping of Storage Nodes (or Archive Nodes), typically defined by site or node metadata tags. ILM rules reference storage pools when specifying placement. For example, "Site-1-Pool" might include all Storage Nodes at the primary data center.

Erasure Coding Profiles

An erasure coding (EC) profile binds a storage pool to an erasure-coding scheme (e.g., 4+2, 6+3, 2+1). ILM rules that use erasure coding reference an EC profile. The profile determines both where the fragments go and how many data/parity fragments are created.

Section 06

Data Protection: Replication vs. Erasure Coding

Replication

Replication creates complete copies of an object and places each on a different Storage Node (and/or site). The ILM engine in the LDR service controls replication:

  1. ILM engine queries the ADC service for the best destination LDR within the target storage pool.
  2. The destination LDR queries ADC for the best source location and sends a replication request.
  3. The source LDR sends the object data to the destination LDR.
  4. Destination LDR confirms successful storage; ILM engine updates Cassandra with the new location.

Replication is ideal for small objects (where erasure coding overhead is disproportionate) and for use cases where read latency is critical.

Erasure Coding

Erasure coding provides storage efficiency superior to full replication while still protecting against multiple simultaneous failures. StorageGRID slices the object into data fragments and computes parity fragments using Reed-Solomon coding. Even if some fragments are lost or corrupt, the object can be reconstructed from the remaining data and parity fragments.

Example: 4+2 Erasure Coding

D1 D2 D3 D4 + P1 P2

The object is divided into 4 equal data fragments (D1–D4) and 2 parity fragments (P1–P2). All 6 fragments are distributed across 6 Storage Nodes. The object can be recovered from any 4 of the 6 fragments, tolerating loss of up to 2 nodes simultaneously.

Common EC Schemes

Erasure Coding Data Flow

EC ingest flow through LDR → DDS → Chunk services
1
ILM engine queries ADC to find the best DDS service for the EC operation and sends an "initiate" request.
2
DDS service instructs an LDR to perform erasure coding on the object data.
3
Source LDR sends a copy of the object to the selected LDR service for encoding.
4
LDR splits the data into the specified number of data and parity fragments and distributes them to Chunk services on separate Storage Nodes.
5
LDR notifies the ILM engine that distribution is complete.
6
ILM engine updates the Cassandra metadata store with the fragment location map.
💡

Erasure coding is recommended for objects larger than 200 KB where storage efficiency matters. For very small objects, the per-fragment overhead can exceed the savings, making replication more efficient.

Section 07

Tenant Accounts & Multi-tenancy

A tenant account is the fundamental unit of multi-tenancy in StorageGRID. Each tenant is an isolated namespace with its own users, groups, S3 buckets (or Swift containers), and objects. Tenants are created by the grid administrator; tenant users manage their own storage using the Tenant Manager UI or the S3/Swift API.

What a Tenant Account Controls

  • Identity — local users/groups, or federated users from LDAP/Active Directory.
  • S3 Access Keys — long-term credentials for programmatic access.
  • Buckets — creation, versioning, CORS, consistency level, Object Lock, lifecycle policies, and last-access-time updates.
  • Platform services — CloudMirror, event notifications, and search integration per bucket (if enabled by grid admin).
  • Storage quota — optional maximum storage capacity set by grid admin.

Tenant Manager

The Tenant Manager is a browser-based interface that tenant users access by signing in to an Admin Node. It provides a dashboard showing storage usage per bucket, access to S3 key management, bucket management, platform service endpoint configuration, and user/group access control.

S3 Object Lock (WORM)

StorageGRID 11.5 introduces S3 Object Lock, replacing the legacy Compliance feature. When enabled globally by the grid admin and then on a specific bucket, object versions can be assigned:

  • Retain-until-date — the object version cannot be deleted until this date. The date can be extended but never shortened.
  • Legal hold — indefinite protection regardless of retain-until-date; must be explicitly lifted.

Bucket versioning is automatically enabled when S3 Object Lock is activated on a bucket. ILM protects locked objects "forever" during their retention period.

StorageGRID implements a broad subset of the Amazon S3 REST API, making it a drop-in replacement or complement to AWS S3 for most applications. Clients connect using standard AWS SDKs and tools.

Authentication

StorageGRID supports AWS Signature Version 2 and AWS Signature Version 4 for request authentication. Tenant users create S3 access key pairs via the Tenant Manager; root access keys provide full access to all of a tenant's buckets and objects unless a bucket policy restricts them.

Endpoint Configuration

The grid admin configures Load Balancer Endpoints — specific ports and protocols (HTTP or HTTPS) on Admin Nodes or Gateway Nodes where S3 clients connect. Each endpoint can be bound to a specific network (Grid, Admin, or Client) and supports custom TLS certificates. Multiple endpoints can serve different tenants or protocols simultaneously.

OpenStack Swift API

In addition to S3, StorageGRID supports the OpenStack Swift REST API (v1). Swift clients use containers (analogous to S3 buckets) and objects. The same Storage Nodes serve both S3 and Swift requests; the protocol is selected by the endpoint port and path format. ILM policies apply uniformly to objects regardless of the protocol used to store them.

Section 09

Platform Services

S3 platform services enable individual tenant buckets to integrate with external cloud services. Platform services operate independently of ILM rules and are configured per bucket by tenant users with appropriate permissions — but they must first be enabled for the tenant by the grid admin.

🪞

CloudMirror Replication

Automatically mirrors specified objects to a target S3 bucket. The target can be on Amazon S3, Microsoft Azure Blob Storage, or a second StorageGRID system. Mirrors happen asynchronously as objects are written. Used for cross-cloud redundancy, analytics offload, or hybrid workflows.

📡

Event Notifications

Sends SNS-compatible messages about bucket events (object created, deleted, etc.) to an external endpoint that supports Amazon SNS. Enables event-driven architectures — for example, triggering an AWS Lambda function when a file is uploaded to StorageGRID.

🔍

Search Integration

Sends object metadata to an external Elasticsearch service whenever an object is created, deleted, or its metadata/tags are updated. Enables full-text and faceted search across StorageGRID object metadata using Kibana or other Elasticsearch-compatible tools.

ℹ️

The RSM (Replicated State Machine) service on Storage Nodes ensures platform service requests are durably tracked and retried until the external endpoint confirms receipt, preventing event loss during transient failures.

Section 10

Consistency Controls

Consistency controls provide a trade-off between object availability and read-after-write consistency across different Storage Nodes and sites. The default behavior (read-after-new-write) guarantees read-after-write consistency for newly created objects and matches Amazon S3 consistency semantics.

Consistency can be configured at the bucket level (persisted for all operations on that bucket) or overridden on a per-operation basis via the Consistency-Control request header.

Consistency LevelBehaviorUse When
all All Storage Nodes must acknowledge immediately, or the request fails. Highest consistency, lowest availability. Critical writes where split-brain is unacceptable.
strong-global Guarantees read-after-write consistency for all clients across all sites. Multi-site workloads requiring cross-site consistency.
strong-site Guarantees read-after-write consistency for all clients within a single site. Single-site apps that need strong local consistency.
read-after-new-write Default. New objects are immediately readable. Overwrites, metadata updates, and deletes are eventually consistent. Matches Amazon S3 guarantees. Most S3 workloads. Best balance of consistency and availability.
available Same as read-after-new-write except HEAD operations use eventual consistency only. Higher availability for HEAD requests when Storage Nodes are down. Apps that frequently HEAD non-existent objects. Avoids 500 errors when nodes are temporarily unavailable.
⚠️

If your application issues many HEAD requests for non-existent objects and one or more Storage Nodes is unavailable, use available rather than read-after-new-write to avoid 500 Internal Server Errors caused by the escalating consistency lookup.

Conflicting Client Requests

When two clients write to the same key simultaneously, StorageGRID resolves the conflict on a "latest-wins" basis. The timing is based on when StorageGRID completes the request internally, not when the client initiates the operation.

Section 11

Security Architecture

Identity Federation & SSO

StorageGRID integrates with enterprise identity systems for both grid administrators and tenant users:

  • LDAP-based federation — Active Directory, OpenLDAP, or Oracle Directory Service. Users authenticate with their corporate credentials.
  • Single Sign-On (SSO) — SAML 2.0 integration with Active Directory Federation Services (AD FS). Administrators and tenant users use SSO tokens; direct password login to the Grid Manager is disabled when SSO is active.

Node Encryption (KMS)

StorageGRID appliance nodes support KMS-managed disk encryption. When node encryption is enabled, every disk volume on the appliance is encrypted using AES-256. Encryption keys are managed by an external Key Management Server (KMS) configured per site in the Grid Manager. Without the KMS key, data on an encrypted appliance is irretrievable, protecting against physical theft or removal.

TLS Everywhere

  • All client S3/Swift connections use HTTPS with configurable TLS certificates per Load Balancer Endpoint.
  • Internal grid-to-grid communications are encrypted in transit.
  • The Grid Manager and Tenant Manager UIs are HTTPS-only.

Compliance Certifications

StorageGRID is designed to help customers meet storage requirements under:

  • SEC Rule 17a-4(f) — broker/dealer electronic storage requirements.
  • FINRA Rule 4511(c) — financial industry record-keeping.
  • CFTC Regulation 17 CFR §1.31(c)-(d) — commodity futures trading records.

Audit Logging

The AMS (Audit Management System) service on Admin Nodes logs all audited system events, object storage operations, client read/write requests, and management API calls to structured text files (audit.log). Audit logs can be accessed via NFS or CIFS shares on Admin Nodes. Log entries include timestamps, operation type, object identifiers, tenant, and result codes.

Section 12

Monitoring & Observability

Grid Manager Dashboard

The Grid Manager is the primary operational interface. Its dashboard provides at-a-glance panels for system health, storage utilization, ILM queue depth and scan progress, and S3/Swift ingest/retrieve rates. Detailed per-node views are available from the Nodes page, with tabs for Hardware, Network, Storage, Events, Objects, ILM, Load Balancer, and Platform Services.

Alert System

The alert system is the primary tool for detecting operational issues:

  • Alerts have three severities: Critical (service disruption), Major (approaching critical), and Minor (monitor but not urgent).
  • Multiple instances of the same alert type are grouped in both the UI and email notifications.
  • Each alert notification includes the affected node/site, current metric values, and recommended remediation steps with documentation links.
  • Admins can silence alerts for a duration, edit default alert rules, and create custom alert rules using Prometheus metric expressions.

Prometheus & Grafana

The Prometheus service on Admin Nodes scrapes time-series metrics from all grid nodes every few seconds. Over 1,000 metrics are available, covering storage utilization, object counts, ILM queue length, replication throughput, erasure coding fragment counts, and more. Grafana is embedded in the Grid Manager to visualize these metrics in pre-built and custom dashboards. Prometheus data is also accessible via the Grid Management API for integration with external monitoring stacks.

SNMP Monitoring

StorageGRID runs an SNMP agent (daemon) on every grid node, supporting SNMPv1, v2c, and v3. The MIB includes table definitions for alerts and alarms. The SNMP agent provides read-only MIB access and can send Traps (v1/v2c/v3) or Informs (v2c/v3) to external SNMP management systems when alerts fire.

Section 13

Hybrid Cloud Integration

Cloud Storage Pools

Cloud Storage Pools allow ILM rules to direct object copies to external cloud storage — Amazon S3 (including S3 Glacier and S3 Glacier Deep Archive) or Microsoft Azure Blob Storage (including the Archive access tier). This enables seamless hot-to-cold tiering driven entirely by ILM policy.

Key behaviors:

  • Objects are moved to the Cloud Storage Pool by the Data Mover (DMV) service on Storage Nodes.
  • Cloud Storage Pool objects remain tracked in the Cassandra metadata store; retrieval is transparent to clients.
  • For Glacier-class storage, clients must issue a POST Object restore request and wait before reading.
  • Note: Cloud Storage Pools cannot be used as FabricPool capacity tiers because of the added retrieval latency.

FabricPool Integration

NetApp ONTAP can use StorageGRID as a FabricPool capacity tier. FabricPool automatically tiers cold (infrequently accessed) ONTAP data blocks to StorageGRID object storage, dramatically reducing primary storage costs. Cold data is presented to ONTAP users transparently as if it were still local. ILM policies on StorageGRID protect tiered data exactly like any other object.

Multi-Site Disaster Recovery

StorageGRID natively supports geographically distributed deployments across failure domains (different earthquake fault lines, flood zones, or data centers). ILM rules automatically distribute copies across sites. If an entire site fails:

  • Remaining sites continue serving client requests if sufficient copies exist elsewhere.
  • Background ILM scanning detects missing copies and creates replacements on surviving nodes.
  • Grid Manager's expansion and recovery procedures guide site restoration.

Architecture: Single Site vs. Multi-Site

Single Site

All infrastructure centralized. Erasure coding within a single site provides node-level fault tolerance. Simpler operations, no WAN bandwidth requirements.

Multiple Sites

Sites in different geographic locations across separate failure domains. Data sharing and disaster recovery achieved by automated ILM-driven distribution. Each site can have different node counts and storage capacity.

Grid Expansion

StorageGRID supports non-disruptive expansion — adding Storage Nodes, Gateway Nodes, Admin Nodes, or entire new sites without interrupting client access. The ILM engine automatically rebalances object placement to use the new capacity over time. Expansion can be driven by the Grid Manager or automated via the Installation REST API and Python scripts.
