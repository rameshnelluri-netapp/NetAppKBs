Cloud storage architecture · NetApp on AWS

Amazon FSx for NetApp ONTAP

How the managed file system actually stores your data, moves it between tiers, and bills for it — and where it splits from NetApp's own Cloud Volumes ONTAP.

Everything below explains exactly how that picture works — and where it bills you.

01 / 08

Two ways NetApp shows up in AWS

Most of the confusion between these two products starts before you even get to storage tiers — it starts with who owns the compute underneath ONTAP.

Cloud Volumes ONTAP (CVO) is NetApp's own software, installed onto a compute instance you pick the size of. It shows up as an ordinary EC2 instance in your account, with ordinary EBS disks attached, and it's orchestrated through NetApp's BlueXP console. FSx for NetApp ONTAP is the opposite model: a native AWS service. AWS runs the real ONTAP nodes on infrastructure that lives inside AWS's own management boundary — you never see it, size it, or patch it. You only ever interact with the logical resources it exposes.

02 / 08

The resource hierarchy

Everything you create in FSx for ONTAP nests inside four layers. None of them require you to pick a compute instance.

Single‑AZ

One zone, lower cost

Everything runs in a single availability zone. Cheaper, but no automatic AZ‑level failover if that zone has a problem. Second‑generation Single‑AZ file systems can scale out to up to 12 HA pairs in one file system.

Multi‑AZ

Synchronous cross‑AZ replication

Data is mirrored synchronously to a standby in a second AZ, with automatic failover. The cost of that cross‑AZ replication traffic is folded into your throughput‑capacity charge, not billed as a separate line item.

03 / 08

Storage tiers: hot and cold

Every file system has exactly two storage tiers underneath it, and they behave — and bill — completely differently.

Primary tier

SSD

  • User‑provisioned, high‑performance, sub‑millisecond latency
  • Purpose‑built for your active working set
  • Billed flat per GB‑month — whether full or empty
  • Keep sustained utilization at or below ~80%
Capacity pool tier

Elastic / cold

  • Fully elastic — scales automatically, nothing to provision
  • Cost‑optimized for infrequently accessed data & snapshots
  • Billed only for what's actually stored (GB‑months)
  • Plus a small per‑request charge whenever it's read or written
Key idea

A volume's data can live in either tier, or both at once — ONTAP moves blocks between them automatically, based on the tiering policy you set on that volume.

04 / 08

Tiering policies & cooling periods

The tiering policy is the dial that controls how aggressively a volume's data moves toward the capacity pool.

PolicyWhat movesCooling periodBest for
None Nothing — everything stays on SSD permanently n/a Latency‑critical workloads, e.g. transactional databases
Snapshot‑only (API default) Only snapshot data 2 days min · range 2–183 General workloads where active data shouldn't move, but snapshots can
Auto ("Balanced" — console default) Cold user data + snapshots, based on access patterns 31 days default · range 2–183 Mixed, general‑purpose file shares
All Nearly everything, including active blocks once written Tiers out continuously in the background Secondary / archive targets, cost‑optimized DR copies
Definition

Cooling period — how long a block has to sit untouched before ONTAP considers it "cold" enough to move. The clock starts the moment the block is written, not when the volume is created.

05 / 08

The real data path

This is the part that resolves most of the confusion: what actually happens, in order, from the moment you create a volume to the moment a client reads cold data back.

The fact that fixes most confusion

All writes land on SSD first — always, no exceptions, regardless of tiering policy. There is no path that writes directly into the capacity pool. File metadata stays on SSD permanently. A brand‑new, empty volume — even one configured with a 2 TB size — consumes zero physical capacity in either tier until real data is actually written into it; the size you set at creation is a logical quota, not a reservation.

Once data is on SSD, a background process continuously scans for blocks that have gone untouched longer than the volume's cooling period. If the tiering policy allows it, that block is copied to capacity pool storage and the SSD copy is freed. When a client later reads that cold data, ONTAP fetches it back and re‑promotes ("rehydrates") it onto SSD so it can be served fast — but only while SSD has headroom.

SSD utilization thresholds that change behavior

≤ 50%

Only "All"‑tiered volumes move data. Auto and Snapshot‑only volumes don't bother yet — there's no pressure to free up space.

> 50% – 80%

Auto and Snapshot‑only volumes tier normally, on schedule with their cooling period. 80% is AWS's recommended sustained ceiling.

~90%

Read‑back caching to SSD stops. Repeat reads of cold data now come straight from the capacity pool instead, to protect remaining headroom for new writes.

~98%

Tiering itself halts entirely until SSD frees up. Grow the file system's SSD capacity, or delete data/snapshots, to resume it.

07 / 08

How FSx for ONTAP billing works

Five metered components, plus one optional sixth. Each one is metered differently because the underlying resource behaves differently.

Provisioned

SSD storage

Average GB provisioned per month (GB‑months). Flat — billed whether the tier is full or empty.

Provisioned

SSD IOPS

3 IOPS per GB of SSD included free. Anything provisioned above that is billed as IOPS‑months.

Consumption‑based

Capacity pool storage

Average GB actually stored per month, plus a small per‑request charge whenever that data is read or written.

Provisioned

Throughput capacity

Average MBps provisioned per month. Also covers inter‑AZ replication transfer for Multi‑AZ deployments.

Consumption‑based

Backups

Incremental — only changes since the last backup are stored. Billed on average GB actually retained per month.

Optional

S3 Access Point

Standard S3 request & data‑transfer pricing — only applies if you attach an Access Point to the file system.

Good to know

There are no minimum fees or setup charges. Pricing is quoted monthly but usage is prorated hourly. Storage efficiency features (deduplication, compression, compaction) reduce the physical footprint that's actually billed in both SSD and capacity pool — you pay for what's physically stored after efficiencies, not the raw logical size of your data.

Worked example

Say you provision 5 TiB of SSD capacity and set most volumes to the Auto tiering policy. Over a couple of months, suppose 3 TiB of that dataset goes untouched long enough to cool and tiers out, leaving roughly 2 TiB active on SSD and 3 TiB sitting in the capacity pool. Your bill for that month reflects: the full 5 TiB of SSD GB‑months — what you provisioned, not what's currently sitting on it — plus 3 TiB of capacity‑pool GB‑months, since that's the part that actually migrated, plus whatever throughput capacity you provisioned, plus whatever backup storage your snapshot policy is retaining. If that cooled data is later deleted or rehydrated back to SSD, the capacity‑pool figure drops the following month — but the SSD charge stays exactly the same until you actively shrink the file system's provisioned SSD capacity.

08 / 08

Glossary

File system
Top‑level FSx for ONTAP resource. Equivalent to an on‑premises ONTAP cluster.
HA pair
Two file server nodes in active/standby. 1 per file system for Gen 1 & Multi‑AZ Gen 2; up to 12 for Single‑AZ Gen 2.
SVM
Storage Virtual Machine — a logical, multi‑tenant file server with its own data & admin endpoint. Not a compute VM.
Volume
A virtual container for files. Doesn't consume capacity itself — only the data inside it does.
Primary / SSD tier
User‑provisioned, high‑performance storage for the active working set. Billed flat regardless of use.
Capacity pool tier
Fully elastic, AWS‑managed cold storage. Billed only for actual consumption.
Tiering policy
Per‑volume setting (None / Snapshot‑only / Auto / All) controlling what moves to the capacity pool.
Cooling period
How long a block must sit untouched before it's eligible to tier out. Starts counting at write time.
Single‑AZ / Multi‑AZ
Deployment type — one zone vs. synchronously replicated, auto‑failover across two zones.
Generation 1 / 2
FSx for ONTAP hardware generation. Gen 2 Single‑AZ supports scaling out to multiple HA pairs.
BlueXP
NetApp's SaaS console for deploying & managing Cloud Volumes ONTAP (not used by FSx for ONTAP).
Connector
An EC2 instance BlueXP uses to orchestrate Cloud Volumes ONTAP in your account.
Architecture, tiering, and pricing mechanics evolve over time — always check the current AWS FSx for NetApp ONTAP documentation and pricing page before sizing or budgeting a real deployment. This guide is an independent explainer, not official AWS or NetApp documentation.
