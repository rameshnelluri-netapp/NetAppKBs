From rnelluri@localhost to a fully resolvable box in NetappWorld.com

A step-by-step record of getting a fresh Rocky Linux VM off a broken localhost identity and onto proper forward/reverse DNS resolution inside a Windows Active Directory domain.

localhost→ myrockyvm→ static IP→ Windows DNS record→ NetappWorld.com member→ self-registering DDNS
00 · Symptom

The prompt says localhost, not the VM's name

Everything starts here — a hostname that never got set, on a VM that already has a real IP.

rnelluri@localhost:~$ hostname -i
::1 127.0.0.1

rnelluri@localhost:~$ ifconfig -a
ens160: flags=4163<UP,BROADCAST,RUNNING,MULTICAST>  mtu 1500
        inet 192.168.59.130  netmask 255.255.255.0  broadcast 192.168.59.255
        inet6 fe80::20c:29ff:fe90:4b15  prefixlen 64  scopeid 0x20<link>

The VM clearly has a working IP (192.168.59.130) from VMware's NAT network. The prompt just never got told what to call itself, and nothing in /etc/hosts maps a real name to that IP — so hostname -i falls back to loopback.

01 · Fix

Set a real hostname and back it with /etc/hosts

  1. Check the current hostname: hostnamectl
  2. Set a real one: 
    sudo hostnamectl set-hostname myrockyvm
  3. Map it to the actual IP in /etc/hosts: 
    sudo vi /etc/hosts

# add / confirm these lines
127.0.0.1        localhost localhost.localdomain
192.168.59.130   myrockyvm myrockyvm.localdomain myrockyvm
  4. Reload and verify: 
    exec bash
hostname
hostname -i
Watch out — if 127.0.0.1 also gets mapped to myrockyvm, hostname -i will resolve back to loopback again. Keep the real IP on its own line.
02 · Stability

Lock in a static IP so the mapping doesn't rot

A DHCP lease can change on reboot — and then your /etc/hosts entry quietly points at the wrong machine.

nmcli con show                          # find the connection name, e.g. ens160
ip route show                           # note current gateway
cat /etc/resolv.conf                    # note current DNS servers

sudo nmcli con mod ens160 ipv4.addresses 192.168.59.130/24
sudo nmcli con mod ens160 ipv4.gateway 192.168.59.2
sudo nmcli con mod ens160 ipv4.dns "8.8.8.8 8.8.4.4"
sudo nmcli con mod ens160 ipv4.method manual

sudo nmcli con down ens160 && sudo nmcli con up ens160

ip addr show ens160
ping -c 3 8.8.8.8

Using the IP the VM already had avoids disrupting anything else — this just stops it from being reassigned later.

03 · Concept

Domain join is not what makes nslookup work

These are two independent things that get conflated a lot.

What nslookup actually needs

A reachable DNS server address in /etc/resolv.conf. Nothing more. Public names resolve the moment that's set correctly.

What domain join is actually for

Centralized authentication (logging in with domain accounts), Group Policy, and resolving internal-only names against a private DNS zone.

cat /etc/resolv.conf
nslookup google.com
nmcli device show ens160 | grep DNS
04 · Why it worked

google.com resolved — but the reverse lookup didn't

rnelluri@localhost:~$ nslookup google.com
Server:         192.168.59.2
Address:        192.168.59.2#53
Non-authoritative answer:
Name:   google.com
Address: 142.251.222.142

rnelluri@localhost:~$ nslookup 192.168.59.130
** server can't find 130.59.168.192.in-addr.arpa: NXDOMAIN

192.168.59.2 is VMware's virtual NAT router. In VMware's NAT networks that single address does double duty: it's the default gateway and it also runs a lightweight DNS forwarder that relays queries to whatever DNS your host machine actually uses.

It has no records of its own, though — which is exactly why the reverse lookup on a private RFC 1918 address like 192.168.59.130 returns NXDOMAIN. Nobody publishes PTR records for private ranges; that record only exists if something creates it locally.

VMware DNS (192.168.59.2)A real DNS server (dnsmasq / bind / AD)
Who runs itVMware, automaticallyYou, deliberately
Resolves google.com?Yes — forwards itYes, if forwarders are set
Resolves your own hostnames?NoYes, once you add records
Reverse (PTR) lookups?NoYes, if a reverse zone exists
05 · Setup

Adding the Unix server's record to Windows DNS

GUI path via DNS Manager, plus the PowerShell equivalent.

GUI

  1. Open DNS Manager (dnsmgmt.msc) on the Windows DNS server.
  2. Expand Forward Lookup Zones → right-click your zone → New Host (A or AAAA).
  3. Name: myrockyvm · IP: 192.168.59.130.
  4. Check "Create associated pointer (PTR) record" → Add Host.
  5. If the checkbox is greyed out, create a matching Reverse Lookup Zone first (Network ID 192.168.59), then re-add the host.

PowerShell

Add-DnsServerResourceRecordA -Name "myrockyvm" -ZoneName "company.local" `
  -IPv4Address "192.168.59.130" -CreatePtr

# if the reverse zone doesn't exist yet:
Add-DnsServerPrimaryZone -NetworkID "192.168.59.0/24" -ReplicationScope "Forest"

Point Linux at it, then verify both directions

sudo nmcli con mod ens160 ipv4.dns "<Windows_DNS_Server_IP>"
sudo nmcli con up ens160

nslookup myrockyvm.company.local
nslookup 192.168.59.130
06 · Sequencing

Which comes first — the DNS record or the client config?

Functionally independent. Practically, one order debugs itself faster than the other.

1. Create the A/PTR record on the Windows DNS server 2. Verify it from the DNS server itself — Resolve-DnsName 3. Point the Linux client's resolv.conf at that DNS server 4. Set the Linux hostname to match the record 5. Test resolution from the Linux side

Testing step 2 on the server first removes one whole class of ambiguity: if Linux later fails to resolve, you already know the record is good — so the problem has to be network reachability, the wrong resolver IP, or a stale resolv.conf, not a missing record.

Don't forget — once Linux points at the internal DNS server instead of VMware's 192.168.59.2, that server needs its own Forwarders configured, or external names like google.com will stop resolving.
07 · Full Walkthrough

Doing it for real: domain controller NetappWorld.com

  1. Open DNS Manager on the domain controller.
  2. Confirm the forward zone — NetappWorld.com already exists under Forward Lookup Zones, created when the DC was promoted.
  3. Create the reverse zone (skip if present): right-click Reverse Lookup Zones → New Zone → Primary, AD-integrated → scope to domain controllers → IPv4 Reverse Lookup Zone → Network ID 192.168.59 → allow nonsecure & secure updates (lab) → Finish.
  4. Add the host record: right-click NetappWorld.com → New Host (A or AAAA) → Name myrockyvm, IP 192.168.59.130, check Create associated pointer (PTR) record → Add Host → Done.
  5. Verify — the A record appears under the forward zone, the PTR under 59.168.192.in-addr.arpa.
  6. Set forwarders — server properties → Forwarders tab → add 8.8.8.8, 8.8.4.4.

Rocky Linux side

sudo nmcli con mod ens160 ipv4.dns "192.168.59.<DC_last_octet>"
sudo nmcli con mod ens160 ipv4.dns-search "NetappWorld.com"
sudo hostnamectl set-hostname myrockyvm.NetappWorld.com
sudo nmcli con up ens160

Verify from both sides

# On the domain controller (PowerShell)
Resolve-DnsName myrockyvm.NetappWorld.com
Resolve-DnsName 192.168.59.130

# On Rocky Linux
nslookup myrockyvm.NetappWorld.com
nslookup 192.168.59.130
nslookup google.com
08 · Clears up confusion

Why forwarders point to 8.8.8.8, not the DC's own IP

NetappWorld.com's DNS server is authoritative for exactly one thing: its own zone. It has no idea what google.com is. When a client asks it for an external name, it has two options:

  • Recurse itself — walk the chain from root servers down to .com down to google.com.
  • Forward the question to a resolver that already knows — that's what the Forwarders tab configures.

Pointing the forwarder at the DC's own IP creates a loop — it would just be asking itself the same question it couldn't answer. The forwarder has to be a different, external-capable resolver: your ISP's DNS, a corporate upstream resolver, or a public one like 8.8.8.8 / 1.1.1.1.

Not mandatory — if this DNS server only ever needs to resolve internal lab names, forwarders can be left empty; Windows will fall back to root-hint recursion. Forwarders just make external resolution faster and offload the work.
09 · Automation

Dynamic DNS — so future VMs register themselves

Two paths, depending on how much security the lab needs.

Option A — Nonsecure updates (lab only)

  1. DNS Manager → right-click NetappWorld.com → Properties → Dynamic updates → Nonsecure and secure. Repeat for the reverse zone.
  2. If using DHCP, have the client send its hostname: 
    sudo nmcli con mod ens160 ipv4.dhcp-send-hostname yes
sudo nmcli con mod ens160 ipv4.dhcp-hostname "myrockyvm.NetappWorld.com"
  3. Or trigger an update manually with nsupdate: 
    sudo dnf install bind-utils -y

nsupdate <<EOF
server 192.168.59.<DC_IP>
zone NetappWorld.com
update add myrockyvm.NetappWorld.com 3600 A 192.168.59.130
send
EOF

Option B — Secure updates via domain join (recommended)

sudo dnf install realmd sssd oddjob oddjob-mkhomedir adcli samba-common-tools krb5-workstation -y

sudo realm discover NetappWorld.com
sudo realm join NetappWorld.com -U Administrator

# after joining, set the zone back to "Secure only" in DNS Manager

kinit administrator@NETAPPWORLD.COM
nsupdate -g <<EOF
server 192.168.59.<DC_IP>
zone NetappWorld.com
update add myrockyvm.NetappWorld.com 3600 A 192.168.59.130
send
EOF

The -g flag makes nsupdate authenticate over Kerberos (GSSAPI), so only domain-joined machines can write records — that's what "secure dynamic update" means in practice.
