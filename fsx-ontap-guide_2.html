Cloud storage architecture · NetApp on AWS

Amazon FSx for NetApp ONTAP

How the managed file system actually stores your data, moves it between tiers, and bills for it — and where it splits from NetApp's own Cloud Volumes ONTAP.

Everything below explains exactly how that picture works — and where it bills you.

01 / 12

Two ways NetApp shows up in AWS

Most of the confusion between these two products starts before you even get to storage tiers — it starts with who owns the compute underneath ONTAP.

Cloud Volumes ONTAP (CVO) is NetApp's own software, installed onto a compute instance you pick the size of. It shows up as an ordinary EC2 instance in your account, with ordinary EBS disks attached, and it's orchestrated through NetApp's BlueXP console. FSx for NetApp ONTAP is the opposite model: a native AWS service. AWS runs the real ONTAP nodes on infrastructure that lives inside AWS's own management boundary — you never see it, size it, or patch it. You only ever interact with the logical resources it exposes.

02 / 12

The resource hierarchy

Everything you create in FSx for ONTAP nests inside four layers. None of them require you to pick a compute instance.

Single‑AZ

One zone, lower cost

Everything runs in a single availability zone. Cheaper, but no automatic AZ‑level failover if that zone has a problem. Second‑generation Single‑AZ file systems can scale out to up to 12 HA pairs in one file system.

Multi‑AZ

Synchronous cross‑AZ replication

Data is mirrored synchronously to a standby in a second AZ, with automatic failover. The cost of that cross‑AZ replication traffic is folded into your throughput‑capacity charge, not billed as a separate line item.

03 / 12

Storage tiers: hot and cold

Every file system has exactly two storage tiers underneath it, and they behave — and bill — completely differently.

Primary tier

SSD

  • User‑provisioned, high‑performance, sub‑millisecond latency
  • Purpose‑built for your active working set
  • Billed flat per GB‑month — whether full or empty
  • Keep sustained utilization at or below ~80%
Capacity pool tier

Elastic / cold

  • Fully elastic — scales automatically, nothing to provision
  • Cost‑optimized for infrequently accessed data & snapshots
  • Billed only for what's actually stored (GB‑months)
  • Plus a small per‑request charge whenever it's read or written
Key idea

A volume's data can live in either tier, or both at once — ONTAP moves blocks between them automatically, based on the tiering policy you set on that volume.

04 / 12

Tiering policies & cooling periods

The tiering policy is the dial that controls how aggressively a volume's data moves toward the capacity pool.

PolicyWhat movesCooling periodBest for
None Nothing — everything stays on SSD permanently n/a Latency‑critical workloads, e.g. transactional databases
Snapshot‑only (API default) Only snapshot data 2 days min · range 2–183 General workloads where active data shouldn't move, but snapshots can
Auto ("Balanced" — console default) Cold user data + snapshots, based on access patterns 31 days default · range 2–183 Mixed, general‑purpose file shares
All Nearly everything, including active blocks once written Tiers out continuously in the background Secondary / archive targets, cost‑optimized DR copies
Definition

Cooling period — how long a block has to sit untouched before ONTAP considers it "cold" enough to move. The clock starts the moment the block is written, not when the volume is created.

05 / 12

The real data path

This is the part that resolves most of the confusion: what actually happens, in order, from the moment you create a volume to the moment a client reads cold data back.

The fact that fixes most confusion

All writes land on SSD first — always, no exceptions, regardless of tiering policy. There is no path that writes directly into the capacity pool. File metadata stays on SSD permanently. A brand‑new, empty volume — even one configured with a 2 TB size — consumes zero physical capacity in either tier until real data is actually written into it; the size you set at creation is a logical quota, not a reservation.

Once data is on SSD, a background process continuously scans for blocks that have gone untouched longer than the volume's cooling period. If the tiering policy allows it, that block is copied to capacity pool storage and the SSD copy is freed. When a client later reads that cold data, ONTAP fetches it back and re‑promotes ("rehydrates") it onto SSD so it can be served fast — but only while SSD has headroom.

SSD utilization thresholds that change behavior

≤ 50%

Only "All"‑tiered volumes move data. Auto and Snapshot‑only volumes don't bother yet — there's no pressure to free up space.

> 50% – 80%

Auto and Snapshot‑only volumes tier normally, on schedule with their cooling period. 80% is AWS's recommended sustained ceiling.

~90%

Read‑back caching to SSD stops. Repeat reads of cold data now come straight from the capacity pool instead, to protect remaining headroom for new writes.

~98%

Tiering itself halts entirely until SSD frees up. Grow the file system's SSD capacity, or delete data/snapshots, to resume it.

07 / 12

How FSx for ONTAP billing works

Five metered components, plus one optional sixth. Each one is metered differently because the underlying resource behaves differently.

Provisioned

SSD storage

Average GB provisioned per month (GB‑months). Flat — billed whether the tier is full or empty.

Provisioned

SSD IOPS

3 IOPS per GB of SSD included free. Anything provisioned above that is billed as IOPS‑months.

Consumption‑based

Capacity pool storage

Average GB actually stored per month, plus a small per‑request charge whenever that data is read or written.

Provisioned

Throughput capacity

Average MBps provisioned per month. Also covers inter‑AZ replication transfer for Multi‑AZ deployments.

Consumption‑based

Backups

Incremental — only changes since the last backup are stored. Billed on average GB actually retained per month.

Optional

S3 Access Point

Standard S3 request & data‑transfer pricing — only applies if you attach an Access Point to the file system.

Good to know

There are no minimum fees or setup charges. Pricing is quoted monthly but usage is prorated hourly. Storage efficiency features (deduplication, compression, compaction) reduce the physical footprint that's actually billed in both SSD and capacity pool — you pay for what's physically stored after efficiencies, not the raw logical size of your data.

Worked example

Say you provision 5 TiB of SSD capacity and set most volumes to the Auto tiering policy. Over a couple of months, suppose 3 TiB of that dataset goes untouched long enough to cool and tiers out, leaving roughly 2 TiB active on SSD and 3 TiB sitting in the capacity pool. Your bill for that month reflects: the full 5 TiB of SSD GB‑months — what you provisioned, not what's currently sitting on it — plus 3 TiB of capacity‑pool GB‑months, since that's the part that actually migrated, plus whatever throughput capacity you provisioned, plus whatever backup storage your snapshot policy is retaining. If that cooled data is later deleted or rehydrated back to SSD, the capacity‑pool figure drops the following month — but the SSD charge stays exactly the same until you actively shrink the file system's provisioned SSD capacity.

08 / 12

Scaling & sizing: SSD, IOPS, throughput, capacity pool

Once a file system is running, three of its dimensions are yours to tune — SSD storage, SSD IOPS, and throughput capacity. The capacity pool tier looks after itself.

Adjustable anytime

SSD storage capacity

  • Increase online, with no downtime — each request must be at least 10% above the current value
  • Second‑generation file systems can also decrease in place — FSx quietly relocates each volume to a smaller aggregate and redirects clients automatically
  • First‑generation file systems can only ever increase, never decrease
  • Keep the result under ~80% utilization
Two modes

SSD IOPS

  • Automatic — scales with storage at 3 IOPS per GiB, up to your configuration's max
  • User‑provisioned — set a fixed number (≥3/GiB) and pay for anything above the included rate
  • Shrinking SSD in user‑provisioned mode may require lowering IOPS first, if your current value would exceed what the smaller footprint supports
6‑hour cooldown (Gen 2)

Throughput capacity

  • Changeable anytime, but second‑generation file systems enforce a minimum 6‑hour wait between throughput changes
  • That cooldown is shared with SSD/IOPS scaling — the two can't run back‑to‑back
  • Rule of thumb: provision for read throughput plus roughly 2× write throughput
  • The highest throughput tiers require a minimum SSD + IOPS floor before AWS will let you provision them
Nothing to provision

Capacity pool

  • Grows automatically as cold data tiers in, shrinks automatically as it's deleted or rehydrated
  • No size limit to plan around — it scales to petabytes on its own
  • The only lever you actually control is each volume's tiering policy (section 04)
Locked at creation

Deployment type (Single‑AZ ↔ Multi‑AZ) and generation (Gen 1 ↔ Gen 2) can't be changed after a file system exists. Changing either means standing up a new file system and migrating your data across — see section 11.

Deployment & setup

Setting one up is three layers of decisions, in order: pick a deployment type for the file system, configure the SVM that will host your namespace, then create volumes inside it.

Choosing a deployment type

This is the one decision you can't undo later without migrating to a new file system.

Single‑AZ 2Second1–12Large‑scale workloads needing massive throughput/IOPS in one AZ

Multi‑AZ 2Second1Production workloads needing AZ resilience and higher throughput
File system settings

What you configure once

  • VPC, subnet(s), security group, and an encryption key (AWS‑managed by default, or your own KMS key)
  • SSD storage capacity, throughput capacity, and IOPS mode
  • Backup retention window, daily backup time, weekly maintenance window
  • The fsxadmin password used to reach the ONTAP CLI/REST API
SVM settings

What you configure per‑namespace

  • A root volume security style — UNIX, NTFS, or mixed — which sets how permissions are interpreted by default
  • Optionally join an Active Directory domain (self‑managed or AWS Managed Microsoft AD) so SMB clients authenticate against real AD identities
  • Or skip AD entirely and run as a standalone workgroup with local SVM users
Multiprotocol, on the same bytes

A single volume can be reached over NFS (v3, v4.0, v4.1, v4.2), SMB (2.0, 3.0, 3.1.1), iSCSI, NVMe/TCP, and even the S3 API via an Access Point — simultaneously. ONTAP maps UNIX UIDs/GIDs to Windows SIDs behind the scenes, so a Linux box and a Windows box can read and write the same files with permissions that make sense on both sides. iSCSI and NVMe/TCP are only available on file systems with 6 or fewer HA pairs.

Networking

FSx for ONTAP lives entirely inside one of your VPCs — there's no public‑internet path to it. Most "why won't this mount" problems trace back to one of three layers, covered below.

Where it sits in your VPC

A Single‑AZ file system takes one subnet, which defines its Availability Zone; its endpoints are simply secondary IP addresses on the active file server's elastic network interface (ENI), living inside that subnet's address range. A Multi‑AZ file system takes two subnets in two different AZs — a preferred subnet for the active node and a standby subnet for, well, the standby — plus a third address range you choose separately, used only for floating endpoint IPs that aren't tied to either subnet.

The mechanism, not magic

On failover, FSx doesn't move the IP address itself — it rewrites the routes in every VPC route table associated with the file system so the floating range now points at the new active node's ENI. Clients keep using the exact same IP and DNS name throughout; only the route changes, and the whole thing typically completes in under 60 seconds. The practical catch: this only happens automatically in route tables FSx actually manages. A client outside the deployment VPC only keeps working through a failover if its path runs through one of those managed route tables — usually via a Transit Gateway attachment, or a Network Load Balancer in front of the file system.

The preferred subnet is fixed at creation and can't be changed afterward to force a manual failover — failover is automatic‑only, triggered by AWS detecting an actual fault, not something you toggle yourself.

Per‑SVM endpoints

Each SVM exposes up to five logical endpoints. NFS, SMB, and management almost always share a single IP. iSCSI and NVMe/TCP get their own separate IP per node instead of a floating IP — because block storage needs the client's own multipathing rather than a transparent route switch. That's why iSCSI/NVMe clients run native OS multipathing (MPIO on Windows, multipath on Linux) and connect to both nodes' addresses directly, letting the operating system — not FSx — handle the failover for block protocols.

Three layers of access control

A failed mount is almost always one of these three layers saying no — check them in order.

1 · AWS

Security groups

The VPC‑level firewall on the file system's ENI. Needs the right inbound ports: NFS — 111, 635, 2049, 4045–4046; SMB — 445 (plus 135, 137–139 for legacy clients); iSCSI — 3260; management/CLI — 22, 443.

2 · ONTAP

Export policies, shares, igroups

Independent of security groups. NFS export policies allow specific IPs/CIDRs per volume; SMB relies on share permissions plus NTFS ACLs; iSCSI uses igroups that map specific client IQNs to specific LUNs.

3 · Filesystem

File & folder permissions

Ordinary UNIX mode bits or Windows ACLs, evaluated once you're actually connected. No IAM role or AWS permission is involved anywhere in this chain — these are network‑storage protocols, not AWS API calls.

Migrating from on‑premises

Which tool you reach for depends entirely on what's sitting at the source.

From on‑premises ONTAP — SnapMirror

SnapMirror does block‑level, asynchronous replication natively between ONTAP systems, over Direct Connect or VPN. Two details make it the clear choice whenever the source is already ONTAP: deduplicated and compressed data stays deduplicated and compressed in transit, so less actually moves over the wire than a naive file copy would; and it stays efficient even on volumes with tens of millions of small files, exactly where naive copy tools tend to choke.

The high‑level flow: create a destination volume on FSx (type DP, sized at least as large as the source), gather both clusters' intercluster LIF addresses (the FSx side from the console's Network & Security tab, the on‑prem side from the ONTAP CLI), establish cluster peering and then SVM peering, create the SnapMirror relationship and kick off the baseline transfer, let it run incremental updates for as long as you like, and finally cut over — break the mirror, repoint clients, retire the source.

Why this de‑risks the migration

Because incremental updates can run indefinitely before cutover, the "big scary migration window" shrinks down to just the final cutover step — flipping DNS or mount points — not the entire data copy.

From anything else — AWS DataSync

For non‑ONTAP sources — generic NFS/SMB file servers, other FSx file systems, EFS, S3, or moving between FSx for ONTAP file systems, regions, or accounts — DataSync is the recommended tool. It's agent‑based (you deploy an agent in your environment unless both ends are AWS‑native) and copies file data plus metadata: ownership, timestamps, permissions.

A few real constraints worth knowing before you plan around it: it only supports NFSv3 against FSx for ONTAP locations, not v4; it can't reach FSx for ONTAP over iSCSI at all; SMB transfers require NTLM authentication on the FSx side, not Kerberos; and to preserve Windows ACLs across an SMB‑to‑SMB transfer, both sides' accounts need to be in the same AD domain or have a trust relationship between domains.

Keeping identity and access intact

If you're already on Active Directory, the cleanest path is pointing the new SVM at that same domain — or a domain with a one‑way trust — so existing users, groups, and NTFS permissions carry over with no re‑mapping. Some migrations even keep the original DNS name resolving to the new file system, so client mount strings and application configs don't need to change at all.

When bandwidth is the real bottleneck

For datasets large enough that Direct Connect or VPN would take too long, the AWS Snow Family (Snowcone, Snowball Edge) copies data onto a physical device on‑site, ships it to AWS, and ingests it directly — after which SnapMirror or DataSync only has to catch up on the smaller delta that accumulated while the device was in transit.

Glossary

File system
Top‑level FSx for ONTAP resource. Equivalent to an on‑premises ONTAP cluster.
HA pair
Two file server nodes in active/standby. 1 per file system for Gen 1 & Multi‑AZ Gen 2; up to 12 for Single‑AZ Gen 2.
SVM
Storage Virtual Machine — a logical, multi‑tenant file server with its own data & admin endpoint. Not a compute VM.
Volume
A virtual container for files. Doesn't consume capacity itself — only the data inside it does.
Primary / SSD tier
User‑provisioned, high‑performance storage for the active working set. Billed flat regardless of use.
Capacity pool tier
Fully elastic, AWS‑managed cold storage. Billed only for actual consumption.
Tiering policy
Per‑volume setting (None / Snapshot‑only / Auto / All) controlling what moves to the capacity pool.
Cooling period
How long a block must sit untouched before it's eligible to tier out. Starts counting at write time.
Single‑AZ / Multi‑AZ
Deployment type — one zone vs. synchronously replicated, auto‑failover across two zones.
Generation 1 / 2
FSx for ONTAP hardware generation. Gen 2 Single‑AZ supports scaling out to multiple HA pairs.
BlueXP
NetApp's SaaS console for deploying & managing Cloud Volumes ONTAP (not used by FSx for ONTAP).
Connector
An EC2 instance BlueXP uses to orchestrate Cloud Volumes ONTAP in your account.
Aggregate
The storage pool behind one HA pair. The SSD tier is the sum of all aggregates across all HA pairs.
ENI
Elastic Network Interface — the virtual network card in your VPC that a file server's IP addresses live on.
Floating IP
A Multi‑AZ endpoint IP that isn't tied to a subnet. FSx redirects it to the active node via route‑table updates on failover.
Junction path
The path where a volume is mounted into its SVM's namespace — what NFS clients actually browse to.
Security style
UNIX, NTFS, or mixed — how a volume interprets and enforces permissions across protocols.
Export policy
ONTAP's own per‑volume NFS firewall — a list of allowed client IPs/CIDRs, independent of AWS security groups.
Igroup
A named group of client iSCSI initiator IDs (IQNs) that's mapped to specific LUNs.
Intercluster LIF
The logical interface used for cluster peering and SnapMirror transfers between two ONTAP systems.
SnapMirror
NetApp's native block‑level replication tool, used to migrate or replicate between ONTAP systems.
DataSync
AWS's agent‑based data transfer service, used for migrating from non‑ONTAP sources to FSx for ONTAP.
Direct Connect / VPN
The two standard ways to link an on‑premises network to a VPC for online migration or hybrid access.
Transit Gateway
An AWS hub used to extend a Multi‑AZ file system's floating‑IP routes to peered VPCs or on‑premises networks.
