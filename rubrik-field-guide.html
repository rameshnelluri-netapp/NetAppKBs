SLA Domains explained

The single policy object that replaces manually scheduling backups for every server or VM.

What it is

An SLA Domain is a policy-based backup rule. Instead of configuring backup frequency, retention, replication, and archival separately for every workload, you define those settings once in an SLA Domain and assign it to whatever needs that protection level — VMs, databases, filesets, or NAS shares.

Why it matters

It simplifies backup management, ensures policy-based protection across the environment, improves compliance, supports automation, reduces manual configuration, and makes large environments far easier to manage and audit.

ASSIGN ONCE — RUBRIK HANDLES SNAPSHOTS, RETENTION, REPLICATION, AND ARCHIVAL FROM THERE

Common SLA types

🥇 Gold SLA

Critical production workloads

Mission-critical databases, ERP systems, payment applications — shortest RPO, longest retention.

🥈 Silver SLA

Medium-priority applications

Application servers, internal tools, reporting servers — balanced frequency and retention.

🥉 Bronze SLA

Low-priority workloads

Test servers, development systems, non-critical VMs — lighter protection footprint.

SLA Domain components

Snapshot frequency · retention period · replication target · archival location · backup window · first full backup behavior · compliance status.

Real-time example — production SQL Server

Business requirement: back up every 4 hours, retain for 30 days, replicate to a DR site, and archive a monthly copy to cloud. Assign the SQL Server to a Gold_SLA domain configured with exactly those parameters — Rubrik then runs snapshots, replication, and archival automatically with no per-server scheduling required.

What is an SLA Domain in Rubrik?

An SLA Domain in Rubrik is a policy-based backup configuration that defines how frequently data should be backed up, how long it should be retained, whether it should be replicated or archived, and whether the workload is compliant with the defined protection policy.

VMware backup workflow in Rubrik

From vCenter discovery to indexed, restorable recovery points — eight stages, mostly automated.

1

Add vCenter to Rubrik

Rubrik connects to vCenter and discovers ESXi hosts, clusters, datastores, folders, tags, and VMs.

2

Assign SLA Domain

The VM is assigned to an SLA Domain manually, or automatically through folder-, cluster-, host-, or tag-based rules.

3

Rubrik triggers a snapshot

During backup, Rubrik creates a VMware snapshot using VMware APIs. The first backup is always full; later backups use Changed Block Tracking (CBT) for incrementals.

4

Data transfer to the Rubrik cluster

Changed data blocks are transferred from the VMware environment to the Rubrik cluster, using the best available transport mode (commonly NBDSSL).

5

Deduplication and compression

Rubrik stores the backup efficiently using global deduplication and compression across the cluster.

6

Snapshot removal

After the backup completes, the VMware-level snapshot is removed to avoid datastore growth or VM performance impact.

7

Indexing and cataloging

Rubrik indexes metadata so individual files, folders, or full VMs can be searched and restored quickly later.

8

Restore options

From the same backup, you can perform a full VM restore, instant recovery / live mount, file-level recovery, disk export, or restore to an alternate location.

How would you summarize this workflow in an interview?

In Rubrik, VMware backups are SLA-based. First we add vCenter to Rubrik, then Rubrik discovers the VMware inventory. We assign an SLA Domain to the VM, or use automatic protection through folders, clusters, hosts, or tags. When the backup runs, Rubrik takes a VMware snapshot, takes the first backup full, and uses CBT-based incrementals afterward. Data is transferred to the Rubrik cluster, stored efficiently, indexed, and made available for restore. After backup completion, the VMware-level snapshot is removed.

Adding a NAS share

Choose share type (NFS or SMB), provide the hostname/IP and export path, give it a display name, and supply credentials — typically a username/password with sufficient read access for backup, plus write access on the target if restores will land there.

Creating a fileset

A fileset names the NAS share to protect and defines include/exclude paths — for example, including /data and /reports while excluding /temp and /cache to skip transient data.

StageWhat it controls
SLA Domain assignmentSets backup frequency, retention period, replication, and archival for the fileset — same model as VM or database protection.
On-demand backupRun a backup outside the schedule when needed, and monitor it through the standard job activity view.
Browse backup snapshotDrill into a point-in-time snapshot to see exactly which files and folders were captured, down to size and path.
RestoreRestore individual files/folders to original location or an alternate path, choosing whether to overwrite existing data.

Types of NAS supported

NFS (Linux/Unix NAS exports) and SMB (Windows File Server shares).

Permissions required

Backup needs read access to the share; restore needs write access to the destination.

Key point for NetApp

SnapDiff-style integration (where supported) helps speed up incremental backups by leveraging the storage array's own change-tracking rather than a full file walk.

  • Rubrik supports NAS backup for both NFS and SMB shares.
  • Filesets define exactly what to include or exclude within a share.
  • The SLA Domain controls backup frequency, retention, and replication — same as any other protected object.
  • Read access is required for backup; write access is required for restore — keep credentials scoped accordingly.
  • File-level restore lets you recover specific files or folders without restoring an entire share.

    CloudOut archival explained

    Rubrik's mechanism for moving aging backup snapshots off local storage and into cheaper, longer-term archive targets.

    CloudOut is Rubrik's archival capability — it moves older backup snapshots from on-prem Rubrik storage to cloud or external archive storage for long-term retention, governed entirely by the archive policy configured inside an SLA Domain.

    PRODUCTION → LOCAL SNAPSHOT → SLA-DRIVEN ARCHIVE POLICY → ARCHIVE TARGET → LONG-TERM RETENTION

    How it works

    Rubrik first takes a local backup snapshot. The SLA Domain decides when that snapshot should be archived. The data is then copied to the configured archive location, and Rubrik retains the archive copy according to the retention policy. During a restore, Rubrik can retrieve the required snapshot back from the archive location as needed.

    Why CloudOut is used

    Long-term retention for compliance · cost optimization versus keeping everything on local fast storage · an offsite DR copy · a modern replacement for physical tape · and keeping local Rubrik storage free for faster, more recent recovery points.

    AreaWhat it means
    Local snapshotUsed for fast backup and quick restore — the first line of recovery.
    CloudOut archiveUsed for long-term, lower-cost storage — not the fastest path to restore.
    SLA DomainControls both backup frequency and archive retention/timing in one place.
    Archive targetAWS S3, Azure Blob, GCP, generic object storage, NFS, or tape.
    Restore impactRestoring from archive typically takes longer than restoring from local Rubrik storage.
    SecurityRubrik uses encrypted transfer where possible, and can dedupe, compress, and encrypt archived data depending on what the target supports.

    Key takeaway

    Local backup is for fast restore. CloudOut archive is for long-term retention and offsite protection. They serve different purposes in the same recovery strategy, not interchangeable copies of the same thing.

    Daily health checks in Rubrik

    The backup administrator's job isn't done once schedules are configured — it continues every single day.

    Daily health checks verify that the backup environment is stable, protected, and ready for recovery — covering backup job status, SLA compliance, cluster health, storage usage, replication status, and any security-related alerts.

    Early issue detection

    Catch problems before they compound into a missed recovery point.

    Improved backup success rate

    Consistent monitoring catches drift before it becomes a pattern of failures.

    Better SLA compliance

    Keeps protection commitments measurable and auditable.

    Faster troubleshooting

    Daily familiarity with the environment shortens diagnosis time when something does break.

    Daily health check list

  • Backup job failures — check for failed or warning states across backup jobs.
  • SLA Domain compliance — confirm SLA domains are at or near 100% compliant.
  • Protected and unprotected workloads — review anything newly added that isn't yet protected.
  • Cluster node health — ensure all nodes are healthy and connected.
  • Storage capacity usage — monitor consumption trends before they become urgent.
  • Replication and archival status — verify both are completing as expected.
  • Ransomware or anomaly alerts — review any threat or anomaly detections.
  • Snapshot availability — confirm snapshots are actually being created on schedule.
  • Failed recovery points — check for any gaps in recoverable history.
  • Open alerts and warnings — review and act on anything outstanding.

    • Why this matters as a backup administrator

    The job isn't only to configure backups — it's to ensure backups are running successfully, recovery points are actually available, and the environment stays healthy every day. A small backup failure today can become a major recovery risk tomorrow if it isn't monitored properly.

    06

    Backup failure troubleshooting

    Failures are routine in daily operations — what matters is finding the root cause quickly, not just rerunning the job.

    Common reasons backups fail

    Network connectivity issues · VM snapshot failure (VMware tooling, resources, or configuration) · credential or permission issues · storage capacity problems on the Rubrik cluster · SLA Domain misconfiguration · guest OS or application-level issues · replication or archival failure · temporary workload unavailability · cluster or node health issues.

    The mindset that matters

    Backup failure troubleshooting isn't only about rerunning the job — it's about understanding why the job failed and preventing the same issue from happening again. As a backup administrator, monitor failed jobs daily, fix recurring issues, document root cause, and keep business-critical workloads protected.

    Basic troubleshooting approach

    1

    Check the failed job details

    Review job status and the failure summary first.

    2

    Review error message and event logs

    Check detailed error and event logs for the specific failure signature.

    3

    Verify workload availability

    Confirm the source VM or application is actually up and reachable.

    4

    Check network connectivity

    Verify connectivity between all components in the backup path.

    5

    Validate credentials and permissions

    Ensure the service account or credentials used are correct and valid.

    6

    Review SLA Domain assignment

    Verify the SLA Domain and its schedules are configured as intended.

    7

    Check Rubrik cluster health

    Ensure all nodes and services on the cluster are healthy.

    8

    Verify storage capacity

    Check capacity headroom and ensure there's enough space for the job.

    9

    Retry the failed job

    Run the job again once the underlying issue is actually fixed — not before.

    10

    Escalate if repeated failures occur

    Involve the support team if the issue persists after the steps above.

    The three-part framing worth remembering

    Failure is an alert. Troubleshooting is action. A successful backup is recovery confidence. Treat every failure as a signal to investigate, not just a button to retry.
