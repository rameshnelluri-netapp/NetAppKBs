SAME EXPORT, TWO PROTOCOLS, ONE SERVER AT 192.168.0.131

NFSv3 vs NFSv4.1 — what actually differs on the wire

Both versions hand you a POSIX-looking filesystem. The interesting part is everything underneath that you can't see until you capture packets, kill a daemon, or reboot a server mid-lock. This guide walks through exactly that — using one real client, one real server, two mounts of the same volume.

One write, two protocols

NFSv3 — discrete RPCs NFSv4.1 — one COMPOUND
v3
LOOKUP
CREATE
GETATTR
WRITE

v4.1
COMPOUND [ SEQUENCE → LOOKUP → OPEN → WRITE → GETATTR → CLOSE ]
5 round-trips vs 1. NFSv3 issues each operation as its own RPC call/reply. NFSv4.1 bundles a whole chain of operations into a single COMPOUND request — fewer round-trips for the same logical file write, which matters most on high-latency links.
00 — Ground truth

Check what you're actually mounting

Before comparing anything, confirm the negotiated version per mount — don't assume it from the export name.

[root@linux2 ~]# nfsstat -m
# /mnt/nfs and /mnt/v4 point at the SAME export — only the version differs
/mnt/nfs from 192.168.0.131:/vol_nfs/nfs
 Flags: rw,relatime,vers=3,proto=tcp,mountport=635,mountproto=udp,local_lock=none

/mnt/v4 from 192.168.0.131:/vol_nfs/nfs
 Flags: rw,relatime,vers=4.1,proto=tcp,clientaddr=192.168.0.63,local_lock=none
Why this pairing matters: mounting the same backend export over both versions means the protocol is the only variable left. Any difference you observe in your captures is attributable to the protocol, not the storage or the data.
01 — Locking

Same behavior, completely different machinery

flock blocks the same way on both mounts. That's the trap — the user-visible result is identical, so the difference only shows up underneath, in what's actually carried on the wire.

NFSv3 bolted on

  • Locking is not part of the NFS protocol at all — it's a side protocol called NLM (Network Lock Manager).
  • Runs as its own RPC service, its own port, its own daemon (rpc.lockd).
  • Crash/reboot recovery depends on a second side-channel daemon, rpc.statd (NSM), watching for reboot notifications.
  • Visible in rpcinfo -p as nlockmgr — but that just means the daemon exists, not that it was used in your test.

NFSv4.1 native

  • LOCK / LOCKU are first-class NFS operations, sent inside a COMPOUND over the same port 2049.
  • No separate daemon, no separate port — lock state lives with the client's session.
  • Recovery is spec-defined: a structured grace period on server restart, not a guess from a side daemon.

Prove it — two-terminal contention test

# Terminal 1 — hold the lock for 30s
$ flock /mnt/nfs/test1 -c "echo locked-v3; sleep 30"

# Terminal 2 — started immediately, should HANG until Terminal 1 finishes
$ flock /mnt/nfs/test1 -c "echo got-lock-v3"

# Repeat identically against /mnt/v4/test1 — same blocking behavior, different wire traffic
A single flock ... -c "echo got lock" with no contender proves nothing — it acquires and releases instantly. You need two terminals racing for the same lock, captured with tcpdump, to actually see NLM vs native LOCK traffic.
02 — Statefulness

Who notices when a client disappears?

This is the difference that actually has teeth — but only under failure, not on the happy path.

ScenarioNFSv3NFSv4.1
Client crashes mid-lockrpc.statd must notice and broadcast a reboot notificationServer expires the client's lease deterministically
Server rebootsNLM has no native recovery — relies on NSM side-channelSpec-defined grace period; clients reclaim state on schedule
Liveness signalExternal daemon, separate protocol (NSM)Built-in lease renewal, piggybacks on normal ops

In your topology, the server is the storage box — 192.168.0.131 — and your linux2 box is the client. The lease lives on the server; the client is responsible for renewing it before it expires (commonly ~90s, implementation-dependent).

# Inspect live NFSv4 client lease state on the server (if Linux-based nfsd)
[root@storage ~]# cat /proc/fs/nfsd/clients/*/info
03 — Round trips

Compounding: where v4.1's design pays off

Locking parity is a wash. Compounding is where you'll actually see fewer packets for identical work — count them yourself.

1

Capture each version separately, same operation

$ tcpdump -i any -w v3_create.pcap host 192.168.0.131 and port 2049 -nn
$ touch /mnt/nfs/file1 && echo hi > /mnt/nfs/file1
# Ctrl+C, then repeat against /mnt/v4
$ tcpdump -i any -w v4_create.pcap host 192.168.0.131 and port 2049 -nn
$ touch /mnt/v4/file1 && echo hi > /mnt/v4/file1
2

Count packets per capture

$ tcpdump -r v3_create.pcap -nn | wc -l
$ tcpdump -r v4_create.pcap -nn | wc -l

Expect fewer, larger frames in the v4.1 capture — multiple logical operations riding inside one COMPOUND.

3

Open both in Wireshark, filter nfs

v3 shows separate LOOKUP / CREATE / WRITE / GETATTR / COMMIT calls. v4.1 shows one or more COMPOUND frames — expand them to see the bundled operation list.

Why strace -e trace=network shows nothing here: touch and shell redirection only make filesystem syscalls (open, write, close). The actual RPC traffic is generated by the kernel's NFS client module, invisible to a userspace process trace. That's exactly why packet capture, not syscall tracing, is the right tool for this comparison.
