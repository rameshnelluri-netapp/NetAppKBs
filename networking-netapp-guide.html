DHCP and the DORA process

How a device gets handed an IP address automatically, without anyone configuring it by hand.

What it does

Hands out IP addresses and network configuration automatically, so devices don't need static, manually entered settings.

Ports used

Runs over UDP — port 67 on the server side, port 68 on the client side — chosen for speed over TCP's overhead.

DORA: DISCOVER → OFFER → REQUEST → ACKNOWLEDGE
StepDirectionWhat happens
Discover0.0.0.0:68 → 255.255.255.255:67The client, with no IP yet, broadcasts a request asking if any DHCP server is listening.
OfferServer IP:67 → 255.255.255.255:68A DHCP server responds with a proposed IP address and configuration details (subnet, gateway, DNS).
Request0.0.0.0:68 → 255.255.255.255:67The client broadcasts back, formally requesting the offered address (so other servers know it's taken).
AcknowledgeServer IP:67 → 255.255.255.255:68The server confirms the lease, and the client can now use the assigned IP.

DNS resolution, step by step

Domain names are for humans; IP addresses are what the network actually routes on. DNS is the translation layer between them.

Forward lookup

Domain Name → IP Address. The everyday case: typing a hostname and getting routed to the right server.

Reverse lookup

IP Address → Domain Name. Used for verification, logging, and anti-spam/email authentication checks.

DNS runs over UDP port 53 for both queries and responses (falling back to TCP for larger replies, such as zone transfers).

FORWARD LOOKUP (STEPS 1–2) AND REVERSE LOOKUP (STEPS 3–4)

Why does DNS use UDP instead of TCP?

Most DNS queries and responses are small enough to fit in a single packet, so the connection setup overhead of TCP isn't worth it — UDP's speed wins for the common case. DNS does fall back to TCP for larger payloads, such as zone transfers between name servers or responses that exceed a single UDP packet.

ONTAP architecture overview

NetApp's storage operating system, built as a clustered architecture where multiple nodes act as one logical storage system.

ONTAP is the operating system underpinning NetApp storage — used for VMware environments, Windows file shares, Linux/UNIX NFS workloads, databases, backup targets, and disaster recovery, among others. Its architecture is built around a small set of composable concepts that combine to deliver scalability, high availability, and rich data protection.

CLUSTER → NODES → SHARED BUILDING BLOCKS (AGGREGATES, VOLUMES, SVMs, LIFs, PROTOCOLS, SNAPSHOTS, SNAPMIRROR)

Cluster

A group of NetApp nodes managed as one system — provides scalability, high availability, and non-disruptive operations.

Node

A physical or virtual controller with CPU, memory, network ports, and disk shelves. Nodes pair up so a partner can take over if one fails.

HA Pair

Two nodes connected for high availability — if one fails, its partner takes over the workload automatically.

Aggregate / Local Tier

A collection of physical disks grouped together to provide the raw capacity from which volumes are created.

Volume

The logical storage container carved out from an aggregate — where databases, VMware datastores, and file shares actually live.

SVM

A Storage Virtual Machine — a logical storage server inside ONTAP, with its own LIFs, volumes, protocols, and security settings.

Basic data access flow — example: CIFS / NFS

1) Client/application sends a request to an ONTAP data LIF → 2) the LIF belongs to an SVM → 3) the SVM checks protocol and security settings → 4) the request is directed to the correct volume → 5) the volume reads/writes data from the underlying aggregate/local tier → 6) ONTAP returns data back to the client.

Data protection building blocks

Snapshot — a point-in-time copy of data, used for fast recovery, file restores, volume restores, and ransomware recovery.

SnapMirror — replication between source and destination ONTAP systems, used for disaster recovery, data migration, and remote copies.

SnapVault — a backup relationship (depending on ONTAP version/design) used for longer-term backup retention.

Common health checks to run

Cluster health · node health · HA status · aggregate capacity · volume status · SVM status · LIF status · protocol status · disk health · snapshot usage · SnapMirror status · network port status · performance (latency, IOPS, throughput).

How would you explain ONTAP architecture in an interview?

NetApp ONTAP uses a clustered architecture where multiple nodes work together as a single storage system. The main components are clusters, HA pairs, aggregates or local tiers, SVMs, LIFs, and protocols. Clients access data through LIFs connected to SVMs, and data is stored in volumes created from aggregates. ONTAP also provides high availability, snapshots, and replication through SnapMirror, with support for both NAS and SAN protocols.

CIFS / SMB configuration on ONTAP

The protocol behind every Windows file share, department folder, and backup staging area in an enterprise NAS environment.

What it is

SMB (Server Message Block) — often still called CIFS from its earlier implementation — is the network protocol providing file-level access to Windows users and applications. A typical path looks like \\fileserver01\Finance_Share.

Where it shows up

Windows file shares, department shared folders, user home directories, application file storage, backup staging folders, file server migrations, and broader enterprise NAS environments.

SVM → DATA LIF → AD JOIN → VOLUME → SHARE → SHARE PERMS → NTFS PERMS → CLIENT TEST

Requirements before you start

An existing or new SVM · a data LIF for client access · Active Directory and DNS reachability · firewall rules allowing TCP 445 · AD users/groups already provisioned for permissions.

Key concepts to keep straight

SVM hosts the CIFS service · CIFS server is the SMB identity created inside the SVM · Data LIF is the network interface clients connect through · Share permission vs. NTFS permission control access at different layers · UNC path (\\server-name\share-name) is how clients reach the share.

SymptomLikely cause to check
Can't resolve server nameDNS resolution issue — confirm forward/reverse records exist and are reachable from the client.
Authentication failuresAD domain join failure, or the SVM's machine account isn't healthy in AD.
Access denied despite valid loginIncorrect share-level permissions, or NTFS folder/file permissions blocking the user.
Connects intermittently or times outData LIF connectivity issue, or a routing/network path problem to the SVM.
Can't reach the share at allFirewall blocking TCP 445, or the user/group isn't part of the required AD group.
Share simply isn't thereThe SMB service on the SVM isn't running — verify CIFS server status.
  • SMB/CIFS is the primary protocol for Windows file sharing in enterprise NAS environments.
  • Proper configuration of the SVM, LIF, AD join, share, and permissions all have to line up — a gap in any one breaks access.
  • Share permissions and NTFS permissions both apply simultaneously; plan for the more restrictive one to govern actual access.
  • Always validate access from an actual Windows client, not just from the storage side — many issues only surface client-side.
