02 — Interoperability

FOS / ONTAP compatibility

Broadcom's compatibility matrix and NetApp's qualification of a given FOS patch level don't always move in lockstep. Check both before you touch firmware.

FOS branchStatusNotes
10.0.x Current target path Latest release 10.0.0a (patch 10.0.0a1), GA December 2025. Newest Gen 7/Gen 8 platforms.
9.2.x Supported 9.2.0a confirmed compatible with ONTAP 9 for both Fabric MetroCluster and standard SAN.
9.0.x Check IMT NetApp IMT qualification can lag Broadcom's release — e.g. a switch shipped with 9.0.1d while an ONTAP release was only qualified to 9.0.0b.
8.2.x Legacy / retiring Still posted for select platforms; confirm target-path status before deploying new.
⚠

Always confirm against the source of truth: use the NetApp Interoperability Matrix Tool filtered to your exact ONTAP version and switch model, and Broadcom's Fabric OS Release Support and Posting Matrix for target-path status. Don't infer compatibility from a prior ONTAP release.

03 — Post-allocation

Zoning after LUN allocation

Single-initiator, single-target zoning — one zone per host-HBA-to-NetApp-LIF pair, repeated per fabric for multipathing.

1

Gather WWPNs

Pull target WWPNs from ONTAP and initiator WWPNs from the host before touching the switch.

ontap · ssh
network fcp adapter show -fields wwpn
network interface show -vserver <svm> -data-protocol fcp
2

Confirm physical connectivity

Verify both the host HBA and NetApp target port are logged in and note their switch ports.

switch · cli
switchshow
3

Create aliases (recommended)

Aliases keep zone definitions readable instead of working in raw WWPNs.

switch · cli
alicreate "host01_hba0", "10:00:00:00:c9:xx:xx:xx"
alicreate "netapp_svm1_lif01", "20:00:00:a0:98:xx:xx:xx"
4

Create the zone

One initiator, one target — keeps RSCN traffic and blast radius contained during fabric changes.

switch · cli
zonecreate "host01_hba0_netapp_lif01", "host01_hba0; netapp_svm1_lif01"
5

Add the zone to the configuration

Adds the new zone to a defined config — doesn't activate it yet.

switch · cli
cfgadd "PRODUCTION_CFG", "host01_hba0_netapp_lif01"
6

Save the configuration

Writes the config to the switch's defined configuration.

switch · cli
cfgsave
7

Enable the configuration

This is the step that actually pushes zoning live to the fabric.

switch · cli
cfgenable "PRODUCTION_CFG"
Activates fabric-wide
8

Verify the zone is active

switch · cli
cfgshow
zoneshow "host01_hba0_netapp_lif01"
9

Repeat for redundant paths

Repeat steps 3–8 on Fabric B, and for every additional HBA/LIF pair, so multipathing spans both fabrics.

10

Verify end to end from the host

Rescan HBAs, confirm login, and check the LUN is visible and multipathed correctly.

linux + ontap
echo "1" > /sys/class/fc_host/hostX/issue_lip
multipath -ll
# on ONTAP
network fcp adapter show -instance
lun mapping show
11

Document

Record zone names, WWPNs, and which fabric/switch each pair traverses — it matters most during troubleshooting, not during setup.

ⓘ

MetroCluster or NPIV/Access Gateway? MetroCluster also requires zoning the FC-VI/ISL ports between fabrics, with stricter switch-model and FOS matching across sites. In Access Gateway mode, WWPN discovery happens against the upstream fabric switch, not the AG device itself.

04 — Maintenance

Fabric OS upgrade procedure

Non-disruptive firmware upgrade (NDFU) sequence for single switches and dual-CP directors. Upgrade one fabric completely, validate, then move to the second.

1

Plan the upgrade path

Confirm the target release is on the current Target Path (not just Posted), check the NetApp IMT against your ONTAP version, and confirm whether the jump requires intermediate hops — FOS often can't skip major versions in one step.

switch · cli
version
switchshow
firmwareshow   # director: confirms both CPs, HA sync
haShow         # director only
2

Back up the configuration

Your rollback safety net — do this even though the upgrade itself shouldn't touch config.

switch · cli
configupload
supportsave    # full diagnostic snapshot
3

Check fabric and switch health

Resolve marginal ports, faulted blades, or degraded PSUs before upgrading — never upgrade a switch already in a warning state.

switch · cli
switchstatuspolicyshow
switchstatusshow
porterrshow
slotshow       # directors
sensorshow
4

Confirm HA state (director only)

Must show the standby CP synced — otherwise the upgrade cannot be non-disruptive.

switch · cli
haShow
Blocks NDU if unsynced
5

Stage the firmware

Make the FOS package reachable on an FTP/SFTP/SCP server accessible from the switch's management IP. Verify checksum if provided.

6

Run the firmware download

On a director, this automatically upgrades the standby CP, fails over, then upgrades the former active CP — both end in sync on the new version.

switch · cli
firmwaredownload
# prompts: server IP, protocol, path, credentials, filename
7

Monitor progress

switch · cli
firmwaredownloadstatus
8

Verify post-upgrade state

Confirm both CPs report the new version, HA is re-synced, and every port that was online before is online again.

switch · cli
version
firmwareshow
haShow
switchshow
9

Check the fabric

switch · cli
fabricshow
nsshow
zoneshow
10

Validate host and storage connectivity

Confirm NetApp target ports are logged in and LIFs are up; confirm host multipath software shows every expected path active again.

ontap
network fcp adapter show
11

Repeat per switch — one fabric at a time

Never upgrade both fabrics simultaneously. Finish and validate Fabric A before starting Fabric B, so a working path exists throughout.

Fabric A
Upgraded & validated
→
Fabric B
Begin only after A is stable
12

Close out

Take a fresh supportsave for your records and update your documentation or CMDB with the new FOS version per switch.

⚠

MetroCluster environments: coordinate the upgrade sequence with NetApp's documented order relative to controller failover state — don't treat it as a standalone switch task.
