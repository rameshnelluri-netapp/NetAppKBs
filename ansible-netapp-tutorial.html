Section 01

What is Ansible?

Ansible is an open-source IT automation engine that lets you describe infrastructure tasks in simple human-readable YAML files called playbooks. Instead of logging into every system and running commands manually, you define what you want — and Ansible figures out how to do it.

For NetApp storage engineers, Ansible is transformative: tasks that used to take 30 CLI commands across multiple SVMs can be reduced to a single playbook run that executes in seconds, is repeatable, and is safe to commit to Git.

agentless

No agent required

Ansible talks to ONTAP via REST API over HTTPS. Nothing is installed on your NetApp cluster.

idempotent

Safe to re-run

Running a playbook 10 times has the same result as once. If the volume already exists, Ansible skips it — no error, no duplicate.

yaml

Human-readable

Playbooks are plain YAML. Storage admins with zero programming background can read and write them within days.

certified

NetApp-certified

NetApp maintains an official Ansible Galaxy collection with 100+ modules covering the entire ONTAP API surface.

scalable

Multi-cluster

One playbook can target 50 clusters simultaneously. Scale from 1 to 500 nodes with no code change.

git

Version controlled

Your entire storage config lives in Git. Every change is tracked, reviewable, and rollback-able.

Why Ansible specifically for NetApp? NetApp provides the netapp.ontap Ansible Galaxy collection — maintained by NetApp engineers — with modules for every ONTAP operation: volumes, SVMs, LUNs, SnapMirror, SVM-DR, NFS/CIFS, igroups, QoS policies, and much more. You don't need to write API calls yourself.
Section 02

Core Ansible Concepts

Before writing NetApp playbooks, understand these six building blocks. Every automation you build uses all of them.

The six pillars of Ansible
01 — Inventory

A file listing all the hosts (clusters) Ansible will manage. Contains IPs, usernames, and variable references. Can be static YAML or dynamic (pulled from CMDB).

02 — Playbook

A YAML file describing what to do and where. Contains one or more plays, each targeting a host group and running a list of tasks.

03 — Module

The unit of work. na_ontap_volume creates/modifies/deletes volumes. na_ontap_snapmirror manages SnapMirror. Each module handles one resource type.

04 — Variables

Named values used across tasks. Can be defined in inventory, playbooks, or separate var files. Referenced as {{ variable_name }} in YAML. Enables reusable playbooks.

05 — Role

A packaged, reusable bundle of tasks with its own defaults, vars, and templates. Example: a "provision_svm" role you call with different var files per environment.

06 — Vault

Ansible's encryption system. Encrypts passwords and sensitive data so your playbooks can be committed to Git safely. Decrypted at runtime using a vault password.

Key mental model — Ansible is declarative You don't write a script saying "if volume doesn't exist, run this command". You write "I want a volume with these properties". Ansible figures out whether to create, modify, or do nothing. This is what "idempotent" means in practice.
Section 03

How Ansible talks to NetApp ONTAP

Ansible runs on a control node (your laptop, a CI server, or AWX) and talks to ONTAP clusters over HTTPS REST API. Nothing is installed on the NetApp side — the netapp.ontap modules handle the API calls.

Section 04

Installation & Setup

Three commands and you're ready to automate your first ONTAP cluster.

BASH terminal
# Step 1 — Install Ansible and the NetApp Python library pip install ansible netapp-lib requests # Step 2 — Install the official NetApp ONTAP collection from Ansible Galaxy ansible-galaxy collection install netapp.ontap # Step 3 — Verify the collection is installed ansible-galaxy collection list | grep netapp

Inventory file

The inventory file tells Ansible which clusters to manage and how to connect to them.

YAML inventory.yml
all: children: ontap_clusters: hosts: cluster_primary: ansible_host: 192.168.1.10 # cluster management IP ansible_user: admin ansible_password: "{{ vault_ontap_password }}" https: true validate_certs: false # set true in production with valid cert cluster_dr: ansible_host: 192.168.2.10 ansible_user: admin ansible_password: "{{ vault_ontap_password }}" https: true validate_certs: false

Encrypting passwords with Vault

BASH terminal
# Create an encrypted vars file — you'll be prompted for a vault password ansible-vault create group_vars/all/vault.yml # Inside vault.yml add: vault_ontap_password: YourSecretPassword123 # Run a playbook with vault decryption ansible-playbook -i inventory.yml playbook.yml --ask-vault-pass
Lab environment tip Use ONTAP Select (free developer licence from NetApp support) or ONTAP Simulator to build a real ONTAP cluster on your laptop or a VM. Practice every playbook here before touching production. You get a fully functional two-node cluster with all ONTAP features enabled.

Section 06

Essential Playbook Examples

Here are the five most common storage automation tasks. Each playbook is production-ready with variables, error handling, and idempotency built in.

1 — Query cluster info (read-only, zero risk)

YAML 01_get_cluster_info.yml
--- - name: Get ONTAP cluster and volume information hosts: cluster_primary gather_facts: false collections: - netapp.ontap tasks: - name: Collect cluster info na_ontap_info: state: info gather_subset: - volume_info - aggregate_info - svm_info - snapmirror_info hostname: "{{ ansible_host }}" username: "{{ ansible_user }}" password: "{{ ansible_password }}" https: true validate_certs: false register: ontap_info - name: Print volume list debug: msg: "Volume: {{ item.key }} — State: {{ item.value.volume_state_attributes.state }}" loop: "{{ ontap_info.ontap_info.volume_info | dict2items }}"

2 — Create NFS volume with export policy

YAML 02_create_nfs_volume.yml
--- - name: Provision NFS volume on ONTAP hosts: cluster_primary gather_facts: false collections: - netapp.ontap vars: svm_name: svm_prod volume_name: vol_oracle_data size_gb: 500 junction_path: /oracle_data aggregate: aggr1_node1 allowed_clients: 10.10.0.0/24 tasks: - name: Create export policy na_ontap_export_policy: state: present name: "{{ volume_name }}_policy" vserver: "{{ svm_name }}" hostname: "{{ ansible_host }}" username: "{{ ansible_user }}" password: "{{ ansible_password }}" https: true validate_certs: false - name: Add export rule na_ontap_export_policy_rule: state: present policy_name: "{{ volume_name }}_policy" vserver: "{{ svm_name }}" client_match: "{{ allowed_clients }}" ro_rule: sys rw_rule: sys super_user_security: sys hostname: "{{ ansible_host }}" username: "{{ ansible_user }}" password: "{{ ansible_password }}" https: true validate_certs: false - name: Create NFS volume na_ontap_volume: state: present name: "{{ volume_name }}" vserver: "{{ svm_name }}" aggregate_name: "{{ aggregate }}" size: "{{ size_gb }}" size_unit: gb space_guarantee: none tiering_policy: auto junction_path: "{{ junction_path }}" export_policy: "{{ volume_name }}_policy" snapshot_policy: default percent_snapshot_space: 20 hostname: "{{ ansible_host }}" username: "{{ ansible_user }}" password: "{{ ansible_password }}" https: true validate_certs: false

3 — Full SVM provisioning in one playbook

This is where Ansible really shines — instead of 20+ CLI commands, one file creates the SVM, sets up networking, enables protocols, and configures DNS.

YAML 03_provision_svm.yml
--- - name: Full SVM provisioning hosts: cluster_primary gather_facts: false collections: - netapp.ontap vars: svm_name: svm_app01 allowed_protocols: [nfs, iscsi] lif_ip: 10.10.1.50 lif_netmask: 255.255.255.0 lif_home_node: node1 lif_home_port: e0c dns_domain: corp.example.com dns_servers: ["10.10.1.5", "10.10.1.6"] tasks: - name: Create SVM na_ontap_svm: state: present name: "{{ svm_name }}" allowed_protocols: "{{ allowed_protocols }}" hostname: "{{ ansible_host }}" username: "{{ ansible_user }}" password: "{{ ansible_password }}" https: true validate_certs: false - name: Create data LIF na_ontap_interface: state: present interface_name: "{{ svm_name }}_data_lif1" vserver: "{{ svm_name }}" address: "{{ lif_ip }}" netmask: "{{ lif_netmask }}" home_node: "{{ lif_home_node }}" home_port: "{{ lif_home_port }}" role: data protocols: [nfs, iscsi] hostname: "{{ ansible_host }}" username: "{{ ansible_user }}" password: "{{ ansible_password }}" https: true validate_certs: false - name: Configure DNS na_ontap_dns: state: present vserver: "{{ svm_name }}" domains: ["{{ dns_domain }}"] nameservers: "{{ dns_servers }}" hostname: "{{ ansible_host }}" username: "{{ ansible_user }}" password: "{{ ansible_password }}" https: true validate_certs: false - name: Enable NFS service na_ontap_nfs: state: present vserver: "{{ svm_name }}" service_state: started nfsv3: enabled nfsv4: enabled hostname: "{{ ansible_host }}" username: "{{ ansible_user }}" password: "{{ ansible_password }}" https: true validate_certs: false
Section 07

Data Protection Automation

This is where Ansible delivers the most value for NetApp admins. SnapMirror setup, SVM-DR configuration, and snapshot policy management become one-command operations.

4 — SnapMirror relationship setup

YAML 04_snapmirror_setup.yml
--- - name: Configure SnapMirror replication hosts: cluster_primary gather_facts: false collections: - netapp.ontap vars: source_vserver: svm_prod source_volume: vol_oracle_data dest_vserver: svm_dr dest_volume: vol_oracle_data_dr policy: MirrorAllSnapshots schedule: hourly tasks: - name: Create SnapMirror relationship na_ontap_snapmirror: state: present source_path: "{{ source_vserver }}:{{ source_volume }}" destination_path: "{{ dest_vserver }}:{{ dest_volume }}" relationship_type: extended_data_protection schedule: "{{ schedule }}" policy: "{{ policy }}" hostname: "{{ ansible_host }}" username: "{{ ansible_user }}" password: "{{ ansible_password }}" https: true validate_certs: false - name: Initialize SnapMirror (baseline transfer) na_ontap_snapmirror: state: present initialize: true source_path: "{{ source_vserver }}:{{ source_volume }}" destination_path: "{{ dest_vserver }}:{{ dest_volume }}" hostname: "{{ ansible_host }}" username: "{{ ansible_user }}" password: "{{ ansible_password }}" https: true validate_certs: false

5 — DR failover and resync workflow

Use tags to selectively run the failover or resync steps. This becomes your DR runbook — version-controlled and auditable.

YAML 05_dr_failover_resync.yml
--- - name: SnapMirror DR failover and resync hosts: cluster_dr gather_facts: false collections: - netapp.ontap vars: source_path: "svm_prod:vol_oracle_data" destination_path: "svm_dr:vol_oracle_data_dr" tasks: - name: FAILOVER — Quiesce SnapMirror (pause scheduled transfers) na_ontap_snapmirror: state: present relationship_state: quiesced source_path: "{{ source_path }}" destination_path: "{{ destination_path }}" hostname: "{{ ansible_host }}" username: "{{ ansible_user }}" password: "{{ ansible_password }}" https: true validate_certs: false tags: [failover] - name: FAILOVER — Break SnapMirror (destination becomes read-write) na_ontap_snapmirror: state: broken_off source_path: "{{ source_path }}" destination_path: "{{ destination_path }}" hostname: "{{ ansible_host }}" username: "{{ ansible_user }}" password: "{{ ansible_password }}" https: true validate_certs: false tags: [failover] - name: RESYNC — Reverse resync (DR becomes new source) na_ontap_snapmirror: state: present source_path: "{{ destination_path }}" destination_path: "{{ source_path }}" relationship_state: active hostname: "{{ ansible_host }}" username: "{{ ansible_user }}" password: "{{ ansible_password }}" https: true validate_certs: false tags: [resync] # Run only failover: ansible-playbook dr_failover_resync.yml --tags failover # Run only resync: ansible-playbook dr_failover_resync.yml --tags resync
SnapMirror health check playbook Add a daily cron job running a playbook that queries all SnapMirror relationships across your clusters with na_ontap_info, checks the lag time and status, and sends an alert if any relationship is broken or behind. This replaces manual checks across every cluster — a common daily task for storage admins.
Section 08

SAN Automation — LUN, igroup & Mapping

Provisioning SAN storage involves multiple steps: create the LUN, create an igroup, add host initiators, map the LUN. Ansible makes this a single atomic operation.

YAML 06_san_provisioning.yml
--- - name: SAN LUN provisioning — iSCSI hosts: cluster_primary gather_facts: false collections: - netapp.ontap vars: svm_name: svm_san volume_name: vol_lun_sql01 lun_name: /vol/vol_lun_sql01/lun_sql01 lun_size_gb: 200 os_type: windows_2008 igroup_name: igrp_sql_cluster initiators: - iqn.1991-05.com.microsoft:sql-node1 - iqn.1991-05.com.microsoft:sql-node2 tasks: - name: Create volume for LUN na_ontap_volume: state: present name: "{{ volume_name }}" vserver: "{{ svm_name }}" aggregate_name: aggr1_node1 size: 300 size_unit: gb space_guarantee: none hostname: "{{ ansible_host }}" username: "{{ ansible_user }}" password: "{{ ansible_password }}" https: true validate_certs: false - name: Create LUN na_ontap_lun: state: present name: "{{ lun_name }}" vserver: "{{ svm_name }}" flexvol_name: "{{ volume_name }}" size: "{{ lun_size_gb }}" size_unit: gb os_type: "{{ os_type }}" space_reserve: false hostname: "{{ ansible_host }}" username: "{{ ansible_user }}" password: "{{ ansible_password }}" https: true validate_certs: false - name: Create igroup with host initiators na_ontap_igroup: state: present name: "{{ igroup_name }}" vserver: "{{ svm_name }}" initiator_group_type: iscsi os_type: "{{ os_type }}" initiators: "{{ initiators }}" hostname: "{{ ansible_host }}" username: "{{ ansible_user }}" password: "{{ ansible_password }}" https: true validate_certs: false - name: Map LUN to igroup na_ontap_lun_map: state: present initiator_group_name: "{{ igroup_name }}" path: "{{ lun_name }}" vserver: "{{ svm_name }}" hostname: "{{ ansible_host }}" username: "{{ ansible_user }}" password: "{{ ansible_password }}" https: true validate_certs: false

Advanced Patterns

Loops — provision multiple volumes at once

YAML loops_example.yml
vars: volumes: - { name: vol_oracle_data, size: 500, junction: /oracle_data } - { name: vol_oracle_redo, size: 100, junction: /oracle_redo } - { name: vol_oracle_arch, size: 200, junction: /oracle_arch } - { name: vol_oracle_backup, size: 800, junction: /oracle_backup } tasks: - name: Create all Oracle volumes na_ontap_volume: state: present name: "{{ item.name }}" vserver: svm_oracle aggregate_name: aggr1 size: "{{ item.size }}" size_unit: gb junction_path: "{{ item.junction }}" hostname: "{{ ansible_host }}" username: "{{ ansible_user }}" password: "{{ ansible_password }}" https: true validate_certs: false loop: "{{ volumes }}"

AWX / Ansible Tower — GUI + scheduling

For production environments, run playbooks via AWX (open-source) or Red Hat Ansible Tower (enterprise). Benefits: web GUI, RBAC, audit trail, scheduling, webhook triggers from ServiceNow or Jira.

Scheduling

Run daily health checks, weekly snapshot audits, or monthly DR tests automatically on a cron schedule.

RBAC

Dev teams can trigger storage provisioning without access to ONTAP credentials. AWX handles auth.

Webhooks

ServiceNow approves a storage request → webhook triggers AWX → playbook runs → volume created. Full workflow automation.

Audit trail

Every playbook run is logged with who ran it, when, what changed — perfect for compliance and change management.
