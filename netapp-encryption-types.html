DATA-AT-REST ENCRYPTION · ONTAP

NetApp encryption, layer by layer

ONTAP gives you three ways to encrypt data at rest — one hardware-based, two software-based — and they sit at different points in the I/O stack. This walks through how NSE (self-encrypting drives), NVE, and NAE actually work, where they differ, and why "VE" (volume/aggregate encryption) is usually the better default even though SED still has a place.

01 · Where each one sits

Same goal, different layer

Every one of these technologies encrypts data at rest with AES-256. The difference that actually matters is where in the write path the encryption happens — that single fact explains almost every practical trade-off below.

Because NVE/NAE sit above the disk and NSE sits inside it, the two are not mutually exclusive — you can layer software encryption on top of self-encrypting drives for "double encryption," which some compliance regimes explicitly want.

02 · Hardware-based

NSE — NetApp Storage Encryption SED

NSE is NetApp's implementation of full-disk encryption using self-encrypting drives (SEDs) from qualified vendors. The drive encrypts every block as it's written and decrypts on read — entirely in the drive's own controller, invisible to ONTAP's CPU.

  • The data key never leaves the drive; ONTAP only holds an authentication key, fetched from the Onboard Key Manager (OKM) or an external KMIP server, to unlock the drive on boot or after it changes nodes.
  • Encrypts the entire drive — there's no concept of "encrypt this volume but not that one" within a SED; the granularity is the physical disk.
  • SED drives are FIPS 140-2 Level 2 validated — a higher physical-tamper bar than the software modules below.
  • Because the crypto is offloaded to dedicated silicon on the drive, NSE typically outperforms software encryption for raw throughput.
  • Requires purchasing NetApp-qualified SED (or NVMe SED) media — you can't retrofit encryption onto drives you already own.
cluster1::> # confirm drives are self-encrypting
disk encrypt show
cluster1::> # onboard key manager setup, needed by NSE, NVE, and NAE alike
security key-manager onboard enable
03 · Software-based

NVE — NetApp Volume Encryption per volume

NVE encrypts data at the RAID layer in software, using ONTAP's CryptoMod. Because it runs above WAFL's storage-efficiency engine, dedup and compression still happen first — only the resulting blocks get encrypted, so efficiency isn't sacrificed for security.

  • Works on any drive type — SED or not, SSD or HDD, any qualified NetApp platform from ONTAP 9.1 onward. No special media required.
  • Every encrypted FlexVol gets its own unique XTS-AES-256 key. Delete the volume, the key is destroyed with it — which is also what makes secure-purge a true cryptographic shred of a single volume, without touching the rest of the aggregate.
  • Included with the VE license (bundled in ONTAP One) at no extra hardware cost.
  • The one trade-off: NVE volumes sit outside aggregate-level deduplication — dedup still works within the volume, just not across volumes in the aggregate.
  • The CryptoMod is FIPS 140-2 Level 1 validated — software's ceiling, one tier below SED hardware.
cluster1::> # enable NVE on an existing volume
volume encryption conversion start -vserver vs1 -volume vol1
cluster1::> # cryptographically shred a deleted volume's data
volume encryption secure-purge start -vserver vs1 -volume vol1
04 · Software-based

NAE — NetApp Aggregate Encryption per aggregate

NAE (ONTAP 9.6+) is NVE's sibling: same CryptoMod, same RAID-layer placement, same AES-256 — but the encryption key is scoped to the aggregate rather than the individual volume.

  • Every volume in an NAE aggregate shares the aggregate's key set, which means those volumes stay eligible for aggregate-level deduplication — the one thing NVE gives up.
  • When a volume is deleted, its data is gone but the aggregate's keys persist (they're only destroyed if the whole aggregate is destroyed) — the trade for that extra dedup reach is that per-volume secure-purge isn't available on NAE volumes.
  • Since ONTAP 9.7, if a VE license is present and a key manager (OKM or external) is configured, new aggregates default to NAE and new stand-alone volumes default to NVE — encryption becomes opt-out rather than opt-in.
  • NVE and NAE volumes can coexist in the same aggregate; you can convert between them with a volume move.

06 · The actual question

So why is "VE" usually the better call?

"VE" (NVE/NAE) wins on flexibility, reach, and lifecycle control — not on raw cryptographic strength, where SED hardware still edges it out. Here's the case:

1. It runs everywhere SED can't

SED is a property of the physical drive — it doesn't exist in NetApp MetroCluster software builds, ONTAP Select, or on any array populated with non-SED media. NVE/NAE are software, so they're the only at-rest option in those environments, and the same feature set follows you from on-prem to virtualized ONTAP.

2. No forklift upgrade, no drive tax

SEDs cost more than standard drives and must come from NetApp's qualified list. NVE/NAE encrypt whatever's already in the shelf — existing HDDs, SSDs, third-party-qualified media — under a software license (VE, bundled in ONTAP One) instead of a hardware refresh.

3. Granularity matches how data actually gets deleted

A SED's unit of control is the whole drive. NVE's unit of control is a single volume — so decommissioning one tenant's data means destroying one key (secure-purge), instantly and verifiably, without touching anything else sharing that aggregate. That's a much cleaner story for multi-tenant or compliance-driven deletion than physically sanitizing a shared drive.

4. You choose what's encrypted, not "everything or nothing per drive"

With SED, every block on the drive is encrypted, full stop. With NVE you decide volume by volume; with NAE you decide aggregate by aggregate — and NAE still gets you back the aggregate-level dedup that NVE gives up, so the efficiency trade-off is tunable rather than fixed.

Where SED still wins

SED hardware is FIPS 140-2 Level 2 validated versus the CryptoMod's Level 1, and because the crypto runs on dedicated drive silicon instead of the controller's CPU, NSE generally has a lower performance overhead at scale. If your compliance framework specifically requires Level 2 hardware validation, or you're already standardized on SED media, NSE isn't obsolete — and NetApp explicitly supports stacking NVE/NAE on top of SED for double encryption rather than treating it as either/or.

07 · Picking one

A quick decision path

Already on ONTAP 9.7+ with a key manager configured?You likely have NVE/NAE running by default already — check with volume show -fields is-encrypted.
Need aggregate-level dedup across many tenant volumes?Favor NAE aggregates over plain NVE volumes.
Need to guarantee instant, verifiable deletion of one dataset?Use NVE on that volume specifically — secure-purge isn't available on NAE.
Mandated FIPS 140-2 Level 2, or maximum throughput at scale?Add NSE/SED media and optionally layer NVE or NAE on top for double encryption.
Running MetroCluster, ONTAP Select, or non-SED media?NVE/NAE is the only path — SED isn't an option here.
