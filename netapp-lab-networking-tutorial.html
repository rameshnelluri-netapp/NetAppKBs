01

What the "PTR test" during reboot actually is

Boot-time memory diagnostics on physical NetApp controllers

There's no documented "PTR test" in NetApp's boot sequence — the closest real match is the PPR test (Post Package Repair), a BIOS-level memory diagnostic.

What triggers it

  • An uncorrectable ECC memory error causes the node to panic.
  • In an HA pair, the partner node takes over while the affected node reboots.
  • On reboot, the BIOS runs a PPR pass against the flagged DIMM — this can take several minutes and prints results to the console.

What it does

PPR works with DDR4-and-newer memory that supports mapping a bad row on a DIMM to a spare row, instead of requiring a physical replacement. It's a self-healing step, not just a pass/fail check.

Known quirk A DIMM can pass its PPR test cleanly during boot, yet ONTAP still leaves the fault LED lit — that's a display/LED-logic issue, not a sign the repair failed.
02

Single-node cluster setup finished — where's the cluster LIF?

It exists; it's just filed under a different vserver

After cluster setup on a single-node system, the dashboard only surfaces node-mgmt and cluster-mgmt because those are the interfaces an admin actually touches. The cluster LIF is still created — it lives on the Cluster vserver, which isn't shown by default.

Where to look

network interface show -vserver Cluster
network interface show -role cluster

For a single node you'll typically see exactly one cluster LIF — no HA partner means nothing to peer with:

Logical         Status     Network            Current       Current  Is
Vserver Interface    Admin/Oper Address/Mask       Node          Port     Home
------- ----------   ---------- ------------------ ------------- -------- ----
Cluster
        <node>_clus1  up/up      169.254.x.x/16    <node>        e0a      true
Why the address looks strange 169.254.x.x is a link-local range. Cluster LIFs auto-assign from it and are never meant to be manually re-IP'd or routed — they only need to work between local cluster ports.

Other useful checks

net port show -role cluster
net int show -vserver Cluster -fields address,home-port,curr-port
03

The ping to cluster-mgmt kept timing out

Working through the checklist, from ONTAP outward to VMware

A dead ping to a simulator's management IP is almost always one of a short list of causes. Worked top to bottom:

01 — LIF state
network interface show — confirm admin/oper is up/up and the address matches.
02 — Port / domain
network port show, network port broadcast-domain show — right IPspace, right broadcast domain.
03 — NIC type
VMware NIC should be E1000 / E1000E. Vmxnet3 can misbehave with the simulator's stock loader.
04 — vSwitch mode
Bridged, NAT, or Host-only — determines who else on the network can even reach this VM.
05 — Subnet match
Compare the LIF's subnet against the laptop's actual interfaces via ipconfig.
06 — Firewall policy
system services firewall policy show — rule out ICMP being blocked (rare, but cheap to check).

The actual output told the whole story:

VMware Network Adapter VMnet1  → 192.168.38.1 /24
VMware Network Adapter VMnet8  → 192.168.59.1 /24

C:\> ping 192.168.59.1   → replies fine
C:\> ping 192.168.0.100  → times out (this was the cluster-mgmt IP)
Root cause 192.168.0.100 didn't belong to either VMnet the laptop actually has an interface on. This was never an adapter-type or firewall problem — it was a plain subnet mismatch. No route existed between the laptop and that address, so the packets had nowhere to go.

Fix — pick one

Option A (cleaner): re-IP the ONTAP LIFs to match the VMnet subnet.

network interface modify -vserver Cluster1 -lif cluster_mgmt \
  -address 192.168.59.100 -netmask 255.255.255.0

Option B: open VMware's Virtual Network Editor and change VMnet8's subnet to 192.168.0.0/24 instead — riskier, since it can affect other VMs relying on that network.

04

Host-only vs. NAT — the actual difference

Both are private virtual networks. One has a door to the outside; one doesn't.
Both networks connect the host to its VMs equally well. Only NAT opens a translated path outward.
Host-onlyNAT
VM ↔ hostYesYes
VM ↔ other VMs on same virtual netYesYes
VM → internet / physical LAN (outbound)NoYes
Internet / LAN → VM (inbound)NoNo (unless port-forwarded)
Typical useIsolated, cluster-internal trafficVM needs updates/internet, doesn't need to be reachable from outside

For context, Bridged mode is the third option: the VM gets its own address directly on the physical LAN via the real router's DHCP — full two-way reachability, as if it were a separate physical machine. That's the one to use when a machine other than the host laptop needs to reach the VM.

05

Where do 192.168.38.0/24 and 192.168.59.0/24 come from?

VMware Workstation, not the ONTAP OVA

These subnets are picked during VMware Workstation's installation — randomized on purpose, specifically to avoid colliding with whatever network the physical machine might already be on. That's why the exact numbers differ from one laptop to the next.

The ONTAP simulator OVA has no say in the IP ranges. It only defines:

  • The VM's virtual hardware (CPU, RAM, disks, NIC count)
  • Which NIC maps to which virtual switch (e.g. NIC1 → VMnet1, NIC3 → VMnet8)

The actual IP addresses — like 192.168.0.100 — get assigned afterward, either by a lab guide's author (who assumed a subnet without checking) or by whoever runs cluster setup.

Practical habit Before typing in any IP from a lab guide, run ipconfig and check your own VMnet1 / VMnet8 subnets first. Don't assume the guide's numbers match your machine.

07

Windows Server, Active Directory, and joining it to NetApp

No purchase required for a lab — evaluation media covers it

Getting Windows Server for free

Microsoft provides fully-functional 180-day evaluation ISOs — not feature-limited, just time-limited. Search "Windows Server evaluation" on microsoft.com/evalcenter for the current version.

You don't need a real domain

A lab AD domain is entirely made up — it never needs to be registered or resolve on the real internet. Common conventions: lab.local, test.local, netapplab.local. Your AD server runs DNS for that name inside your lab network — that's all the resolution it needs.

Installing AD DS — the short version

  1. Set a static IP on the Windows Server VM, on the same VMnet as the rest of the lab.
  2. Server Manager → Add Roles and Features → Active Directory Domain Services (DNS Server comes along as a dependency).
  3. After install, click the flag notification → Promote this server to a domain controller.
  4. Choose Add a new forest, name it (e.g. lab.local), set the DSRM password, accept the DNS defaults.
  5. Reboot. Manage it afterward via Active Directory Users and Computers (dsa.msc).

Joining the NetApp SVM to that domain

dns create -vserver <svm_name> -domains lab.local -name-servers 192.168.59.150

vserver cifs create -vserver <svm_name> -cifs-server <cifs_name> -domain lab.local

vserver cifs show
Two things that quietly break this DNS on the SVM must point at the AD server, and clocks must stay within about 5 minutes of each other — Kerberos fails hard on clock drift. Sync both to NTP.
08

Does installing software need the internet?

dnf/yum vs. Windows' Add Roles wizard — different answers

LinuxYes, it reaches out

dnf install / apt install pull both package metadata and the package files themselves from repository mirrors defined in /etc/yum.repos.d/ or /etc/apt/sources.list — real servers out on the internet (or an internal mirror in air-gapped shops). No reachable repo, no install.

WindowsNo, it's already on the disc

AD DS and other server roles ship inside the Windows Server installation media itself. "Add Roles and Features" reads from that local image — no internet required, aside from optional Windows Update checks you can skip.

What this means for the lab The Windows Server VM can promote itself to a domain controller on Host-only with zero internet. The Linux VM needs NAT (or Bridged) — at least for the one-time install of nfs-common / cifs-utils.
09

Once everyone's on the same subnet, the internet drops out of the picture

Two separate jobs — only one of them ever needed the internet

Devices on the same subnet send data straight to each other's IP addresses — that's ordinary local networking, nothing to do with the internet. The internet only matters when a device needs to reach something outside its own local network, like a package mirror out on the public internet.

Once nfs-common is installed (that one-time internet use), mounting a share is just two machines on the same private network talking directly:

Linux VM  (192.168.59.50)  ──────────────►  NetApp data LIF  (192.168.59.100)
                              same subnet, no internet involved

The same logic covers everything else in this lab:

  • Windows client mounting an SMB share from NetApp
  • NetApp SVM's DNS lookups against the AD server
  • Kerberos authentication between NetApp and AD
The one-line rule Internet = only needed to reach something outside your private network. Same-subnet communication = only needs matching IP ranges, fully local, no internet ever. This is exactly why real datacenters run fully air-gapped internal networks with zero internet access.
10

Storage in one country, servers in another

The same-subnet trick has a physical limit — this is where real WAN links take over

A single subnet can't span countries — it's built for one local network, at most a campus. Two sites in different countries need routed networking: an actual path connecting the two locations, built and configured by someone. There are two common ways companies build that path.

Two ways to physically bridge distant sites — same endpoints, different roads.

Site-to-site VPN — rides on the public internet

A VPN is encrypted traffic on top of the same public internet everyone else uses — like a locked box sent through the regular mail. The India router encrypts, sends it out over its normal internet connection, it crosses the public internet, and the US router decrypts it on arrival.

MPLS — a separate, dedicated network

A telecom provider (AT&T, Tata Communications, BT, etc.) already owns fiber and routers forming its own private backbone. Your company pays for a dedicated circuit into that backbone at each site. Instead of every router examining the full destination address, MPLS routers read a short label stuck on the packet and forward it along a pre-set path — faster and more predictable, and it doesn't touch public internet routing at all.

In practice the same physical fiber often carries both public internet and multiple companies' private MPLS traffic, separated logically rather than by literally separate cables. What makes it private is that labeling and dedicated bandwidth guarantee, not a wire that's exclusively yours end to end.

11

Full trace — opening \\svm1\share1 from India, share sits in the US

CIFS doesn't care which path it travels — routing decides that, invisibly

The protocol conversation is identical regardless of distance. What differs is only the physical path the packets take to get there — decided entirely by how the network team wired up routing between the two sites.

1 — Name lookup
Laptop resolves svm1 via internal DNS to the SVM's data LIF, e.g. 10.50.20.100.
2 — Route decision
Laptop sees that IP isn't on its local subnet, sends the packet to its default gateway.
3 — Path chosen
India router's routing table sends anything destined for that US range either through the VPN tunnel or the MPLS circuit — whichever the company has configured.
4 — Arrival
US router receives it (decrypting, if VPN) and forwards it onto the local network to the NetApp filer.
5 — SMB negotiation
Client and SVM agree on an SMB dialect.
6 — Authentication
Laptop authenticates against Active Directory — if the only DCs are in the US, this round-trip also crosses the same VPN/MPLS path.
7 — File access
Reads/writes flow over the same established path.
The catch nobody mentions until they hit it Even once it "works," every file open, folder listing, and small read/write is a full round-trip across thousands of miles — SMB is chatty, and 100–250ms+ latency adds up fast. This is exactly why companies place a local AD domain controller replica in each region, and use tools like NetApp FlexCache or SnapMirror to keep frequently-used data close to where people actually work, rather than serving every request across an ocean.
