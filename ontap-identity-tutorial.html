01 · The core confusion

"vserver cifs server create" vs "vserver active-directory create"

Both commands can create a machine account in Active Directory. That's exactly why people mix them up. The difference is what that account is for.

vserver cifs create

creates a data-serving SMB server
  • Stands up an actual CIFS/SMB server on the SVM, used to serve file shares to clients
  • If given -domain, it creates the AD machine account as a byproduct of joining the domain
  • Requires an SMB/CIFS license
  • Visible via vserver cifs show

vserver active-directory create

creates an identity-only AD account
  • Creates an AD machine account for the SVM for authentication / management only — no SMB shares
  • Used so AD users can manage the cluster over SSH/HTTP, or manage iSCSI/FC SVMs
  • No CIFS license required
  • Visible via vserver active-directory show
cluster1::> vserver cifs create -vserver prod -cifs-server PRODCIFS -domain example.com
cluster1::> vserver active-directory create -vserver prod -account-name PROD-AD -domain example.com

Rule of thumb: if the goal is file shares, use cifs create. If the goal is AD-based login to manage the cluster or a block-protocol SVM, and no CIFS server is wanted, use active-directory create.

02 · Guardrail

You can't have both on the same SVM

ONTAP enforces this directly — one SVM gets one AD machine-account relationship, not two.

⚠ Error on collision: "A CIFS server for this Vserver already exists. Having both a CIFS server and an Active Directory account for the same Vserver is not supported." — you'd need vserver cifs delete first before running active-directory create, or vice versa.

03 · Clearing up a common mix-up

LDAP is a protocol, not "the Linux thing"

A frequent assumption is that "LDAP" means a Linux server and "Active Directory" means Windows, as if they're rival products. They're not really comparable that way:

TermWhat it actually is
LDAPA protocol for querying/modifying directory data (users, groups, computers). Not tied to any OS.
Active DirectoryA Microsoft directory service that speaks LDAP as one of several protocols (also Kerberos, DNS, SMB).
OpenLDAPA Linux-based directory service that speaks only LDAP.

So Active Directory is an LDAP server, among other things. "LDAP vs AD" isn't really a fair fight — it's "a protocol vs. a product that (among other things) implements that protocol."

Fig 2 — (A) ONTAP querying AD's built-in LDAP service directly, vs (B) ONTAP querying a wholly separate OpenLDAP directory

A "Linux LDAP server syncing from AD, then serving NetApp" would require a third piece of infrastructure — a sync tool or proxy copying data from AD into OpenLDAP. That's not automatic, not default, and fairly rare in practice. Most environments that want UNIX identity info (UID/GID) just query AD's own LDAP interface directly, using AD's Identity Management for UNIX (RFC2307) schema extensions.

05 · Even more disconnected than LDAP

NIS and Active Directory don't talk natively — at all

NIS (Network Information Service) predates AD entirely — it's an old Sun/Unix mechanism for distributing passwd, group, and hosts maps. Different protocol family, different vendor lineage, no shared schema.

Fig 3 — ONTAP's NIS client only ever sees the NIS server's own maps; there's no built-in path to AD

If a NIS server appears to reflect AD data, someone built custom plumbing for it — e.g. a script that periodically dumps AD accounts and regenerates NIS maps. There's no standard, off-the-shelf sync tool for this the way there loosely is for AD↔LDAP. Most shops that once ran NIS have either migrated to LDAP (often AD's own LDAP interface) or kept NIS as a genuinely separate legacy island.

On ONTAP, vserver services name-service nis-domain create simply points the SVM at whatever NIS server you give it — ONTAP has no visibility into where that server's data originally came from.

07 · Quick decision guide

Which command / protocol do I actually need?

  1. Need to serve SMB/CIFS file shares to Windows clients?

    Use vserver cifs create -domain <fqdn>. This joins AD as part of setup — no separate AD command needed.

  2. Need AD users to manage the cluster (SSH/HTTP) or an iSCSI/FC-only SVM, with no file shares?

    Use vserver active-directory create. Skip CIFS entirely.

  3. Need UNIX-style UID/GID lookups for NFS?

    Configure an LDAP client (vserver services name-service ldap create) pointed at AD's own LDAP interface if AD already has UNIX attributes populated — no separate Linux LDAP server required.

  4. Already running a legacy NIS environment?

    Point ONTAP's NIS client at the existing NIS server. Understand that its data is independent of AD unless someone has explicitly built a sync process.

  5. Trying to combine CIFS and a standalone AD account on the same SVM?

    Not supported — pick one. Use a second SVM if you genuinely need both relationships.
