01

Why "encryption" isn't one thing here

The question "is my NetApp system encrypted?" doesn't have a single yes/no answer — encryption can exist at the drive level, the aggregate level, or the volume level, independently of each other.

All of NetApp's at-rest encryption technologies protect against the same core threat: someone gaining physical or logical possession of storage media without authorization — a stolen drive, a returned lease unit, a misplaced shelf, or repurposed hardware that wasn't properly wiped. What differs is where the encryption happens, what granularity it operates at, and what it costs you in performance, licensing, or storage-efficiency tradeoffs.

Hardware layer

NetApp Storage Encryption (NSE) — encryption built into the physical drive itself, via self-encrypting drives (SEDs).

Software layer

NetApp Volume Encryption (NVE) and NetApp Aggregate Encryption (NAE) — encryption performed by ONTAP itself, independent of the underlying disk.

Key management layer

Onboard Key Manager (OKM) or an external KMIP-based key manager — governs who can actually unlock any of the above.

03

NetApp Storage Encryption (NSE) & SEDs

Hardware-based encryption — every bit written to the drive is encrypted by the drive itself, transparently and continuously.

How it works mechanically

NSE supports self-encrypting drives (SEDs) that encrypt data as it's written. The data cannot be read without an encryption key stored on the disk, and that key is accessible only to an authenticated node. The encryption engine lives inside the drive's own firmware — completely invisible to ONTAP, WAFL, or any application above it.

Authentication key behavior

Data encryption operations, including generating an authentication key, are performed internally, with the authentication key generated the first time the disk is accessed by the storage system. After that, the drive requires storage system authentication for every subsequent data operation.

Two flavors of self-encrypting drive

TypeFIPS statusNotes
FIPS-certified SEDFIPS 140-2 Level 2 validatedSelf-encrypting FIPS-certified SAS or NVMe drives are supported on all FAS and AFF systems. NSE drives carry this Level 2 hardware validation, compared to the Level 1 validation of the software CryptoMod used by NVE/NAE.
Non-FIPS NVMe SEDNot FIPS-certified, still encryptedBeginning with ONTAP 9.6, self-encrypting NVMe drives that haven't undergone FIPS testing are supported on AFF A800, A320, and later systems, offering the same encryption capabilities as FIPS drives but able to be mixed with non-encrypting drives on the same node or HA pair. These use AES 256-bit transparent disk encryption to protect data at rest, even without formal FIPS 140-2/140-3 certification.

If NSE drives are self-encrypting, why does anyone need a key manager for them?

The drive always encrypts mechanically — that part is automatic. What a key manager controls is the authentication key that unlocks the drive's internal encryption key. Out of the box, that authentication key sits at a known default (the manufacturer secure ID, or a null key for NVMe), meaning the drive will decrypt for anyone. Assigning a real key through an onboard or external key manager is what actually turns on the protection — without it, the drive is technically self-encrypting but practically unlocked.

  • NSE protection is per-drive, completely independent of how ONTAP organizes volumes or aggregates above it.
  • No CPU overhead on the controller — the encryption work happens entirely in dedicated drive silicon.
  • Best suited for protecting against physical drive theft or improper disposal — it does nothing for data already exposed once a node is authenticated and reading normally.
  • You can check whether a system actually has SEDs with storage disk show -fields is-sed,is-fips-sed,is-non-fips-sed — if there are none, the encryption-specific show command returns nothing.

    NetApp Volume Encryption (NVE)

    Software-based encryption, applied one volume at a time, with no special drive hardware required.

    What it actually encrypts

    NVE is a software-based technology for encrypting data at rest one volume at a time. An encryption key accessible only to the storage system ensures volume data cannot be read if the underlying device is repurposed, returned, misplaced, or stolen. With NVE, both metadata and data — including snapshots — are encrypted.

    Key model

    Access to the data is given by a unique XTS-AES-256 key, one per volume. Ordinarily, every encrypted volume is assigned a unique key, and when the volume is deleted, the key is deleted with it.

    EACH NVE VOLUME GETS ITS OWN INDEPENDENT KEY — UNENCRYPTED VOLUMES CAN COEXIST IN THE SAME AGGREGATE

    Granularity is the whole point

    With NVE, you can choose which volumes are encrypted and which are not — useful when only some data actually needs encryption, or when you're rolling it out incrementally rather than converting an entire environment at once.

    Storage efficiency tradeoff

    NVE supports the full range of storage efficiency features, including deduplication and compression within a volume — but aggregate-level deduplication is not supported by NVE, since dedup across volumes can't see past each volume's independent encryption.

  • NVE works on any drive type — HDD, SSD, hybrid — no SED hardware required.
  • Customers can use any existing disk with NVE, including NSE drives, for double or layered encryption.
  • NVE and NAE are the only options available for encrypting data in NetApp MetroCluster software and ONTAP Select — environments without dedicated SED hardware support.
  • When an NVE volume is SnapMirrored to another cluster, the destination volume gets its own new, unique key — the source key is never reused at the destination.

    NetApp Aggregate Encryption (NAE)

    NVE's sibling — same software encryption mechanism, but keyed at the aggregate instead of the volume, specifically to preserve cross-volume storage efficiency.

    The problem NAE solves

    With NVE, every volume has its own key, so two volumes with identical data blocks produce completely different ciphertext — deduplication across volumes becomes impossible. NAE fixes this by sharing a single key across an entire aggregate.

    How it's implemented

    NAE allows ONTAP to encrypt data for each volume with keys shared for the aggregate, and enables use of aggregate deduplication for greater storage efficiency. A benefit of NAE is that its volumes are included in aggregate-level deduplication, whereas NVE volumes are excluded.

    ONE AGGREGATE-LEVEL KEY LETS NAE VOLUMES PARTICIPATE IN CROSS-VOLUME DEDUPLICATION — NVE VOLUMES CANNOT

    Key management: the layer that actually matters most

    Every encryption technology above is only as strong as how its keys are generated, stored, and controlled.

    Onboard Key Manager (OKM)

    The Onboard Key Manager is a built-in tool that serves keys to nodes from the same storage system as your data. The OKM provides a self-contained encryption solution for data at rest with NSE, NVE, or NAE. Simpler to set up, but the keys live alongside the data they protect.

    External Key Manager (KMIP)

    The external key management server is a third-party system in your storage environment that serves keys to nodes using the Key Management Interoperability Protocol (KMIP), and it's a best practice to configure it on a different storage system from your data.

    When external key management is the right call

  • Your encryption key management solution must comply with Federal Information Processing Standards (FIPS) 140-2 or the OASIS KMIP standard.
  • You need a multi-cluster solution with centralized management of encryption keys.
  • Your business requires the added security of storing authentication keys on a system or in a location different from the data.
  • You're in a multi-tenant environment — an SVM scope can configure external key management for a specific data SVM in the cluster, which is best for multitenant setups where each tenant uses a different SVM, so only that tenant's SVM administrator has access to their own keys.

    • Does the FIPS validation level of the key management module matter?

    Yes, and it's a real distinction, not just paperwork: NSE drives are FIPS 140-2 Level 2 validated, while the CryptoMod used by NVE and NAE is FIPS 140-2 Level 1 validated — Level 1 being the highest attainable level for a purely software-based module. Organizations with strict compliance requirements sometimes need to factor this distinction in when choosing between hardware and software encryption paths.

    07

    Layering them: double encryption

    Hardware and software encryption aren't competing options — NetApp explicitly supports running both at once.

    ①

    NVE or NAE encrypts first

    Data is encrypted in software by ONTAP, before it ever reaches the RAID layer or physical disk.

    ②

    NSE/SED encrypts again at the drive

    The already-encrypted data is then encrypted a second time by the drive's own hardware as it's physically written.

    ③

    Two independent key domains protect it

    Software keys (OKM/KMIP for NVE/NAE) and hardware authentication keys (for the SED) are managed separately — compromising one doesn't expose the other.

    You can use both software (NAE or NVE) and hardware (NSE or NVMe SED) encryption solutions together to achieve double encryption at rest — NVE can be used together with NetApp Storage Encryption specifically to double-encrypt data on NSE drives. ONTAP does not pregenerate or reuse keys for either layer, and never displays them in plain text.

  • Double encryption is supported, not just theoretically possible — it's a documented, validated configuration.
  • The two layers use cryptographically independent keys, so there's no shared point of failure between them.
  • This combination is typically chosen for the highest compliance bar — defense in depth at both the hardware and software level simultaneously.

    What's actually on by default in modern ONTAP

    This is the detail that resolves the "is everything automatically encrypted?" question precisely.

    The actual default behavior, starting ONTAP 9.7

    Beginning with ONTAP 9.7, NAE and NVE are enabled by default if the volume encryption (VE) license is in place, either the onboard or an external key manager is configured, and NSE is not in use. NAE volumes are created by default on NAE aggregates, and NVE volumes are created by default on non-NAE aggregates.

    Brand new aggregates will have NetApp Aggregate Encryption enabled by default, and brand new volumes not part of an NAE aggregate will have NetApp Volume Encryption enabled by default — but only once an onboard or external key manager is actually configured.

    So is "everything encrypted by default" true?

    ConditionResult
    VE license present + key manager configured + no NSE in useNew aggregates/volumes get NAE/NVE by default — yes, automatically.
    No key manager configured at allNothing encrypts by default — there's no key to encrypt with.
    System uses NSE/SED drivesHardware encryption is mechanically always happening, but data is only protected once a non-default authentication key is assigned via a key manager.
    Existing aggregates/volumes created before 9.7 or before key manager setupNot retroactively encrypted — defaults apply to newly created objects, not historical ones.

    You can also explicitly turn this default off if needed: you can override the default-encryption behavior by entering options -option-name encryption.data_at_rest_encryption.disable_by_default true at the cluster level.

    09

    Interview-ready summary

    Walk me through NetApp's encryption-at-rest options.

    NetApp offers both hardware and software encryption at rest. NetApp Storage Encryption (NSE) is hardware-based, using self-encrypting drives that transparently encrypt every write at the drive's own firmware level. NetApp Volume Encryption (NVE) and NetApp Aggregate Encryption (NAE) are software-based alternatives built into ONTAP itself — NVE assigns a unique key per volume, while NAE shares one key across an entire aggregate so that cross-volume deduplication still works. All three can use either the Onboard Key Manager or an external KMIP-based key manager to control the actual encryption keys, and hardware and software encryption can be layered together for double encryption. Starting in ONTAP 9.7, NAE and NVE are enabled by default for newly created aggregates and volumes, but only once a volume encryption license is present and a key manager is actually configured.

    Quick distinctions to keep straight

    NSE = hardware, per-drive.
    NVE = software, per-volume.
    NAE = software, per-aggregate (enables dedup).
    OKM = keys stored on the same system as the data.
    External KMIP = keys stored elsewhere, for compliance/multi-cluster needs.

    The trap question to watch for

    "Are all NetApp drives self-encrypting by default?" — No. SED-capable hardware varies by platform and what was purchased, and even when present, a SED sits in an unprotected/default-key state until a key manager assigns a real authentication key.
