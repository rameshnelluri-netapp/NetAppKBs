Background

From NFSv3 to pNFS, in one lineage

pNFS isn't a competing protocol — it's a feature bolted onto NFSv4.1. To understand why NetApp built it the way it did, it helps to see what each generation was actually solving.

~1995

NFSv3

Stateless, UDP or TCP, external locking (NLM). Still the throughput workhorse for many workloads today.

1998–2005

NFSv4.0

Stateful, single port, integrated locking and delegations, mandatory strong security.

2006

NFSv4.1 / pNFS

Sessions, trunking, and pNFS — layouts that let clients talk to data servers directly, defined in RFC 5661.

ONTAP 8.1+

NetApp support

Clustered Data ONTAP adds pNFS with a files-based layout across FlexVol and, later, FlexGroup volumes.

Core Concepts

NFSv3 vs. NFSv4 vs. pNFS

These three sit on a spectrum: NFSv3 is simple and stateless, NFSv4 adds state and security in exchange for a single connection to one server, and pNFS keeps NFSv4's model but lets that single connection stop being a bottleneck for data traffic.

Property NFSv3 NFSv4 / 4.0 pNFS (NFSv4.1+)
State model Stateless — no session state on the server Stateful — opens, locks, and delegations are tracked Stateful, plus layout state describing where data lives
Transport / ports UDP or TCP; separate ports for mount, NLM, NSM, portmapper TCP only, single well-known port 2049 Same as NFSv4 for metadata; additional data-server connections opened as needed
Locking Side-band protocol (NLM) — not part of NFS itself Integrated into the protocol; leases replace NLM Same integrated locking as NFSv4.1
Security Typically AUTH_SYS (UID/GID trust); Kerberos optional and clunky Kerberos v5 (RPCSEC_GSS) mandatory to implement; ACLs supported Inherits NFSv4 security model on the metadata path
Data path Single path from client to the server that owns the file Single path — all reads/writes traverse the same server connection Parallel — client writes/reads directly against the node holding the data
Metadata path Mixed with data on the same connection Mixed with data on the same connection Isolated on a dedicated MDS connection (LAYOUTGET, GETATTR, LOOKUP, etc.)
Cluster awareness None — client has no concept of remote nodes None — remote files are proxied internally by the node the client is attached to Full — client is told which node actually owns the data and goes there directly
Ideal for Simple, high-throughput workloads where statelessness and broad compatibility matter Environments needing strong security, ACLs, and protocol-level locking Clustered, multi-node deployments — especially FlexGroup — with parallel or high-fan-out I/O
Key distinction

NFSv4 fixes protocol weaknesses in NFSv3 (locking, security, statefulness). pNFS fixes a topology weakness that NFSv4 inherited: every operation, metadata or data, still funnels through one connection to one node — even in a multi-node cluster where the actual file might live somewhere else entirely.

Under the Hood

pNFS architecture in ONTAP

pNFS has three moving parts: a client that understands layouts, a metadata server that hands them out, and data servers that serve bytes once the client knows where to look.

Metadata Server (MDS)

Established the moment a client mounts with NFSv4.1+ and pNFS is enabled. Handles GETATTR, SETATTR, LOOKUP, ACCESS, REMOVE, RENAME, and the pNFS-specific control calls. This connection persists for the life of the mount.

Data Servers

The cluster nodes that physically hold the volume. They answer read/write requests directly — the client is redirected to a local network interface instead of hairpinning through the cluster's backend network.

Control Path

The internal channel ONTAP uses to keep device IDs and volume-to-interface mappings in sync across the cluster, replicated periodically over the backend cluster network.

How the client knows it's eligible

Support is negotiated in the very first EXCHANGE_ID call of the mount. If both the EXCHGID4_FLAG_USE_PNFS_DS and EXCHGID4_FLAG_USE_PNFS_MDS flags come back set, the interface the client landed on is eligible to act as both a metadata and a data path for that session.

pNFS-specific operations

Beyond ordinary NFSv4.1 calls, a handful of operations exist purely to hand out and manage layouts, defined in RFC 5661 §12.3:

LAYOUTGET LAYOUTCOMMIT LAYOUTRETURN GETDEVICEINFO GETDEVICELIST CB_LAYOUTRECALL CB_RECALL_ANY CB_NOTIFY_DEVICEID
OperationWhat it does
LAYOUTGETClient asks the MDS for the data-server map for a given file.
LAYOUTCOMMITServer commits a layout and updates its metadata maps after a write.
LAYOUTRETURNClient returns a layout, or requests a refreshed one if the data changed.
GETDEVICEINFOClient asks for current connection info for a specific data server.
GETDEVICELISTClient requests the full list of data servers participating in the cluster.
CB_LAYOUTRECALLServer recalls a layout from a client if a conflict is detected.
CB_RECALL_ANYServer asks a client to return any layouts it's holding.
CB_NOTIFY_DEVICEIDServer notifies a client that a device ID has changed.
Worth noting

Only metadata-triggering calls establish device mappings. Running ls in a mount, for instance, is a GETATTR — it will not populate a pNFS device mapping. Mappings appear only once an actual read or write happens.

Sequence

How a pNFS device gets populated

The first time a client touches a file, ONTAP walks through a fixed handshake before any parallel data path exists:

Client opens the file

A read or write is requested; the client performs an OPEN and retrieves the file handle over the metadata connection.

LAYOUTGET is sent

The client sends the file handle to the MDS in a LAYOUTGET call.

MDS returns the layout

The reply includes the state ID, stripe size, file segment, and the device ID that owns this data.

Client resolves the device

The device ID is sent back in a GETDEVICEINFO call to find out which IP address to actually use.

Storage replies with local paths

ONTAP returns the list of IP addresses that provide local access to that device.

Data flows directly

The client continues the conversation over the local interface — bypassing the cluster's internal backend network entirely.

Scale-out

pNFS with FlexGroup volumes

FlexGroup volumes stripe a single namespace across constituent FlexVols on multiple nodes. That's exactly the scenario pNFS was built for: without it, every file access from one client funnels over one mount path to one node, even when the file physically lives elsewhere.

Fig. 1 — Without pNFS: single path, remote hops for 3 of 4 files
Fig. 2 — With pNFS: local, parallel paths to every node

NetApp's own testing on a single RHEL 9.5 client reading four 10GB files in parallel — spread across two cluster nodes — shows the effect directly:

ConfigurationLocal filesRemote / cross-node files
NFSv4.1, no pNFS ~227–228 MB/s, ~46s ~192 MB/s, ~54.5s
NFSv4.1 with pNFS ~246–248 MB/s, ~42.5s ~244 MB/s, ~43s

The headline isn't just that pNFS is faster — it's that the gap between "local" and "remote" files nearly disappears, because every file effectively becomes local from the client's point of view.

Before you start

Prerequisites

Client-side

  • An RFC-compliant NFS client with pNFS support — most Linux distributions from 2014 onward (RHEL 6.4+, Fedora 17+)
  • Mounted with NFSv4.1 or later — pNFS does not exist below 4.1
  • Confirm pNFS support with your client OS vendor before relying on it in production

Server-side (ONTAP)

  • NFSv4.1 enabled on the SVM (off by default)
  • pNFS explicitly enabled on the SVM (disabled by default)
  • At least one data LIF per node, routable to clients — more may be needed for load balancing
  • Export policies and rules that allow NFSv4 on the target volumes

Works with both FlexVol and FlexGroup volumes. With FlexGroup, ONTAP scales to up to 200 billion files and 60PB of capacity. Be cautious combining pNFS with nconnect — each client mount multiplies TCP connections per data LIF, and connection counts can climb quickly.

Hands-on

Configuring pNFS on ONTAP

Enabling pNFS is a two-flag operation on top of a working NFSv4 SVM — but both are required, and both are off by default.

1. Enable NFSv4.1 on the SVM

ONTAP CLI::> vserver nfs modify -vserver SVM -v4.1 enabled

2. Enable pNFS on top of it

ONTAP CLI::> vserver nfs modify -vserver SVM -v4.1-pnfs enabled

3. Confirm export policies allow NFSv4

Make sure the export policy rules covering your target volumes include NFSv4 in their allowed protocols, or clients that mount with vers=4.1 will be rejected before pNFS ever comes into play.

4. Mount from the client

Linux client# request NFSv4.1, which is required for pNFS
mount -o vers=4.1 svm-data-lif:/vol1 /mnt/pnfs_vol
New SVM shortcut

If you're creating the NFS server for the first time, vserver nfs create lets you set -v4.1 enabled up front — but pNFS itself still needs the separate -v4.1-pnfs enabled flag either way.

Operations

Verifying and monitoring pNFS

ONTAP exposes device and mapping state directly in advanced privilege. Note that volumes show up by numeric ID, not name.

advanced privilege::*> pnfs devices show -vserver DEMO

Vserver Name     Mapping ID      Volume MSID     Mapping Status  Generation
---------------  --------------- --------------- --------------- -------------
DEMO             16              2157024470      available       1

::*> pnfs devices mappings show -vserver DEMO

Vserver Name    Mapping ID      Dsid            LIF IP
--------------  --------------- --------------- --------------------
DEMO            16              2488            10.193.67.211

To resolve those numeric IDs back to a volume name: volume show -dsid [dsid_numeric] or volume show -msid [msid_numeric], also in advanced privilege.

Live statistics

advanced privilege::*> statistics start -object nfsv4_1 -vserver SVM -sample-id pnfs_check
::*> statistics show -object nfsv4_1 -vserver SVM -sample-id pnfs_check

Watch counters like getdeviceinfo_error to catch clients that are failing to resolve a data server after a LAYOUTGET.

Operational guidance

Best practices

  • Spread mounts across nodes. Once a mount point is established it stays on that data interface until remounted or the LIF moves — so point different clients at different nodes to balance metadata-server load across the SVM.
  • Treat LIF migrations as disruptive. NFSv4.1 is stateful, so moving a data interface can interrupt clients actively using the mount. Schedule interface migrations and storage failovers/givebacks in a maintenance window.
  • Watch metadata-heavy workloads. Metadata operations are small individually but can be very high in volume for workloads that create large numbers of files — plan MDS placement with that in mind.
  • Get NFSv4 ID domains right. Client and server must agree on the ID domain, or users/groups can show up anonymized (effectively squashed) in the export.
  • Be deliberate with nconnect. It multiplies TCP connections per data LIF on top of what pNFS already opens — size accordingly.
Rollback

What happens if you disable pNFS

Disabling pNFS doesn't tear anything down immediately — it just stops the server from handing out new layouts. Existing layouts already negotiated by clients continue to be used, though some clients may behave unpredictably if they expect pNFS capabilities that are no longer being offered.

ONTAP CLI::> vserver nfs modify -vserver SVM -v4.1-pnfs disabled
Test first

Both enabling and disabling pNFS add a step of complexity to how clients negotiate the mount. Validate the change on a test SVM before rolling it into production — the same way you would test any change to interface topology.
