01

Three trust models, one rule syntax

An ONTAP export policy rule doesn't grant access based on a username. It grants access based on which security type the incoming request actually authenticated with — and it will only trust the security types you explicitly list in -rorule / -rwrule.

sys / AUTH_SYS
TRUST LEVEL — CLIENT-ASSERTED

The client simply states its UID/GID in the request. ONTAP takes its word for it. No cryptographic proof of identity at all.

NTLM
TRUST LEVEL — HASH-VERIFIED, ONE-WAY

A challenge-response using a password hash. Proves the client knows a secret, but doesn't let the client verify the server, and carries no ticket.

Kerberos (krb5)
TRUST LEVEL — MUTUAL, TICKET-BASED

A trusted third party (the KDC) issues a cryptographic ticket addressed to one specific service. Both sides can verify each other.

02

sys (AUTH_SYS)

NFS only · no cryptography · trust-the-client model

This is classic UNIX/NFS security, and it's exactly as weak as it sounds — by design, for a design era when the network itself was assumed trusted.

  • The client's NFS request simply carries a UID and a list of GIDs in plaintext, as asserted by the client's own kernel.
  • ONTAP does not verify that the client is actually who it claims — there's no password, no ticket, no cryptographic check of any kind at the protocol level.
  • Anyone with root on a trusted client (or a spoofed IP that matches your clientmatch) can claim to be any UID they like — which is exactly why -anon 65535 ("squash root entirely") and superuser controls exist as the real safety valve for sys.
  • It's still the correct, recommended choice for NFS when you're not integrating with Kerberos — it's simple, has zero infrastructure dependency, and is fine on a genuinely trusted internal network.
Why it still matters

Even in a fully Kerberized NFSv3 setup, export rules still have to allow sys alongside krb5 — Network Lock Manager (NLM) traffic for file locking doesn't ride over Kerberos, so a pure -rorule krb5 with no sys will break locking on NFSv3 mounts.

03

NTLM

CIFS/SMB only · challenge-response · legacy fallback

NTLM is the mechanism a Windows client falls back to when Kerberos isn't available or wasn't negotiated — never used by NFS at all.

How it actually works

1
Client requests access

The client sends the username to ONTAP's CIFS server — no password yet.

2
Server sends a random challenge

ONTAP generates a random challenge value and sends it back to the client.

3
Client hashes the challenge with its password hash

The client encrypts/hashes the challenge using a hash derived from the user's password, and returns the result — the plaintext password itself is never sent.

4
Server verifies against its own copy

ONTAP (via the domain controller) checks the response against the expected hash. Match → authenticated.

Why it's considered weak today

  • One-way trust only — the client never verifies the server's identity, which opens the door to relay and man-in-the-middle attacks.
  • No ticket, no expiry logic tied to a third party — every request effectively re-proves identity to whichever server is asking, with no centralized, time-bounded ticket the way Kerberos has.
  • Hash-cracking exposure — captured challenge/response pairs are vulnerable to offline attacks against the underlying password hash.
When you still see it

Non-domain-joined Windows machines, workgroup clients, some older applications, or a client that simply can't reach a domain controller to negotiate Kerberos. In an export policy, allowing ntlm is what lets those clients through instead of being denied outright.

04

Kerberos — krb5 / krb5i / krb5p

NFS + CIFS · ticket-based · mutual authentication

This is the exchange shown in the hero diagram above, spelled out fully — it's the same three-step handshake whether the client is an NFS host or a Windows CIFS client.

1
AS exchange — get a TGT

The client authenticates once to the KDC (Authentication Service) using its own principal, and receives a Ticket Granting Ticket. This proves identity to the realm generally — not to any specific service yet.

2
TGS exchange — request a ticket for one specific service

The client presents its TGT to the KDC's Ticket Granting Service and asks for a ticket addressed to a specific SPN — for example nfs/datalif1.example.com@EXAMPLE.COM. The KDC encrypts a service ticket using the secret key on file for that SPN.

3
AP exchange — present the ticket directly to the service

The client sends this service ticket straight to ONTAP. ONTAP decrypts it with its own copy of the same secret key. Successful decryption is proof the KDC vouched for exactly this client, addressed to exactly this service.

Three strength levels

  • krb5 — authentication only. Proves identity; the actual NFS traffic afterward is not protected.
  • krb5i — adds per-packet integrity checksums, so tampering with data in transit is detectable.
  • krb5p — adds full privacy: NFS traffic is encrypted, not just checksummed.
05

SPN — the addressing layer Kerberos runs on

Service Principal Name · required for step ② above

Every other authentication type in this guide works fine without an SPN. Kerberos cannot function without one — it's the label that step ② uses to ask the KDC for a ticket to the right place.

Format

service/hostname@REALM — e.g. nfs/datalif1.example.com@EXAMPLE.COM

Where it's used — two different mechanisms in ONTAP

CIFS / SMB — automatic

When ONTAP's CIFS server joins Active Directory, AD auto-registers HOST/ SPNs on the SVM's computer object. Verify with setspn -l svm1 from a Windows box.

NFS — manual, per LIF

You define it explicitly:
vserver nfs kerberos interface enable -lif datalif1 -spn nfs/datalif1.example.com@EXAMPLE.COM

The one rule that breaks everything if missed

The hostname the client actually connects with must exactly match a registered SPN. Mount via a DNS alias that isn't in the SPN, and the KDC simply can't issue a ticket for it — Kerberos fails, and the client either falls back to sys/NTLM (if the export rule allows it) or is denied outright.

06

Full end-to-end trace: an NFS krb5 mount

Putting every piece together — from a user typing mount to ONTAP deciding read/write access.

1
Admin configures the SPN on the LIF
vserver nfs kerberos interface enable -vserver vs1 -lif datalif1 -spn nfs/datalif1.example.com@EXAMPLE.COM
2
Admin sets the export policy rule
vserver export-policy rule create -policyname nfskrb -rorule sys,krb5 -rwrule krb5 -superuser krb5

Note sys included in -rorule too — this is the NLM-locking allowance mentioned in Section 02.

3
Client requests a TGT (AS exchange)

The client's machine or user principal authenticates to the KDC and receives a TGT — no NetApp component involved yet.

4
Client requests a service ticket for the SPN (TGS exchange)

Client asks the KDC for a ticket to nfs/datalif1.example.com@EXAMPLE.COM — matching exactly what was registered in step 1.

5
Client presents the ticket to ONTAP (AP exchange)

ONTAP decrypts it using its stored key for that SPN. Decryption succeeds → the request's effective security type becomes krb5.

6
ONTAP maps the SPN to a UNIX identity

The client principal is mapped to a UNIX user via a krb-unix name-mapping rule (by default, the first portion of the SPN) — this determines the effective UID/GID for permission checks.

7
Export policy rule is evaluated

ONTAP checks the effective security type (krb5) against the rule's -rorule/-rwrule/-superuser lists for the matching -clientmatch entry, and grants or denies accordingly.

8
Access granted, mount proceeds

Ordinary file reads/writes continue under the mapped UNIX identity. If NFSv3 locking is needed, that traffic authenticates separately as sys — which is why it had to be allowed in step 2.

08

Common failure points

!
Hostname / SPN mismatch

Client connects via a name not covered by any registered SPN → Kerberos negotiation fails silently, falls back to a weaker method or is denied.

!
15-character AD account truncation

AD machine account names cap at 15 characters. Two Kerberized NFS LIFs whose SPNs only differ after character 15 collide on the same account.

!
Missing sys allowance for NFSv3 locking

An export rule with only krb5 and no sys breaks NLM lock requests on NFSv3, even though file access itself authenticates fine.

!
Clock skew

Kerberos tickets are time-bounded. More than roughly 5 minutes of drift between ONTAP, the KDC, and the client causes authentication failures — NTP is not optional in a Kerberized environment.

!
No UNIX name-mapping for the SPN

If the incoming SPN can't map to a valid UNIX user (no matching name-mapping rule and no matching local user), the Kerberos access attempt fails even though the ticket itself was valid.

09

Glossary

KDC
Key Distribution Center — the trusted third party (AD or MIT Kerberos) that issues tickets.
TGT
Ticket Granting Ticket — proves identity to the realm generally, obtained once per session.
Service ticket
A ticket addressed to one specific SPN, used to authenticate to that exact service.
SPN
Service Principal Name — the unique address (service/host@REALM) a service is known by in Kerberos.
Effective security type
The authentication method ONTAP determines a request actually used, which export policy rules are evaluated against.
Keytab
A file holding a service's secret key(s), used instead of interactive KDC login for non-Microsoft KDCs.
krb-unix name mapping
The rule ONTAP uses to translate an authenticated Kerberos principal/SPN into a UNIX UID/GID.
