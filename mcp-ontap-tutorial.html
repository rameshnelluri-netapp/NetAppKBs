01

Client vs. Server — who's who

MCP borrows the classic client/server split. One side reasons in language, the other side just executes.

MCP Client

Claude (the agent)

The reasoning layer. Reads your request, decides which tool answers it, and fills in the parameters.

  • Runs tool_search to discover what's available
  • Chooses ontap_get vs. create_volume, etc.
  • No direct access to your cluster — only through tools
MCP Server

ontap-mcp-server (Docker)

A plain backend service. No model, no language understanding — just a catalog of functions.

  • Holds credentials for registered clusters
  • Translates each tool call into a REST HTTP request
  • Returns raw JSON back to the client
Naming gotcha: the label ontap-mcp that shows up in front of every tool (ontap-mcp:list_registered_clusters) is just a key in the client's config file — not something read from the Docker container. It could be named anything; it happened to be chosen independently of the container name ontap-mcp-server. 
{
  "mcpServers": {
    "ontap-mcp": {              // ← arbitrary label, chosen in config
      "command": "docker",
      "args": ["exec", "-i", "ontap-mcp-server", "..."]
    }
  }
}
02

What actually happened, step by step

Four requests, each resolved to a different tool call against the same MCP server.

1
"List the ONTAP systems available"
Claude called list_registered_clusters — a purpose-built tool with no parameters, since it just reads the server's own config of registered pollers. Returned: Cluster1 (9.11).
2
"Check the simulator is reachable, give version + details"
Claude called the generic ontap_get tool with path: /cluster. This is a live REST GET against the cluster, so a successful response also proves reachability.
3
"Give me the vservers list"
Same generic tool, different path: ontap_get(path: "/svm/svms"). One flexible tool, many endpoints.
4
"Is this using the NetApp REST API?"
Yes — ontap_get strips the /api prefix and hits ONTAP's native REST endpoints directly, e.g. https://<cluster-mgmt-ip>/api/svm/svms.
03

Two shapes of tool: read vs. write

Reads get one flexible tool. Writes get many narrow ones. That's a deliberate safety trade-off, not an inconsistency.

OperationToolUnderlying REST call
Discover clusterslist_registered_clusterslocal server config, not a REST call
Any readontap_getGET /api/<any path>
Create a volumecreate_volumePOST /storage/volumes
Create an SVMcreate_svmPOST /svm/svms
Create a snapshotcreate_snapshotPOST /storage/volumes/{uuid}/snapshots
Resize / rename a volumeupdate_volumePATCH /storage/volumes/{uuid}
Delete a volumedelete_volumeDELETE /storage/volumes/{uuid}
Why the split exists: reads are low-risk, so one generic tool covering any REST path is fine. Writes are high-risk, so each gets an explicit, validated parameter set (size, protocol, aggregate…) instead of an arbitrary JSON body — harder to misuse by accident.
04

Extending it: plugging in Ansible health checks

MCP tools aren't limited to REST calls — a tool is just "some code the server runs." That means an existing Ansible playbook could become a tool too.

To make "run a health check" a real request Claude can act on, the MCP server itself needs a new tool added by whoever maintains it — this isn't something the client side (Claude) can create on the fly.

What that tool would need to do

1Define a new tool, e.g. run_ansible_health_check(cluster_name)
2Implementation shells out to the playbook: ansible-playbook health_check.yml -e cluster=<name>
3Capture stdout / JSON callback output from Ansible
4Return it as the tool's structured result
5Redeploy the MCP server so the tool is registered

Once live, it behaves exactly like every other tool in this conversation: it shows up in tool_search, and a request like "run a health check on Cluster1" resolves to a single call — run_ansible_health_check(cluster_name: "Cluster1") — same pattern as everything above.
