ONTAP · System Manager · Identity

Getting under the hood of System Manager: web services, access failures, and SAML

A working reference for how ONTAP exposes System Manager over HTTPS, which cluster services keep it running, what breaks when SAML is misconfigured, and how to wire up Okta as an identity provider — including the gotchas specific to sandboxed lab environments.

01

Architecture overview

System Manager isn't one service — it's a GUI shell sitting on top of several independent cluster services, all scoped to the admin Vserver.

Every ONTAP cluster runs a set of lightweight web services under vserver services web / system services web. These are visible per-Vserver, and each has an Enabled flag you can toggle independently. System Manager is a consumer of several of these at once — it's a browser application that calls into the REST and legacy ONTAPI layers, wrapped in a portal/session framework, optionally gated by SAML.

BrowserHTTPS request to cluster-mgmt LIF
→
Web server layerportal · security · rest · ontapi
→
sysmgrrenders the System Manager UI
→
Optional: SAMLsaml / saml-sp redirect to IdP
Key idea Disabling any one of the underlying services doesn't necessarily take the whole GUI down — but it degrades specific functionality. Losing rest breaks the modern UI panels; losing security breaks HTTPS/session handling entirely; losing saml-sp mid-configuration can lock you out if SAML is already enforced.

03

The web server layer, one level down

Above the services sits the actual HTTPS listener — this is where firewall policy, LIF assignment, and certificates come into play.

What's actually listening

System Manager is served over HTTPS (443) on the cluster management LIF by default. The web server binds to whichever LIF has the management firewall policy applied and a valid role of cluster-mgmt or node-mgmt. Two things commonly get confused here:

  • Service enablement (vserver services web modify) — turns a given service on/off logically.
  • Firewall/LIF policy (system services firewall policy show) — controls whether traffic on port 443 is even allowed to reach that LIF from a given network.

A service can be Enabled: true and still be unreachable if the firewall policy on the LIF blocks HTTPS, or if DNS/routing can't get a client to the LIF at all.

Certificates

The web server layer also owns the TLS certificate presented during the handshake. An expired or mismatched cluster certificate is one of the most common "System Manager won't load" causes that has nothing to do with SAML or the services above — always rule this out first:

cluster1::*> security certificate show -type server
Common trap If you rotate or renew the cluster certificate while SAML is enabled, some IdPs will also need their stored SP certificate metadata refreshed — otherwise the SAML handshake starts failing even though the plain HTTPS listener works fine.
04

How SAML actually fits into this stack

SAML doesn't replace the web server layer — it intercepts the authentication step that happens after the browser reaches it.

Without SAML, a request to System Manager hits portal/security, which prompts for local or Active Directory/LDAP credentials directly. With SAML enabled, that same request gets redirected out to an external Identity Provider (IdP) — Okta, Entra ID, ADFS, PingFederate, Shibboleth, and so on — and only after the IdP successfully authenticates the user does control return to ONTAP with a signed assertion.

1 · RequestBrowser → cluster-mgmt LIF /sysmgr
→
2 · RedirectONTAP SP sends browser to IdP
→
3 · AuthUser authenticates at IdP (Okta)
→
4 · AssertionIdP posts signed SAML assertion back to ACS URL
→
5 · SessionONTAP validates, grants System Manager session

Two ONTAP services carry this whole exchange: saml enables SP capability cluster-wide, and saml-sp is the live endpoint that receives and validates the assertion at the callback URL (the "ACS URL" in IdP terminology). SAML in ONTAP applies specifically to the http and ontapi applications — the ones System Manager and the Service Processor Infrastructure use.

Scope SAML authentication in ONTAP applies only to the admin Vserver. It governs access to System Manager and related web APIs — it has no bearing on SSH/CLI login, which continues to use local accounts or AD/LDAP domain authentication regardless of SAML state.
05

Step-by-step: Okta as the IdP

End-to-end, from Okta org creation to a working SSO login on System Manager.

  1. Confirm outbound reachability from the cluster

    SAML metadata is fetched by ONTAP itself, not just your browser — the cluster needs its own path to the IdP.

    cluster1::*> network ping -lif cluster_mgmt -destination okta.com -vserver cluster1
okta.com is alive

  2. Sign up for an Okta org

    Use the Okta Integrator Free Plan (developer track) rather than the 30-day Workforce Identity trial if you want something that doesn't expire mid-lab. Business-domain email required — a corporate address works, personal providers (Gmail, Outlook, Yahoo) are usually blocked by the signup form.

  3. Get the cluster management LIF address

    You'll need this for both the Okta app config and the ONTAP-side command.

    cluster1::*> network interface show -lif cluster_mgmt

  4. Create a SAML 2.0 app integration in Okta

    Applications → Create App Integration → SAML 2.0. Set:

    • Single sign-on URL (ACS): https://<cluster_mgmt_ip>/security/saml/sp/callback
    • Audience URI (SP Entity ID): matches the value you'll use for -sp-host
    • Name ID format: EmailAddress

  5. Copy the metadata URL

    From the app's Sign On tab. Must not include a Token groups Unqualified name segment in the path — a malformed URL here is one of the most common Okta+ONTAP failure points.

    # correct
https://your_domain.okta.com/app/abc1a23a1234567abcd/sso/saml/metadata

  6. Register ONTAP as the SAML service provider

    cluster1::*> security saml-sp create -idp-uri https://your_domain.okta.com/app/<app_id>/sso/saml/metadata -sp-host <cluster_mgmt_ip>
Warning: This restarts the web server. Active HTTP/S sessions will be disrupted.

    Verify it landed correctly:

    cluster1::*> security saml-sp show

  7. Create a SAML-authenticated ONTAP user

    Must match a user assigned to the app in Okta's Assignments tab.

    cluster1::*> security login create -user-or-group-name you@domain.com -application http -authentication-method saml -role admin
cluster1::*> security login create -user-or-group-name you@domain.com -application ontapi -authentication-method saml -role admin

  8. Test the login

    Browse to https://<cluster_mgmt_ip>/sysmgr — you should be bounced to Okta, authenticate there, and land back in System Manager already signed in.

06

Accessibility issues & lockout recovery

What actually happens when SAML is misconfigured, and how to get back in.

Important Once SAML is enabled and enforced for the http/ontapi applications, it becomes the only way to log into System Manager. If the IdP metadata is wrong, expired, or unreachable, you cannot fall back to a local admin login from the normal GUI URL — the redirect loop or handshake failure blocks everyone, including local admins.

The only supported way out

SAML cannot be disabled from a standard SSH session to the cluster. Recovery requires out-of-band access to the Service Processor (SP) or Remote LAN Module (RLM) console of a node:

SP> system console
cluster1::*> security saml-sp delete

This reverts authentication to local/AD accounts immediately, letting you back into System Manager to fix and re-test the IdP configuration.

Common root causes

SymptomLikely cause
Redirect loop between ONTAP and IdPACS URL / Entity ID mismatch between Okta app config and -sp-host
"Metadata could not be retrieved"Cluster has no outbound path to the IdP, or DNS can't resolve it
Assertion accepted, but access deniedNo matching security login create entry with -authentication-method saml for that user
Worked, then broke after a cert renewalSP certificate metadata went stale on the IdP side after ONTAP's cluster cert rotated
AD group-based SAML roles not applyingDomain groups with SAML require ONTAP 9.14.1+ and must be added with -authentication-method domain

Before you enable SAML in any environment

  • Confirm you actually have SP/RLM console access — not just SSH — before flipping SAML on.
  • Keep security saml-sp delete written down somewhere outside the cluster.
  • Test with a non-critical admin account first, and keep at least one local account with a known-good password as a bridge.
07

Lab on Demand specific notes

What's different when you're testing this inside NetApp's sandboxed lab platform.

LOD clusters usually sit behind a split-tunnel VPN — your laptop gets full internet access, but the simulated ONTAP cluster inside the lab network historically does not. That matters here specifically because security saml-sp create requires the cluster itself, not just your browser, to fetch the IdP metadata over HTTPS.

Check reachability before building anything

cluster1::*> network ping -lif cluster_mgmt -destination 8.8.8.8 -vserver cluster1
cluster1::*> network ping -lif cluster_mgmt -destination okta.com -vserver cluster1

Both need to succeed — the first confirms routing, the second confirms DNS resolution. If either fails, check dns show on the cluster and configure name servers if missing.

If outbound access is blocked Some LOD labs include a pre-deployed Windows AD/ADFS server on the internal lab network — that lets you practice the exact same security saml-sp create mechanics against an internal IdP with no internet dependency at all.

SP console access in LOD

Many LOD "vsim" clusters simulate nodes without exposing a genuine Service Processor console. Before you enable SAML in a lab, check whether your specific lab guide documents SP/RLM access — if it doesn't, treat this as a one-way door for the duration of the lab and be prepared to reset the lab environment entirely if you get locked out, rather than expecting to recover in-session.
