Wiring up ONTAP's Event Management System: SNMP, email, filters, and destinations

How ONTAP turns internal system events into SNMP traps and email alerts — the EMS pipeline end to end, with working commands for SNMPv1/v2c/v3, SMTP relay configuration, custom event filters, and routing it all to real destinations.

event filter create event notification destination create system snmp traphost security login -application snmp
01

EMS: the pipeline behind every alert

Three independent pieces have to be built, in order, before any alert reaches you.

Every warning, error, or state change inside ONTAP — a disk failure, a failed takeover, a full aggregate — is generated internally as an EMS event (Event Management System). By itself, an EMS event just lands in the internal event log. To actually get notified, three separate objects need to exist and be linked together:

1 · FilterWhich events matter to you
→
2 · DestinationWhere they should go (email / SNMP / syslog / REST)
→
3 · NotificationThe link that binds a filter to one or more destinations

This is the modern event filter / event notification destination / event notification command set. Older ONTAP guides reference event destination and event route — those are deprecated but may still show up if you inherit an older cluster's config.

Out of the box A fresh cluster has exactly one destination pre-defined — snmp-traphost — and it's already bound to the built-in default-trap-events filter (all ALERT/EMERGENCY events, plus all Standard/Built-in SNMP trap type events). No email destination exists until you create one.
02

SNMP concepts in ONTAP

Traps vs. polling, and the version differences that decide how much setup you need.

SNMP in ONTAP works in two directions:

  • Polling — an external monitoring tool queries the cluster's SNMP agent for values (disk status, interface counters, etc.) using GET/GETNEXT/WALK against ONTAP's MIB.
  • Traps — ONTAP proactively pushes an alert to a configured traphost the moment a matching event occurs, rather than waiting to be asked. This is what EMS event notifications ride on.
VersionAuth modelUse case today
SNMPv1Plaintext community stringLegacy only — avoid on anything reachable outside a trusted segment
SNMPv2cPlaintext community stringStill common for read-only polling on isolated management networks
SNMPv3Per-user auth (MD5/SHA) + optional privacy encryption (DES/AES)Recommended — the only version with real authentication and encryption
Security note SNMPv1/v2c community strings travel in clear text and offer no per-user accountability. If your monitoring tooling supports it, SNMPv3 with authPriv (auth + privacy) is the only version worth using outside a fully isolated management VLAN.
03

SNMP setup

Enable the protocol, then configure the version you actually need.

1. Confirm SNMP is enabled

cluster1::> system snmp show

2. Set contact and location (optional but good practice)

cluster1::> system snmp contact -contact "Storage Team <storage@company.com>"
cluster1::> system snmp location -location "DC2 - Row 4 - Rack 12"

3a. SNMPv1/v2c — community string (simple, less secure)

cluster1::> system snmp community add -type ro -community-name my_ro_string

Only read-only communities are supported in ONTAP — there's no write community.

What a community string actually is It is not a user account, and it has no relationship to Active Directory, LDAP, or ONTAP's own local/SSH accounts. Think of it as a shared password that also doubles as an access label. It lives in exactly two places — the ONTAP cluster and whatever monitoring tool (NMS) is polling it — and both sides just need to type the same string. ONTAP never asks "who are you" for v1/v2c; it only checks "did the request include the right string." There is no identity, no per-caller accountability, and nothing is encrypted on the wire: 
snmpwalk -v2c -c my_ro_string 10.30.40.10 .1.3.6.1.4.1.789...
If my_ro_string matches what's configured on the cluster, the poll succeeds — that's the entire v1/v2c security model.

3b. SNMPv3 — USM user (recommended)

cluster1::*> security login create -username snmpv3user -application snmp -authmethod usm
Enter the authoritative entity's EngineID [local EngineID]: <enter>
Which authentication protocol do you want to choose (none, md5, sha) [none]: sha
Enter the authentication protocol password (min 8 characters): ********
Which privacy protocol do you want to choose (none, des, aes128) [none]: aes128
Enter privacy protocol password (min 8 characters): ********
This still isn't an AD user SNMPv3 replaces the shared-string model with USM — the User-based Security Model, which is why the command uses -username. But this is a locally-defined, SNMP-only identity that exists purely inside ONTAP's SNMP subsystem — it has no relationship to Active Directory/LDAP, and no relationship to security login create -application ssh accounts used for CLI/System Manager login. A USM user can't log into the cluster anywhere else; it exists for exactly one purpose — authenticating SNMP polling and trap traffic under its own credentials instead of a string everyone shares.

4. Register a traphost

The traphost is where SNMP traps actually get sent — this is separate from creating the user or community itself. DNS must resolve the traphost name if you use a hostname.

# SNMPv1/v2c-style trap delivery (uses configured community strings)
cluster1::> system snmp traphost add -peer-address 10.30.40.10

# SNMPv3 trap delivery (authenticated + optionally encrypted)
cluster1::> system snmp traphost add -peer-address 10.30.40.10 -usm-username snmpv3user
cluster1::> system snmp traphost show
10.30.40.10 (10.30.40.10)
USM User: snmpv3user
How this connects to EMS Once a traphost exists, ONTAP auto-creates the snmp-traphost event notification destination pointing at it — you'll see it reflected in event notification destination show with a note like (from "system snmp traphost"). You don't create that destination manually; it inherits from this SNMP config.
04

SMTP / email setup

EMS email alerts need a mail relay configured before any email destination will actually deliver.

Unlike SNMP, there's no "email agent" to enable — you just need to tell ONTAP which SMTP relay/MTA to hand outbound mail to. This is a cluster-wide setting, separate from any individual destination.

cluster1::> event config modify -mail-server smtp.company.com -mail-from ontap-alerts@company.com
ParameterMeaning
-mail-serverFQDN or IP of your SMTP relay (must accept mail from the cluster's management network — usually an internal relay, not a public MTA requiring auth)
-mail-fromThe sender address shown on outbound EMS alert emails
Common trap ONTAP's built-in mailer does not support SMTP AUTH or TLS submission on older versions — it expects an open internal relay that trusts the cluster's management IP. If your organization only has an authenticated external SMTP provider (like a hosted 365/Gmail relay), you'll typically need an internal relay/smarthost in between that ONTAP can hand mail to unauthenticated, which then forwards it out.

Verify DNS resolves the mail server

Just like the SNMP traphost, if you configure -mail-server by hostname, cluster DNS must be able to resolve it — check with dns show if mail never arrives.

05

Event notification destinations

A destination is just an address — email, syslog, SNMP, or REST — that a notification can point events at.

Create an email destination

cluster1::> event notification destination create -name StorageAdminEmail -email storageadmin@company.com

Create a syslog destination

cluster1::> event notification destination create -name syslog_dest -syslog 10.23.12.1

Create a REST webhook destination (9.9+)

cluster1::> event notification destination create -name webhook_dest -rest-api-url https://alerts.company.com/ontap-events

If the URL is HTTPS, ONTAP validates the destination's certificate — and can optionally check revocation status via OCSP (security config ocsp show -application ems).

See what exists today

cluster1::> event notification destination show
Name              Type      Destination
----------------  --------  ---------------------------
StorageAdminEmail email     storageadmin@company.com
syslog_dest       syslog    10.23.12.1
snmp-traphost     snmp      10.30.40.10 (from "system snmp traphost")
3 entries were displayed.
Naming rule Destination names must be 2–64 characters, using A–Z, a–z, 0–9, underscore, and hyphen only — and must start and end with an alphanumeric character.
06

Event filters

Filters decide which events actually qualify for notification — without one, nothing gets sent, no matter how the destination is configured.

Built-in filters (read-only, cannot be modified or deleted)

FilterMatches
default-trap-eventsAll ALERT/EMERGENCY events, plus all Standard/Built-in SNMP trap type events
important-eventsAll ALERT/EMERGENCY events, plus callhome.* ERROR events
no-info-debug-eventsEverything except INFO and DEBUG severity (EMERGENCY, ALERT, ERROR, NOTICE)

Build a custom filter

Filters are evaluated as an ordered rule list — first match wins, and there's an implicit final rule that excludes everything not explicitly included.

cluster1::> event filter create -filter-name CRITICAL_ALERTS
cluster1::> event filter rule add -filter-name CRITICAL_ALERTS -type include -message-name callhome.* -severity ALERT,ERROR
cluster1::> event filter rule add -filter-name CRITICAL_ALERTS -type include -message-name raid.aggr.*
cluster1::> event filter rule add -filter-name CRITICAL_ALERTS -type exclude -message-name callhome.bad.ram
cluster1::> event filter rule add -filter-name CRITICAL_ALERTS -type exclude -message-name *
cluster1::> event filter show -filter-name CRITICAL_ALERTS
Filter Name     Rule  Rule     Message Name       SNMP Trap Type  Severity      Position Type
--------------  ----  -------  -----------------  --------------  ------------
CRITICAL_ALERTS 1     include  callhome.*         *               ALERT, ERROR
                2     include  raid.aggr.*        *               *
                3     exclude  callhome.bad.ram   *               *
                4     exclude  *                  *               *
4 entries were displayed.
Rule fields Each rule matches on message nameseveritySNMP trap type combined with a logical AND. Within a single field, multiple values are OR'd — e.g. -severity ALERT,ERROR matches either. Rules are checked top to bottom; the first match (include or exclude) decides the event's fate for that filter.
Order matters include and exclude rules are evaluated in the order you add them — a broad include early in the list can shadow a more specific exclude added after it. Put narrow exceptions before the broad rule they're meant to carve out of, unless you're deliberately relying on last-match-wins ordering.

You can define up to 50 event filters per cluster.

07

Wiring it together: the notification link

The final step — bind a filter to one or more destinations. Nothing is delivered until this exists.

cluster1::> event notification create -filter-name CRITICAL_ALERTS -destinations StorageAdminEmail,syslog_dest,snmp-traphost
cluster1::> event notification show
ID   Filter Name           Destinations
---- --------------------- -----------------------------
1    default-trap-events   snmp-traphost
2    CRITICAL_ALERTS        StorageAdminEmail,syslog_dest,snmp-traphost
2 entries were displayed.

You can point the same filter at multiple destinations in one notification, or create several notifications from different filters that share a destination — e.g. send everything ALERT+ to email, but only callhome.* events to SNMP.

Mental model recap Filter = the "what." Destination = the "where." Notification = the object that actually says "send this filter's matches to that destination." All three must exist for an alert to reach you — a perfectly good filter pointed at no destination, or a destination with no notification referencing it, both silently do nothing.

Troubleshooting

Where alerts most often go missing, in the order to check them.

SymptomCheck
No emails at allevent config show — is -mail-server actually set? Cluster DNS resolving it?
No SNMP traps receivedsystem snmp traphost show — traphost registered? system snmp show — SNMP/traps enabled cluster-wide?
Some events missing, others fineevent filter show -filter-name <name> — check rule order; an early broad exclude may be shadowing later includes
Destination exists but nothing arrivesevent notification show — is that destination actually referenced by a notification?
SNMPv3 traps rejected by receiverConfirm auth/privacy protocol and passwords on the USM user match exactly what the trap receiver expects (security login show -application snmp)
REST webhook destination fails silentlyCertificate validation — check security config ocsp show -application ems and confirm the destination's TLS cert chain is trusted by the cluster

Generate a test event

Useful for confirming the whole pipeline works end to end without waiting for a real failure:

cluster1::*> set diag
cluster1::*> event generate -message-name callhome.test
