FC PATH GUIDE
Concepts Create LUN Find WWPNs Switch Databases Zoning Host Setup Troubleshoot Cheatsheet
End-to-end SAN walkthrough

A LUN is only as good as the path that reaches it.

This is the full chain a Fibre Channel I/O actually travels: from a NetApp LUN, through a host bus adapter, across a switched fabric, into a zone, and back. Break any one link — a missing WWPN, an inactive zoneset, an unmapped igroup — and the disk simply never appears. We'll trace every link in order.

Simplified single-initiator, single-target FC path — a real fabric mirrors this twice for redundant multipathing.
01

The addressing model

Before touching a CLI, it's worth being precise about what identifies what — this vocabulary is what every later command is built on.

TermWhat it identifiesScope
WWNN — World Wide Node NameThe physical device as a whole (a controller, an HBA card)One per node
WWPN — World Wide Port NameA single physical port on that deviceOne per port — this is what gets zoned
FCIDA temporary 24-bit address the switch assigns a port after login, similar in spirit to how DHCP hands out an IPReassigned on every fabric login
Igroup (NetApp-side)A named group of host initiator WWPNs allowed to see specific LUNsPer SVM

A zone is created from WWPNs, never from IP-style addresses. Two ports must be in the same active zone before they can even attempt SCSI communication — zoning happens at the fabric layer, independently of whether the NetApp side has mapped anything yet.

The three logins that happen before any data moves

  1. FLOGI (Fabric Login) — a port logs into the switch itself and receives an FCID. This is what populates the switch's flogi database.
  2. PLOGI (Port Login) — one N-port logs into another N-port directly, establishing a session. Only possible if both ports are in the same active zone.
  3. PRLI (Process Login) — negotiates the actual upper-layer protocol (SCSI-FCP) parameters between initiator and target.
Why this order matters

If FLOGI never happens, the switch has no record of the port and zoning is irrelevant. If FLOGI succeeds but zoning is missing or inactive, PLOGI is refused — the host sees the switch but never sees the array. This is the single most common point of failure in new LUN presentations.

02

Creating the FC LUN on NetApp

Everything here happens before you ever touch the switch — the array side must exist first so you know which target WWPNs you're about to zone.

Confirm FCP is licensed and running on the SVM

cluster1 :: netapp cli
advanced not required
::> vserver fcp show -vserver svm_prod
::> vserver fcp create -vserver svm_prod -status-admin up   # if not yet enabled

Identify the SVM's target WWPNs

You need these before building the zone later.

cluster1
::> network interface show -vserver svm_prod -data-protocol fcp -fields wwpn,home-node,home-port

vserver    lif       wwpn                    home-node   home-port
svm_prod   svm_lif01 50:0a:09:81:00:aa:bb:01  node-01     0c
svm_prod   svm_lif02 50:0a:09:82:00:aa:bb:02  node-02     0c

Create the volume and the LUN

cluster1
::> volume create -vserver svm_prod -volume vol_sql01 -aggregate aggr01 -size 500GB -space-guarantee none

::> lun create -vserver svm_prod -path /vol/vol_sql01/lun_sql01 \
             -size 450GB -ostype windows -space-reserve enabled

Create an igroup with the host's initiator WWPN

The igroup is the access-control object on the NetApp side — think of it as the array's own private allow-list, independent of fabric zoning.

cluster1
::> igroup create -vserver svm_prod -igroup ig_winsql01 \
              -protocol fcp -ostype windows \
              -initiator 21:00:00:24:ff:5a:1b:01,21:00:00:24:ff:5a:1b:02

Map the LUN to the igroup

cluster1
::> lun mapping create -vserver svm_prod -path /vol/vol_sql01/lun_sql01 \
                     -igroup ig_winsql01 -lun-id 0
Where zoning fits

At this point the LUN exists and is mapped, but the host still can't see it — the igroup only controls who's allowed to talk to the LUN once they can reach the target port at all. Reachability itself is the fabric's job, and that's what zoning grants.

03

Finding initiator & target WWPNs

You'll need both ends of the conversation in hand before building a zone. Here's where to look on each side.

Target WWPN — from NetApp

cluster1
::> network fcp adapter show -fields wwpn,state

::> network interface show -data-protocol fcp -fields wwpn

Initiator WWPN — from the switch's own login table (fastest way)

Rather than logging into the host at all, the switch already recorded every port that has completed FLOGI:

Cisco MDS
switch# show flogi database

INTERFACE  VSAN  FCID       PORT NAME                NODE NAME
fc1/4      10    0x650001   21:00:00:24:ff:5a:1b:01  20:00:00:24:ff:5a:1b:01
fc1/5      10    0x650002   50:0a:09:81:00:aa:bb:01  50:0a:09:80:00:aa:bb:01

Initiator WWPN — directly from the host, if you don't have switch access

Windows PowerShell
PS> Get-InitiatorPort | Select PortAddress, ConnectionType

PortAddress          ConnectionType
-----------          --------------
2100002...4ff5a1b01   Fibre Channel
Linux
$ cat /sys/class/fc_host/host*/port_name

0x21000024ff5a1b01
ESXi
[root@esxi:~] esxcli storage san fc list

  World Wide Port Name: 21:00:00:24:ff:5a:1b:01

04

Reading the switch's own view of the fabric

Two tables answer almost every "why can't the host see the array" question, before you even open zoning config.

DatabaseAnswers
flogi database"Is this port even logged into the switch at all?" — the most basic reachability check
fcns database (Name Server)"What FC-4 type is this port advertising (e.g. SCSI-FCP), and what symbolic name/WWNN does it carry?" — the fuller registration record
zoneset active"Which pairs of WWPNs are actually allowed to talk to each other right now?"
Cisco MDS
# Everyone logged in, per VSAN
switch# show flogi database

# Fuller name-server record — vendor, symbolic name, FC-4 type
switch# show fcns database vsan 10

# What's actually active right now
switch# show zoneset active vsan 10

# All configured zonesets, including inactive drafts
switch# show zone vsan 10
Brocade
# Port + WWN overview for the whole switch
switch:admin> switchshow

# Name server database — equivalent to fcns on MDS
switch:admin> nsshow

# Currently active (enabled) zone configuration
switch:admin> cfgactvshow

# All defined zones, aliases, and configs — active or not
switch:admin> cfgshow
A common trap

A WWPN can appear in flogi/nsshow and still fail to communicate with its target — that table only proves the port reached the switch. It says nothing about whether a zone permits it to reach any specific other port.

05

Creating and activating a zone

Standard practice is single-initiator, single-target zoning — one host port and one array port per zone, never grouping multiple initiators together. This keeps RSCN (fabric change) traffic from one host affecting unrelated hosts.

Enter configuration mode for the right VSAN

Cisco MDS
switch# configure terminal
switch(config)# zone name Z_HOST01_NETAPP01_A vsan 10

Add the two members by WWPN

Cisco MDS
switch(config-zone)# member pwwn 21:00:00:24:ff:5a:1b:01
switch(config-zone)# member pwwn 50:0a:09:81:00:aa:bb:01

Add the zone to a zoneset

Cisco MDS
switch(config)# zoneset name ZS_FABRIC_A vsan 10
switch(config-zoneset)# member Z_HOST01_NETAPP01_A

Activate the zoneset

This is the step that's easy to forget — a configured zone does nothing until its zoneset is active.

Cisco MDS
switch(config)# zoneset activate name ZS_FABRIC_A vsan 10
switch(config)# copy running-config startup-config

Create aliases for readability (optional but recommended)

Brocade
switch:admin> alicreate "HOST01_HBA0", "21:00:00:24:ff:5a:1b:01"
switch:admin> alicreate "NETAPP01_0c", "50:0a:09:81:00:aa:bb:01"

Create the zone from those aliases

Brocade
switch:admin> zonecreate "Z_HOST01_NETAPP01_A", "HOST01_HBA0;NETAPP01_0c"

Add the zone into the active configuration

Brocade
switch:admin> cfgadd "PROD_CFG", "Z_HOST01_NETAPP01_A"

Save and enable

cfgsave writes the definition to flash; cfgenable is what actually makes it live on the fabric.

Brocade
switch:admin> cfgsave
switch:admin> cfgenable "PROD_CFG"
Redundant fabric reminder

A resilient design has two independent physical fabrics (Fabric A / Fabric B). Repeat this whole zoning process once per fabric, pairing the host's second HBA port with the array's second target port. Never cross-connect A-fabric zoning with B-fabric WWPNs.

06

Verifying and configuring the host end

Once the zone is active and the NetApp mapping exists, the host still needs to rescan and confirm it sees a consistent, multipathed device — not four separate disks.

Windows PowerShell
# Trigger a rescan for new storage
PS> Update-HostStorageCache
PS> Get-Disk

# Confirm MPIO sees multiple paths to the same LUN
PS> mpclaim -s -d
PS> Get-MPIOAvailableHw

# NetApp Host Utilities equivalent of sanlun
PS> sanlun lun show -p
Linux
# Ask the HBA driver to rescan the fabric
$ echo "1" > /sys/class/fc_host/host0/issue_lip
$ for h in /sys/class/scsi_host/host*/scan; do echo "- - -" > $h; done

# Confirm the multipath device and how many paths it has
$ multipath -ll
$ sanlun lun show -p
ESXi
[root@esxi:~] esxcli storage core adapter rescan --all
[root@esxi:~] esxcli storage nmp path list
[root@esxi:~] esxcli storage nmp device list
What "correct" looks like

With a dual-fabric, dual-HBA, dual-target-port design, a healthy LUN shows 4 active paths (2 HBAs × 2 target ports across 2 fabrics) collapsing into one multipath device — not four separate disks. If you see the LUN four times as distinct disks, MPIO/DM-Multipath isn't claiming it correctly, not a zoning problem.

07

Troubleshooting checklist

Work top to bottom — each layer assumes the one above it is already confirmed working.

HBA port is logged into the switch

Confirm the initiator WWPN appears in show flogi database / nsshow. If absent: check cabling, SFP, and that the HBA port isn't administratively down.

Target WWPN is also logged in

Confirm on the NetApp side with network fcp adapter show, and on the switch with the same flogi/nsshow query.

Zone contains both WWPNs, correctly spelled

A single mistyped colon-separated octet is the most common zoning error — copy WWPNs directly from CLI output, never retype them.

Zoneset/config is active, not just defined

show zoneset active (MDS) or cfgactvshow (Brocade) — a saved-but-inactive zone has no effect.

Igroup on NetApp contains the correct initiator

igroup show -instance — confirm the WWPN matches exactly and the ostype is correct for the host.

LUN mapping exists and LUN ID isn't already used

lun mapping show — a duplicate LUN ID within the same igroup will block presentation.

Host has rescanned since the mapping was created

Host OSes generally don't detect new LUNs automatically — a rescan or reboot is required after every change above.
