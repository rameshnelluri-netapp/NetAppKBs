01

Core model

The single biggest difference — and the source of most of the others — is whether the server remembers anything about the client between requests.

NFSv3 · Stateless

  • The server treats every request as independent. It has no memory of prior opens, reads, or client sessions.
  • Simple to implement and easy to recover from a server crash — the client just retries.
  • Locking can't be stateless by nature, so it's bolted on via a separate protocol (NLM), which is the classic weak point.

NFSv4 · Stateful

  • The server tracks open files, locks, and client sessions directly as part of the protocol.
  • Enables features impossible in a stateless model: delegations, proper byte-range locking, callback-based cache coherency.
  • Recovery is more complex — uses lease timers and explicit client reclaim after a server restart.
02

File handles

A file handle is the opaque token a server hands the client to reference a file on subsequent calls — the file's real "address" on the wire.

PropertyNFSv3NFSv4
Max size64 bytes128 bytes
TypePersistent onlyPersistent or volatile
StabilityFixed for the file's lifetimeVolatile handles may expire (e.g. after rename) — client must recover
Why it's bigger in v4—More room to embed metadata for clustered/multi-node storage backends
Why this matters in practice: tools that manipulate storage directly at the block/volume level (cloning, replication, migration utilities) often rely on v3's simple, guaranteed-stable handle model — volatile v4 handles introduce a case those tools have to explicitly handle or avoid.
03

Identity & user/group IDs

This is the difference that causes the most real-world troubleshooting: how a file's owner is represented on the wire.

NFSv3
UID 1001 / GID 1001
raw 32-bit integers
≠
NFSv4
jdoe@example.com
string identifier

NFSv3 sends the numeric UID/GID exactly as stored locally — client and server just need matching numbers, and authentication typically relies on AUTH_SYS, which trusts whatever UID the client claims.

NFSv4 instead sends a user@domain string. This requires an ID-mapping service on both ends — rpc.idmapd on Linux, or ONTAP's identity-mapping configuration — to translate that string back into a local numeric UID/GID.

Common failure mode: if the domain string in idmapd.conf doesn't match between client and server, files silently show up owned by nobody:nobody even though nothing looks wrong numerically. This single mismatch accounts for a large share of "permissions broke after switching to v4" tickets.
04

Locking & state recovery

NFSv3 locking path
Client→ NLM (separate RPC service)→ NSM tracks server reboot state→ Manual-ish reclaim after crash
NFSv4 locking path
Client→ Native OPEN/LOCK ops, same protocol→ Lease timer per client→ Grace period reclaim on restart

Because v3 splits locking into a separate protocol (NLM) with its own crash-tracking service (NSM), lock state can drift out of sync with actual file state after a server reboot — a long-standing source of "stale lock" issues. v4 folds locking into the core protocol and uses lease renewal, so the server can reliably expire a client's locks if it disappears, and delegations let a client cache a file locally and skip round-trips entirely when it's the only one using it.

05

Wire behavior & ports

NFSv3

  • Needs portmapper, mountd, nlockmgr, and statd — several RPC services on several ports.
  • Each client operation (lookup, open, read) is typically its own RPC round trip.
  • Firewall-unfriendly: multiple dynamic ports need to be opened or pinned.

NFSv4

  • Consolidated onto a single well-known port — TCP 2049 — no portmapper dependency.
  • Supports compound operations: multiple ops (lookup + open + read) bundled into one RPC call.
  • A single unified pseudo-filesystem root — clients mount once and traverse into exports, rather than mounting each export separately.
06

ACLs & security

NFSv3

  • Traditional Unix mode bits only (owner/group/other, rwx).
  • Auth is typically AUTH_SYS — the server trusts the client's claimed UID unless something stronger is bolted on separately.

NFSv4

  • Native NFSv4 ACLs — richer, closer to Windows/NTFS-style ACL semantics than Unix mode bits.
  • Much deeper integration with RPCSEC_GSS / Kerberos for strong authentication and encryption in transit.

08

Which one to use

Reach for NFSv3 when —

A tool or workflow needs simple, predictable, stable file handles (storage-level cloning, migration, or replication utilities); the environment is tightly controlled with matching UID/GID numbering across hosts; or you're working with legacy systems/appliances that never implemented v4 properly.

Reach for NFSv4 when —

You need strong Kerberos-based security, richer ACLs, better firewall traversal (single port), improved performance over higher-latency links via compound operations, or robust native locking without NLM's historical flakiness. This is the right default for most new deployments.
