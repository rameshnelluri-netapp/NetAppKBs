01 — Introduction

What is NetApp Data Migrator?

NetApp Data Migrator (NDM) is an enterprise-grade, multicloud data migration software application designed to simplify the migration of unstructured file data from on-premises or third-party storage systems to public cloud storage services powered by NetApp.

It is purpose-built for large and complex migration projects with a defined start, end goal, and cutover window — unlike general-purpose copy tools like rsync or robocopy which require substantial DIY effort.

🎯

Multi-Protocol

Supports both NFS and SMB/CIFS migrations in a single platform. No need for separate tools per protocol.

☁️

Multi-Cloud

Migrates to Azure NetApp Files (ANF), Google Cloud NetApp Volumes (GCNV), Amazon FSx for ONTAP (FSxN), and Cloud Volumes ONTAP (CVO).

💰

Completely Free

Available at no additional cost to NetApp customers. Traditional tools can cost over $150K per PiB migrated.

🔒

Chain of Custody

Checksum-based validation after every migration proves 100% file integrity from source to destination.

📊

Discovery First

Scans and inventories source data before any movement occurs — understand what you're migrating before you start.

⚡

Minimal Downtime

Incremental sync runs before cutover, keeping source live. Final cutover window is short and controlled.

04 — Internals

Under the Hood — What Actually Moves Data

The Worker VM is a NAS client

The Worker VM (Linux or Windows) mounts the source storage via NFS or SMB, mounts the destination the same way, then reads and writes files across — but in parallel streams rather than one file at a time like rsync.

Temporal — The Real Migration Engine

The most important discovery from exploring the pods: NDM uses Temporal, a workflow orchestration platform, as its core engine. This is what makes NDM enterprise-grade:

🔄

temporal-frontend

API gateway — accepts migration job requests from the jobs-service

📜

temporal-history

Tracks the complete state of every workflow step — scan, copy, sync, verify

🎯

temporal-matching

Assigns tasks to available workers — enables parallel processing

⚙️

temporal-worker

Executes workflow logic — retries failed steps automatically without losing progress

08 — Roles & Personas

Three Roles in NDM

NDM uses role-based access control with three distinct personas — each has a different level of access and responsibility.

🛡️

Application Admin

Sets up the environment. Creates users, assigns roles, manages workers, initializes projects. First login configures the whole system.

🔧

Project Admin

Manages file servers, runs discovery jobs, performs migrations (Bulk Discover → Bulk Migrate → Bulk Cutover), oversees job progress.

👁️

Project Viewer

Read-only access. Reviews discovery reports, downloads Chain of Custody reports, approves cutovers. Supports audit and compliance.

09 — Setup

Adding Workers

Workers are the VMs that actually move data. Each protocol needs its own worker type. Workers are installed via a one-line script from the NDM UI — you don't download a separate image.

NFS Worker (Linux)

1

Log in as Project Admin

Open NDM in browser → login with projectadmin@demonetapp.com

2

Navigate to Workers

From navigation menu, select Workers

3

View Installation Instructions

Click View Instruction to Setup Worker → the NFS tab shows a one-line install command

4

Copy the install command

Click the copy icon. Each worker gets a unique WORKER_ID — always close and reopen instructions for each new worker.

5

SSH into the Linux Worker VM

Open PuTTY → connect to ndmlx (192.168.0.10) → enter password → run sudo su

6

Paste and run the install command

Paste the copied command → press ENTER. Installation completes in a few seconds.

7

Verify in NDM UI

Worker appears in list as nfs-worker-1 with status Online.

SMB Worker (Windows)

1

View Instructions → select SMB

In NDM Workers section → click View Instruction → select SMB radio button

2

On the Windows Jumphost

Open File Explorer → navigate to C:\temp\ → double-click windows-worker-installer-*.exe

3

Install to default location

Keep default C:\datamigrator → click Next

4

Copy values from NDM instructions

Copy each field value carefully — match by field name, not by order (order may differ)

5

Install (~5 minutes)

11 — Migration

Migration Lifecycle

Every migration in NDM follows the same three-phase lifecycle, whether you're doing a full volume or a single directory:

PHASE 01
Bulk Discover
Scan source, inventory files, generate PDF report. No data moves.
PHASE 02
Bulk Migrate
Baseline copy + incremental syncs. Source stays live.
PHASE 03
Bulk Cutover
Final sync → CoC report → review → approve. Migration complete.
⚠️

Important: Do not run Migration and Cutover jobs simultaneously. Ensure only one job is active at a time.

12 — Migration

Bulk NFS Migration (Full Volume)

This pattern moves entire NFS exports as a single unit — ideal for lift-and-shift of complete datasets. Performed by Project Admin.

Phase 1: Bulk Discover

1

Select source_svm1_nfs

Storage Servers → File Servers → click source_svm1_nfs

2

Click Bulk Discover

Job Schedule: Start Now · Protocol: NFS

3

Select NFS export paths

Check both: /svm1_nfs_engineering and /svm1_nfs_patents

4

Submit → monitor in Job Run List

Jobs → Job Run List → wait for status: Completed

5

Download Discovery Report PDF

Action menu (⋯) → Download Discovery Report as PDF. Review the inventory before proceeding.

Phase 2: Bulk Migrate

1

Storage Servers → source_svm1_nfs → Bulk Migrate

2

Add first path mapping

Source: /svm1_nfs_engineering → Destination: destination_svm2_nfs → /svm2_nfs_engineering → click + Add Mapping

3

Add second path mapping

Source: /svm1_nfs_patents → Destination: destination_svm2_nfs → /svm2_nfs_patents → click + Add Mapping

4

Accept all defaults → Proceed → Submit

Select both checkboxes → Submit

5

Monitor in Job Run List

Wait for Status: Completed and Files/Size count > 0. Click refresh to update.

6

Verify on destination

Open File Explorer on Jumphost → navigate to \\svm2 → open svm2_nfs_patents → confirm files are present.

Phase 3: Bulk Cutover

1

Storage Servers → source_svm1_nfs → Bulk Cutover

2

Select both paths + accept disclaimer → Proceed

Read the liability waiver carefully and check the checkbox.

3

Ensure no ongoing jobs → Submit

Jobs should be idle before submitting cutover.

4

Wait for Blocked state

Jobs → Job Run List → refresh until jobs show Blocked (final sync complete, waiting for approval).

5

Review each job → Confirm

Action (⋯) → Review → check "I have reviewed…" → click Confirm. Repeat for second job.

6

Status changes to Approved

NFS full volume migration is now complete. Log out as Project Admin.

13 — Migration

Directory-Level SMB Migration

This pattern targets specific subfolders within a share with custom incremental sync schedules — ideal for coordinating cutover windows per team. Also enables restructuring data during migration (e.g., splitting one group drive into multiple separate destinations). Performed by App Admin.

Phase 1: Bulk Discover (SMB)

1

Log in as App Admin

appadmin@demonetapp.com

2

Storage Servers → source_svm1_smb → Bulk Discover

3

Select svm1_smb_groupdrives → Submit

Leave all defaults. Monitor in Job Run List until Completed.

Phase 2: Bulk Migrate with Directory Mapping

1

source_svm1_smb → Bulk Migrate

2

Add Finance directory mapping

Source: svm1_smb_groupdrives → + Add Source Directory → select Finance → Confirm → Dest: svm2_smb_group_finance → Add Mapping

3

Add Operations mapping

Source dir: operations → Dest: svm2_smb_group_operations → Add Mapping

4

Add Sales mapping

Source dir: sales → Dest: svm2_smb_group_sales → Add Mapping → Proceed

5

Configure aggressive sync options

• Preserve a-time: Enabled
• Preserve permissions: Enabled
• Skip Files modified in last: 1 minute
• Incremental Sync Schedule: Cron Expression → */2 * * * * (every 2 minutes)

6

Select all 3 paths → Submit

Monitor in Job Run List. Status will switch frequently between Completed/Running/Ready due to 2-minute sync schedule.

7

Test incremental sync

On Jumphost → navigate to \\svm1\svm1_smb_groupdrives\finance → create a new text file called finance_update → wait 2 minutes → check \\svm2\svm2_smb_group_finance → file should appear.

Phase 3: Bulk Cutover (SMB)

1

source_svm1_smb → Bulk Cutover

Select all 3 entries + check disclaimer → Proceed

2

Ensure no active jobs → Submit

Refresh if needed to confirm idle state before submitting.

3

Wait for all 3 jobs → Blocked state

Jobs → Job Run List → refresh until all 3 cutover jobs show Blocked.

4

Review and Confirm each job

For each of the 3 jobs: ⋯ → Review → "I have reviewed…" → Confirm. All 3 jobs change to Approved.

✅

Both migrations are now complete. No more incremental updates will occur between source and destination. The source is now safe to decommission after report review.

16 — Summary

What We Learned

🏗️

NDM = Kubernetes Appliance

Pre-built Ubuntu 24.04 VM image running MicroK8s with ~50 pods. Not a simple installer — a full microservices platform.

⚙️

Temporal Powers Workflows

The real migration engine is Temporal — it orchestrates scan → copy → sync → verify with automatic retry and state tracking.

🖥️

Workers = Separate VMs

Linux VM for NFS, Windows VM for SMB. Installed via one-line script from the NDM UI. Multiple workers scale throughput.

🔄

Three-Phase Lifecycle

Always: Discover → Migrate (with incremental sync) → Cutover. Source stays live until the short controlled final cutover.

🛡️

Proof of Integrity

Chain of Custody reports with checksums verify every file. You can prove data arrived intact before decommissioning source.

💡

Pods ≠ VMs

50 pods run inside 1 VM. Pods are lightweight processes sharing the OS kernel — like apartments in a building, not separate houses.
