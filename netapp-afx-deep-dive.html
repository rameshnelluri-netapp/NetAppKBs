01 — Orientation

What AFX actually changes

AFX is still ONTAP — same codebase, same System Manager, same SnapMirror/FlexClone/ARP feature set. What's different is the relationship between compute and storage underneath it.

Left: node-owned disks, direct HA cabling. Right: everything meets at the switch — no ownership, no direct cabling.
Unified ONTAP

Compute and capacity scale together

Each controller has a fixed relationship with its own disks or partitions, manages its own aggregate, and fails over to its HA partner via a direct NVRAM cable. Want more throughput? You typically add nodes and capacity together.

Disaggregated ONTAP (AFX)

Compute and capacity scale independently

Every controller node sees every disk through a shared Ethernet fabric. There's no node-to-shelf ownership. Need more performance — add nodes. Need more capacity — add shelves. Nothing else has to change.

AFX is NAS and S3 object only — block storage isn't supported and isn't planned. Supported protocols are SMB 2/3, S3, and NFSv3 through NFSv4.2, which covers essentially every AI data-pipeline pattern: NFS for feeding GPU training jobs, S3 for the data lake / model artifacts, and pNFS for clients that can pull from multiple nodes in parallel.

02 — Building Blocks

The physical components

A typical AFX deployment is three kinds of boxes plus a pair of switches.

Controller

AFX 1K node

2U, based on the AFF A1K platform. No on-board disk. Purely a compute node — modular, and performance increases roughly linearly as you add more.

Storage

NX224 NVMe shelf

2U shelf, 24 NVMe SSDs. Drive sizes: 7.6TB and 15.3TB (TLC), 30.7TB and 61.4TB (QLC, the latter added in ONTAP 9.18.1).

Optional

DX50 compute node

Runs NetApp AI Data Engine (AIDE) natively inside the AFX cluster — metadata indexing, vectorization, and privacy/governance for AI pipelines.

Purchasing constraints worth knowing

  • Shelves are sold fully populated — there's no partial-shelf configuration.
  • Drive sizes can't be mixed within a single Storage Availability Zone.
  • Once a shelf is added, it can't be removed.
  • 15.3TB drives can start on a single shelf; every other drive size requires a minimum of two shelves.
  • Smallest practical footprint: a 4-node cluster with one 15.3TB shelf needs ~12U (8U controllers + 2U shelf + 2U switches).
03 — Networking

The switch fabric

This is the part that makes disaggregation physically possible: nodes and shelves both plug into the same pair of switches — nothing is chained, nothing is directly wired to anything else.

Every node and every shelf connects independently to both switch A and switch B for redundancy.
Q — new shelves needed, do they attach to switches or shelf-to-shelf?

Directly to the switches, every time. When you hot-add an NX224 shelf, you rack it, power it, set a unique shelf ID, and cable both I/O modules straight to switch A and switch B. There's no chaining one shelf into another — ONTAP recognizes the new shelf automatically once it's cabled, and firmware updates itself if needed.

This is deliberate: if shelves were chained, a shelf further down the line could bottleneck or become a single point of failure for everything behind it. Direct, independent, symmetric connections are what let every node reach every disk with the same low latency.

Port speed — 100GbE at the box, 400GbE at the switch

All controller and shelf interfaces (cluster, storage, and HA ports) run at 100GbE. The backend switches — Cisco Nexus 9332D / 9364D class — run at 400GbE. The gap between the two is closed with breakout cabling.

A 400G QSFP-DD port carries four independent 100G lanes internally — a breakout cable simply separates them into four physical connectors, each going to a different device.
Q — how can one switch port take cables from 4 NetApp ports?

The 400G connector isn't one stream — it's 4 independent 100G lanes bundled into a single QSFP-DD cage, a standard, switch-configurable mode. A breakout cable is one connector on the switch end, fanning into 4 separate cables on the far end, each plugging into a different node or shelf port.

Think of it like a power strip on a wall outlet: one socket feeds the strip, but 4 independent devices plug into the strip's separate outlets. On the switch's config, that one port becomes 4 addressable sub-interfaces, e.g. Ethernet1/1/1 through Ethernet1/1/4.

04 — Availability

HA pairs, without the HA cable

One of the more surprising changes AFX makes: HA partner nodes no longer need to be physically wired together.

AFX removes the need to directly connect HA partner nodes — HA pairs instead communicate over the internal cluster network, i.e. through the same backend switches carrying everything else, isolated on its own VLAN.

Because HA no longer depends on a physical adjacency, you get a genuine operational benefit: HA pairs can be deployed in separate racks or rows for better fault tolerance against a rack-level power or cooling failure — something impossible when HA partners had to sit in the same chassis with a direct NVRAM cable.

Failover behavior also changes shape. When a node fails, its volumes fail over to the HA partner just long enough to commit any in-flight writes to disk — then ONTAP rebalances those volumes evenly across all surviving nodes in the cluster, not just onto the one HA partner. Because the data itself already sits in the shared pool, none of this requires a data copy.

05 — Scale

Cluster size and the port-count ceiling

If every node and shelf needs a direct switch connection, switch port density becomes the real limiting factor on how large a cluster can grow.

The 9364D-GX2A and newer 9808 chassis switch exist specifically to push node and shelf counts higher — the 9364D-GX2A explicitly enables building ONTAP clusters with more than two nodes, and the 9808 extends that further for AFX 2K systems.

Cluster minimums

4 nodes minimum

Each AFX cluster must have at least four nodes. The maximum varies by ONTAP release — always check the NetApp Hardware Universe for the current ceiling.

Published scale target

Up to 128 controller nodes

NetApp has discussed AFX scaling to 128 nodes to hit a target of ~4 TB/s aggregate read throughput and over 1 EB of capacity — well beyond the 24-node ceiling of classic unified-ONTAP clusters.

Note: the familiar "2 minimum, 24 maximum nodes" figure is the classic unified ONTAP cluster limit — it does not apply to AFX. NetApp has said the AFX architecture can scale "more than an order of magnitude" above its early published spec numbers.

06 — Storage Pooling

The Storage Availability Zone (SAZ)

This is the single concept that makes disaggregation work at the software level.

Every controller node has read/write access to every disk. No node "owns" any disk.

How ONTAP recognizes new storage — automatically

There's no manual "assign this disk to that node" step. When storage shelves are added to a cluster, ONTAP automatically incorporates the disks — a storage abstraction layer configures RAID groups and low-level disk management with zero admin intervention.

Who owns what — the ownership model flips

  • No node owns a disk. Every node can read and write every disk in the SAZ — there's no aggregate ownership at all.
  • A node does own a volume. That ownership determines which node's NVRAM commits writes for that volume — but the underlying data can physically live on any disk in the pool.
  • Moving a volume is nearly free. Since the data is already reachable from every node, a volume move is a Zero Copy Volume Move — just a metadata/pointer update, not a data copy. This also applies during HA failover and automatic rebalancing.

The data path — node to disk

Shelves use NVMe over Fabrics (NVMe-oF), transported over RDMA over Converged Ethernet (RoCE). This is what lets a node treat a "remote" disk almost like a locally attached one — RDMA's ultra-low latency is what makes pooling disks across a switch fabric practical instead of a performance compromise.

NVMe-oF is the command protocol; RoCE-over-Ethernet is the transport it rides on. No Fibre Channel involved.
07 — Data Protection

RAID inside the SAZ

Pooling disks doesn't remove RAID — it just makes RAID groups bigger and fully automatic.

Default

RAID-TEC

Triple-parity erasure coding — survives three simultaneous drive failures. Larger drives take longer to rebuild, so more parity headroom matters more as capacity grows.

Group size

Up to 96 drives per group

92 data + 3 parity + 1 spare — a 3× jump over the 32-drive max on unified ONTAP. Only ~4% overhead, which is excellent usable-to-raw efficiency.

Small-scale exception: the smallest configs (single shelf of 15.3TB drives) start on RAID-DP. Once a second shelf is added, ONTAP automatically converts the RAID groups to RAID-TEC at the 96-drive size — no admin action required.

Multiple groups, one zone: a small SAZ might fit in a single RAID group. As the SAZ grows past ~96 drives, ONTAP creates additional RAID groups (still capped at 96 each) and spreads capacity across them — all still inside the one SAZ. You never manually create, size, or assign disks to a RAID group.

Rebuilds are disaggregated too. Because every node can reach every disk, RAID rebuilds run distributed across multiple cluster nodes simultaneously — shrinking the post-failure risk window compared to a single controller doing the rebuild alone.

08 — Protocol vs. Transport

NVMe-oF ≠ Fibre Channel

A common point of confusion — NVMe-oF names a command protocol, not a specific kind of cable or switch port.

NVMe-oF just means "the NVMe command set, sent over a network instead of local PCIe." It's transport-agnostic — the same way "email" can travel over WiFi, Ethernet, or cellular without changing what email is.

TransportNamePhysical mediumUsed by AFX?
Fibre ChannelNVMe/FCDedicated FC switches, HBAs, FC cablingNo
RDMA over Converged EthernetNVMe/RoCEStandard Ethernet, RDMA NICsYes
TCPNVMe/TCPStandard Ethernet, regular NICsNo

AFX shelves connect via standard 100GbE Ethernet ports, on the same Cisco Nexus switches used for everything else in the cluster — not Fibre Channel switches, HBAs, or cabling. RoCE delivers FC-like low latency, but over cheaper, more common, higher-bandwidth Ethernet gear — which is also why AFX doesn't need InfiniBand: NFS-over-RDMA and NVMe/RoCE already deliver RDMA-class performance on standard Ethernet.

09 — Performance

Where the big throughput numbers actually come from

A single LIF is still bound to one node's ports — it doesn't get faster just because AFX is disaggregated. The scale comes from parallelism across many nodes at once.

NetApp's standard practice for AFX: one LIF (IP address) per node per protocol. A 64-node cluster means 64 independent NFS/SMB/S3 endpoints, each capped at that node's own port bandwidth.

How clients actually reach that aggregate bandwidth

  • pNFS (NFSv4.1+): each node presents its own NFS endpoint; pNFS-aware clients discover all nodes and spread I/O across them in parallel (recent Linux distros use trunkdiscovery to automate this).
  • SMB Multichannel: the Windows equivalent — multiple paths are discovered and used automatically, on by default.
  • nconnect / multiple mounts: lets even non-pNFS clients open several parallel connections across different node IPs.
Aggregate throughput scales by adding fire hoses, not by making one hose fatter.

Analogy: think of it as adding more fire hoses (one per node) all drawing from the same shared reservoir (the SAZ) — total flow scales with the number of hoses, not the size of any single one. A single client on a single connection never sees the full cluster figure; the cluster-wide number is what you get when many parallel connections are active at once.
