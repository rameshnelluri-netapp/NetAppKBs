1) Big picture: what problem key managers solve

When ONTAP encrypts a volume, it needs encryption keys. Those keys must be generated, protected, stored safely, and made available when ONTAP needs to read/write encrypted data. A key manager is the component responsible for that key lifecycle.

At a very high level:

Encrypted Volume
    │
    ▼
Volume Data Encryption Key (DEK / VEK)
    │
    ▼
Protected by / stored through Key Manager
    │
    ├─ Onboard Key Manager (OKM)  → keys managed inside ONTAP cluster
    └─ External Key Manager (KMIP) → keys managed by external KMS
Important: Encryption in ONTAP is not “just a license”. The license enables the feature, but actual protection requires a configured key manager and then encrypted volumes/aggregates/root volumes as applicable.

3) NVE vs NAE vs NSE — what each one encrypts

NVE (NetApp Volume Encryption)

  • Encryption is applied per volume.
  • Each encrypted volume has its own key.
  • You can rekey a single volume.

NAE (NetApp Aggregate Encryption)

  • Encryption is applied at the aggregate level.
  • Volumes created on an NAE aggregate are protected through the aggregate encryption model.
  • Useful when you want encryption + storage efficiencies across volumes in the same aggregate.

NSE (NetApp Storage Encryption)

  • Hardware-based self-encrypting drives (SEDs/FIPS drives).
  • Separate from NVE/NAE. You can have NSE alone, NVE alone, or both depending on platform/support.
If you hear “volume key rotation”, that usually points to NVE behavior, because NVE manages volume-specific keys.

5) Where the OKM database is stored

Short answer

There is no single “master node” holding the only OKM database. With OKM, the key-manager state is cluster-scoped logically but persisted locally on each node in that node’s boot/root environment.

Logical vs physical view

Logical view: one cluster-wide OKM state/configuration.

Physical view: each node has its own persisted local copy of the OKM recovery/key-manager information.

Cluster-wide OKM state (logical)
   │
   ├── Node1 local OKM persisted copy
   ├── Node2 local OKM persisted copy
   ├── Node3 local OKM persisted copy
   └── Node4 local OKM persisted copy

Is it in the root volume?

The safest mental model is:

  • The node’s local OKM recovery material is tied to that node’s boot/root environment.
  • Do not think of it as a normal file sitting in a browsable data directory.
  • It is boot/recovery metadata required by the node, especially if the root volume is encrypted.
This is why after boot media or controller replacement, a node can lose its local OKM recovery material while the rest of the cluster still has their copies.

7) When root volumes are encrypted

Important rule

NVE license installed + encrypted data volumes does NOT automatically mean the node root volume is encrypted.

Node root volume encryption

  • Node root volume encryption is a separate capability and admin action.
  • If the node root is encrypted, boot-time key recovery matters much more after hardware replacement.
  • If the node root is not encrypted, the node can generally boot without needing Boot Menu Option 10.

SVM root volume encryption

  • SVM root volume behavior depends on ONTAP version and whether the SVM root sits on an NAE aggregate or is explicitly supported for NVE in that release.
Do not assume “volumes are encrypted” means “all roots are encrypted”. Always identify which root volume you mean and whether that specific root was encrypted.

8) Volume key rotation (rekey) vs OKM passphrase rotation

A) Volume key rotation / rekey

This changes the data encryption key for a specific encrypted volume.

Before
Volume vol1  → Key-A

After rekey
Volume vol1  → Key-B

The data stays online; ONTAP generates the new key and transitions the volume to it.

Core commands

volume show -vserver <svm> -volume <vol> -fields is-encrypted,encryption-state

volume encryption rekey start -vserver <svm> -volume <vol>

volume encryption rekey show

volume encryption rekey pause -vserver <svm> -volume <vol>

volume encryption rekey resume -vserver <svm> -volume <vol>

B) OKM passphrase rotation

This changes the cluster-wide OKM passphrase that protects the onboard key-manager store/recovery secrets. It does not directly change the DEK of each volume.

security key-manager onboard update-passphrase

Easy way to remember

OperationWhat changes?
Volume rekeyVolume’s DEK/VEK changes
OKM passphrase updateCluster-wide OKM passphrase changes

10) OKM restore/sync vs Boot Menu Option 10

These are not the same thing

ActionRuns fromWhen usedPurpose
security key-manager onboard syncONTAP CLI (post-boot)Node already bootedRestore/synchronize the full OKM state to a node
Boot Menu Option 10Boot Menu (pre-ONTAP boot)Node cannot boot encrypted root because local OKM recovery secrets are missingRestore enough recovery secrets so the node can boot

Why Option 10 exists

If the node root volume is encrypted and you replace boot media/controller/motherboard, the node may lose the local OKM recovery material it needs to unlock the encrypted root before ONTAP can even boot. In that case:

Power On
   ↓
Need to mount encrypted root volume
   ↓
Need OKM recovery secrets
   ↓
But ONTAP CLI is not available yet

Option 10 breaks that dependency by restoring the recovery secrets before ONTAP boots.

Why onboard sync still matters after Option 10

Option 10 restores enough for boot. After the node comes up, security key-manager onboard sync is used to restore/synchronize the complete OKM state back to that node.

11) Motherboard / controller / boot media replacement scenarios

Case A — Node root volume is encrypted

Typical recovery flow:

  1. Boot to Boot Menu.
  2. Choose Option 10 and provide:
    • cluster-wide OKM passphrase
    • OKM backup data (saved from security key-manager onboard show-backup)
  3. Normal boot.
  4. Complete the hardware recovery / giveback steps.
  5. Run security key-manager onboard sync after the node is up.

Case B — Node root volume is NOT encrypted

Usually you do not need Option 10 for boot-time root unlock, because there is no encrypted root to unlock.

  • The node can generally boot without Option 10.
  • You still follow the normal hardware replacement procedure.
  • If encrypted data volumes / key-manager state need to be synchronized to that node after boot, you use the post-boot recovery path such as security key-manager onboard sync as appropriate.

12) Your doubts and clarifications — Q&A section

Q1) How do keys “know” different policies if it’s just a license in NetApp?

Answer: The license only enables encryption capability. Actual behavior depends on:

  • whether OKM/EKM is configured,
  • whether the aggregate/volume/root volume is encrypted,
  • the ONTAP version and supported encryption mode,
  • the admin action taken (for example, explicit root encryption or volume rekey).

Q2) How can I encrypt a volume? What security policy types are available?

Answer: In ONTAP, encryption is usually done through NVE or NAE. The “policy” is not typically a per-volume AES-128 vs AES-256 selector. You enable/configure key management, then create or convert encrypted volumes/aggregates based on the supported feature set of your ONTAP version.

Q3) What is the difference between AES-256 and AES-128? Where do we choose it?

Answer: AES-128 and AES-256 differ mainly in key length. In ONTAP, administrators generally do not pick AES-128 vs AES-256 per volume the way they might pick a volume option. The cryptographic implementation and platform support determine what is used.

Q4) Does each volume in the same SVM have a different key?

With NVE: yes, each encrypted volume has its own DEK/VEK. Volumes in the same SVM can have different volume keys even though they share the same key-manager framework.

Q5) Is key rotation the same as disabling and re-enabling encryption on a volume?

No. Rekeying changes the volume’s encryption key while the volume stays encrypted and online. It is not the same as decrypting and re-encrypting from scratch.

Q6) Who performs key rotation and where is it changed?

Volume key rotation: usually initiated by a storage admin via ONTAP CLI. ONTAP generates a new key and stores it in OKM/EKM.

OKM passphrase rotation: usually initiated by a storage/security admin using the onboard key-manager passphrase update command.

Q7) What exactly changes during volume rekey?

The volume’s DEK/VEK changes. The volume remains online. ONTAP transitions the volume from the old key to the new key.

Q8) Where is the OKM database stored — on master node or all nodes?

All nodes. There is no special “master node” that alone stores the only OKM copy. The OKM state is cluster-scoped logically and persisted locally on each node’s boot/root side.

Q9) Will the root volume contain the OKM database?

The node’s local OKM recovery material is tied to that node’s boot/root environment, but it is better to think of it as boot/recovery metadata, not as a normal user-browsable file living in a data directory.

Q10) If NVE license is installed and encrypted volumes exist, does that automatically mean the root volume is encrypted?

No. Encrypted data volumes do not automatically imply encrypted node root. Root volume encryption is a separate support/enablement decision.

Q11) If the root is not encrypted, why can’t we directly go to Option 10 post motherboard replacement?

You generally don’t need Option 10 in that case. Option 10 is for restoring OKM recovery secrets required to boot an encrypted root volume. If the root volume is not encrypted, the node does not need those secrets just to boot root.

13) Runbooks and checklists

Runbook A — Rotate a volume encryption key

  1. Verify the volume is encrypted: 
    volume show -vserver <svm> -volume <vol> -fields is-encrypted,encryption-state
  2. Start rekey: 
    volume encryption rekey start -vserver <svm> -volume <vol>
  3. Monitor: 
    volume encryption rekey show
  4. If needed, pause/resume: 
    volume encryption rekey pause -vserver <svm> -volume <vol>
volume encryption rekey resume -vserver <svm> -volume <vol>

Runbook B — Change OKM passphrase

  1. Ensure you have the current passphrase and a maintenance window if your process requires one.
  2. Run: 
    security key-manager onboard update-passphrase
  3. Update secure records / password vault as per policy.
  4. Take or verify backup data: 
    security key-manager onboard show-backup

Runbook C — Boot media / controller / motherboard replacement with encrypted root

  1. Before replacement, capture/confirm:
    • cluster-wide OKM passphrase
    • backup blob from security key-manager onboard show-backup
  2. After replacement, boot to Boot Menu.
  3. Choose Option 10 and provide passphrase + backup blob.
  4. Normal boot.
  5. Complete takeover/giveback or the hardware runbook steps.
  6. Run: 
    security key-manager onboard sync
  7. Validate encrypted volumes / key-manager state as appropriate.

Runbook D — Node booted, but local OKM copy needs restoring

  1. Confirm the node is up and cluster healthy enough for post-boot recovery.
  2. Run: 
    security key-manager onboard sync
  3. Provide cluster passphrase when prompted.
  4. Verify the node now has the synchronized OKM state.

      │
      ▼

      │
      ▼

      │
      ▼
Keys are protected by the key manager
      │
      ├─ Volume rekey → changes the volume’s DEK
      ├─ OKM passphrase update → changes the OKM passphrase
      ├─ Option 10 → pre-boot recovery for encrypted root
      └─ onboard sync → post-boot restoration/synchronization of OKM state
If you remember only one rule: Option 10 is about booting an encrypted root when the node has lost its local OKM recovery secrets. onboard sync is about restoring/synchronizing the node’s full OKM state after ONTAP is already up.
