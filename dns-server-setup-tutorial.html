Tutorial · Windows Server DNS

Setting up a DNS Server and adding DNS entries

A practical walkthrough for standing up DNS on a Windows Server (including as part of a domain controller like NetappWorld.com), creating zones, adding host and pointer records, and pointing client machines — like a Rocky Linux VM — at it.

Install DNS role→ Create zones→ Add records→ Set forwarders→ Point clients→ Verify + automate
00 · Overview

What a DNS server actually needs to do

A DNS server has two jobs: answer questions about names it owns (authoritative resolution — your zone), and pass along questions it doesn't own to someone who does (recursion / forwarding — the rest of the internet). Setting one up means configuring both halves.

Authoritative side

Zones you create — e.g. NetappWorld.com — plus the A, PTR, CNAME, and other records inside them. This is what makes myrockyvm.NetappWorld.com resolvable.

Recursive / forwarding side

Where the server sends queries it can't answer itself — like google.com. Configured under Forwarders, pointing at an external resolver.

01 · Install

Installing the DNS Server roleGUIPowerShell

Via Server Manager

  1. Open Server Manager → Manage → Add Roles and Features.
  2. Click through to Server Roles → check DNS Server → Add Features when prompted → Next through the wizard → Install.
  3. Once installed, open it from Tools → DNS, or run dnsmgmt.msc.

If this server is being promoted to a Domain Controller (e.g. for NetappWorld.com), the DNS role is typically installed automatically as part of that promotion, along with a forward zone matching the domain name.

Via PowerShell

Install-WindowsFeature -Name DNS -IncludeManagementTools
02 · Zones

Creating forward and reverse lookup zones

A forward zone answers "what's the IP for this name?". A reverse zone answers "what's the name for this IP?" — and it doesn't exist unless you create it.

Forward Lookup Zone (skip if it already exists, e.g. from AD promotion)

  1. In DNS Manager, right-click Forward Lookup Zones → New Zone…
  2. Primary zone → (if AD is present) check Store the zone in Active Directory → Next.
  3. Choose replication scope → Next.
  4. Zone name: NetappWorld.com → Next.
  5. Choose dynamic update setting (covered in section 08) → Finish.

Reverse Lookup Zone

  1. Right-click Reverse Lookup Zones → New Zone…
  2. Primary zone (+ AD-integrated if applicable) → Next.
  3. Select IPv4 Reverse Lookup Zone → Next.
  4. Enter the Network ID, e.g. 192.168.59 for a /24 → Next.
  5. Choose dynamic update setting → Finish.
Why it matters — without a reverse zone, PTR records have nowhere to live, and nslookup <ip> will always return NXDOMAIN, even if the forward record resolves fine.
03 · Core Task

Adding a Host (A) record with its PTRGUIPowerShell

GUI

  1. Right-click your forward zone (NetappWorld.com) → New Host (A or AAAA)…
  2. Name: myrockyvm (short hostname, not the FQDN)
  3. IP address: 192.168.59.130
  4. Check "Create associated pointer (PTR) record"
  5. Click Add Host → confirm the success popup → Done

PowerShell

Add-DnsServerResourceRecordA -Name "myrockyvm" -ZoneName "NetappWorld.com" `
  -IPv4Address "192.168.59.130" -CreatePtr

The -CreatePtr switch only succeeds if a matching reverse zone already exists — create that first if the command errors out.

Confirm it landed

  • Forward zone → myrockyvm should appear with IP 192.168.59.130
  • Reverse zone (59.168.192.in-addr.arpa) → a PTR record pointing back to myrockyvm.NetappWorld.com

05 · Internet resolution

Setting Forwarders (so google.com still resolves)

Your zone is authoritative for NetappWorld.com only — it knows nothing about google.com. Forwarders tell the server where to send queries it can't answer itself.

  1. Right-click the server name (top of the DNS Manager tree) → Properties
  2. Go to the Forwarders tab → Edit…
  3. Add a public resolver, e.g. 8.8.8.8 and 8.8.4.4 (or your company's upstream DNS) → OK → OK
Don't point this at your own server's IP — that creates a loop where the server just asks itself the same unanswerable question. Forwarders must be a different, external-capable resolver. If left empty, Windows falls back to slower root-hint recursion instead of forwarding.
06 · Client side

Pointing a Linux client at this DNS server

sudo nmcli con mod ens160 ipv4.dns "<Windows_DNS_Server_IP>"
sudo nmcli con mod ens160 ipv4.dns-search "NetappWorld.com"
sudo hostnamectl set-hostname myrockyvm.NetappWorld.com
sudo nmcli con up ens160

Order doesn't matter functionally — the DNS record existing and the client's resolver config are independent — but creating the record first and confirming it from the server (Resolve-DnsName) before touching the client makes troubleshooting far easier if something doesn't resolve.

07 · Verification

Confirming forward and reverse resolution both work

# From the DNS server (PowerShell)
Resolve-DnsName myrockyvm.NetappWorld.com
Resolve-DnsName 192.168.59.130

# From the Linux client
nslookup myrockyvm.NetappWorld.com
nslookup 192.168.59.130
nslookup google.com

All three should return clean answers: the FQDN resolving to the IP, the IP resolving back to the FQDN, and external names still working through the forwarder.

08 · Automation

Dynamic DNS — let clients register themselves

Instead of adding every host record by hand, machines can register their own A/PTR records.

Option A — Nonsecure dynamic updates (lab only)

  1. Zone Properties → Dynamic updates → Nonsecure and secure (do this for both forward and reverse zones).
  2. DHCP clients: enable hostname sending — 
    sudo nmcli con mod ens160 ipv4.dhcp-send-hostname yes
sudo nmcli con mod ens160 ipv4.dhcp-hostname "myrockyvm.NetappWorld.com"
  3. Static-IP clients: push a manual update with nsupdate — 
    sudo dnf install bind-utils -y

nsupdate <<EOF
server 192.168.59.<DC_IP>
zone NetappWorld.com
update add myrockyvm.NetappWorld.com 3600 A 192.168.59.130
send
EOF
Trade-off — nonsecure updates accept writes from anyone who can reach the DNS server — fine to learn on, not something to run in production.

Option B — Secure updates via domain join (production pattern)

sudo dnf install realmd sssd oddjob oddjob-mkhomedir adcli samba-common-tools krb5-workstation -y

sudo realm discover NetappWorld.com
sudo realm join NetappWorld.com -U Administrator

# set zones back to "Secure only" once machines are domain-joined

kinit administrator@NETAPPWORLD.COM
nsupdate -g <<EOF
server 192.168.59.<DC_IP>
zone NetappWorld.com
update add myrockyvm.NetappWorld.com 3600 A 192.168.59.130
send
EOF

The -g flag makes the update authenticate over Kerberos, so only domain-joined machines can write records to the zone.

A · NonsecureB · Domain join
Setup effortLowHigher
SecurityWeak — open writesStrong — Kerberos-authenticated
Production-realisticNoYes
Bonus—Also enables AD login on Linux via sssd
09 · Cheatsheet

Quick troubleshooting reference

SymptomLikely cause
nslookup <ip> → NXDOMAINNo reverse zone exists, or the PTR wasn't created
Internal names resolve, google.com doesn'tForwarders not configured on the DNS server
Client can't reach DNS server at allWrong IP in /etc/resolv.conf, or firewall blocking port 53
PTR checkbox greyed out when adding a hostMatching reverse lookup zone doesn't exist yet
nsupdate fails silentlyZone set to "Secure only" but client isn't domain-joined / no Kerberos ticket
