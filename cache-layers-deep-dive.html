Remote & Branch Access Tutorial

Three ways to
cache a NetApp share

BranchCache, FlexCache, and Global File Cache all solve the same complaint — "the file share is slow from our other office" — with three completely different architectures. This walks through how each one actually moves data, step by step.

Every caching layer is really this same idea — shrink the distance between the second request and its answer.

01

Same problem, three architectures

A branch office, a slow WAN link, and a file share that lives somewhere else. Every one of these technologies attacks that same gap — but they disagree about where the cache lives, who owns the software, and what still has to touch the origin every time.

BranchCache

Microsoft, not NetApp

Built into Windows

ONTAP just needs to speak the protocol. The cache lives on Windows clients or a Windows server at the branch — no NetApp component is deployed there at all.

FlexCache

Native ONTAP feature

Runs on storage controllers

The cache is itself an ONTAP volume, on another cluster or another site. NFS and SMB both work. No Windows infrastructure required anywhere.

Global File Cache

NetApp product, ex-Talon

Dedicated appliance per site

A purpose-built virtual appliance sits at the origin and at every branch. SMB only, licensed per site, strongest multi-site write locking of the three.

02

BranchCache

SMB only · Windows-native · no license cost

ONTAP's role is small: authenticate every request and hand out freshness metadata. All the actual caching infrastructure is Windows.

Two deployment modes — pick one per branch office

  • Hosted cache mode: one designated Windows server at the branch stores the cache. Every client at that branch is pointed at it. Better for larger branches, or ones with mobile/roaming users.
  • Distributed cache mode: no server required. Each client keeps its own local cache and clients serve each other peer-to-peer over the LAN, discovered via WS-Discovery. Recommended only for small branches — typically under 15 users.

Request flow

1
First client requests a file

Full request goes over the WAN to the NetApp SMB share. ONTAP authenticates the user, sends the complete file, and generates content metadata — hashes calculated over chunks of the file.

2
Client caches the content

The file is stored locally — either in that client's own cache (distributed mode) or pushed to the branch's hosted cache server.

3
A second client asks for the same file

The request still goes to the NetApp SVM first. ONTAP authenticates and authorizes the user, then checks whether the cached content is still current.

4
NetApp sends metadata, not the file

If the cache is valid, ONTAP returns only the small content-info hashes — not the file itself.

5
Client fetches the bytes locally

Using that metadata, the client locates and pulls the actual content from the local cache — a peer client (distributed) or the hosted cache server — never crossing the WAN.

The part people miss

BranchCache never fully bypasses NetApp. Every request still triggers an auth-and-freshness check against the origin. What gets skipped is only the WAN transfer of the actual file bytes — and only if a valid copy already exists somewhere local.

Different branch office, same share

Each branch builds its own cache independently — there's no cross-site sharing. The first client at Site B still pulls the complete file over the WAN, exactly as Site A's first client did, even if Site A already cached it.

03

FlexCache

NFS + SMB · runs on ONTAP · no Windows dependency

Instead of caching on a client or a Windows server, FlexCache creates a real ONTAP volume — a sparse, writable, self-updating cache of another volume.

How it's structured

  • An origin volume holds the full, authoritative dataset.
  • A FlexCache volume, on a different node, cluster, or even a different cloud region, holds only the actively-read ("hot") portion of it.
  • A cold read — data the cache doesn't have yet — is pulled from the origin, served, and cached for next time. A hot read is served straight from the local cache volume, with no origin round trip needed for the data itself.

Request flow

1
Client mounts the FlexCache volume

Clients at the remote site connect to the local FlexCache volume directly — it looks and behaves like any ordinary volume.

2
Cold read (first access)

The FlexCache volume doesn't have the requested block yet, so it retrieves it from the origin volume over the network, serves it to the client, and stores it.

3
Hot read (repeat access)

The data is already present locally, so it's served directly — faster, and without needing to travel back to the origin.

4
Writes (write-around, the default)

Writes pass through the cache straight to the origin. The rule of thumb is at least 80% reads / 20% writes for this mode to be efficient, since every write still pays the WAN penalty.

5
Writes (write-back, optional)

For write-heavy workloads on large files, write-back lets clients write at local speed while the cache asynchronously forwards changes to the origin. Not recommended for many small-file writes.

Worth knowing

FlexCache isn't limited to branch offices. It's just as often used inside a single cluster or datacenter to relieve a hot volume that's being hit by many clients at once, by spinning up extra cache mount points for the same data.

04

Global File Cache (GFC)

SMB only · dedicated appliance per site · per-site license

GFC is the most infrastructure-heavy of the three: a real NetApp-supported appliance pair, not a feature riding on top of existing Windows or ONTAP components.

Request flow

1
Origin appliance is deployed centrally

A GFC virtual appliance (Windows Server VM) sits in front of the central SMB storage — NetApp or otherwise.

2
A branch appliance is deployed at every remote site

Each branch gets its own GFC virtual appliance acting as the local cache node.

3
User opens a file at the branch

The request goes to the local GFC appliance, not directly across the WAN.

4
Cache miss → optimized pull from origin

If the local appliance doesn't already hold a current copy, it retrieves the needed data from the origin appliance using its own byte-level transfer, not a full-file copy every time.

5
Local cache serves every subsequent user at that branch

Other users at the same branch are served straight from the local appliance's cache.

6
Writes flow back through, with global locking

Writes go through the local appliance to the origin, keeping a single authoritative copy. Global file locking prevents two sites from conflicting edits on the same file simultaneously.

The trade you're making

GFC costs real money per site — roughly $4K list per year, per remote-site instance — but in exchange you get a purpose-built, NetApp-supported appliance with stronger cross-site write consistency than BranchCache offers, and SMB caching without needing native ONTAP on both ends the way FlexCache does.

These aren't mutually exclusive. It's common to run BranchCache at small offices, GFC at a handful of large collaborative sites, and FlexCache for NFS-based engineering or media workloads — all pointed at the same underlying NetApp estate.

07

Glossary

Content metadata
The hash information BranchCache uses to let a client locate and verify cached content locally instead of re-downloading it.
Hosted cache mode
BranchCache mode where one designated branch server holds the cache for all local clients.
Distributed cache mode
BranchCache mode with no server — clients cache and serve each other peer-to-peer.
Origin volume
The authoritative FlexCache source volume that a cache volume pulls hot data from.
Write-around
FlexCache's default write mode — writes pass straight through the cache to the origin.
Write-back
Optional FlexCache mode for write-heavy workloads — writes land locally first, then sync to origin.
Global file locking
GFC (and optionally FlexCache) mechanism that prevents two sites from editing the same file at once.
