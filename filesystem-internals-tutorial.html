§1

atime, mtime, ctime

Every Unix/Linux file carries three timestamps. Only one of them means what people assume it means.

stat.outputext4 / xfs
$ stat file.txt Access: 2026-07-09 09:12:03 Modify: 2026-07-08 22:40:51 Change: 2026-07-09 08:55:17

What each one actually tracks

FieldUpdates whenCommon misconception
atime File contents are read — opened, catted, scanned by a backup job. Often disabled entirely (noatime, relatime) because updating it on every read is expensive.
mtime File contents change — edited, appended, overwritten, truncated. This is what ls -l shows. Most people mean this when they say "last modified."
ctime File metadata changes — permissions, ownership, links, name — or whenever mtime changes. Not "creation time," despite the name. That's the single most common mix-up.
The rule that matters: mtime changes only when content changes. ctime changes when content or metadata changes — ctime is a superset of mtime. If ctime moved but mtime didn't, something touched permissions, ownership, or the file's name/location — not the data itself.
examplebash
$ echo "hello" > file.txt # mtime + ctime both update $ chmod 644 file.txt # only ctime updates — content untouched

One more nuance: Linux has no universally reliable "creation time" exposed through ctime. Filesystems like ext4 store a separate crtime ("birth time") field, viewable via stat -c %w where supported — but it isn't ctime, and isn't guaranteed everywhere.

§2

NTFS Security Descriptors

Windows attaches a Security Descriptor to every file and folder. It's a bundle of who-owns-it and who-can-do-what — the DACL is the "who can do what" part.

icacls / Get-Acl outputNTFS
NTFS Security Descriptor Control: 0x8004 Owner: BUILTIN\Administrators Group: DEMO\Domain Users DACL - ACEs ALLOW-Everyone-0x1f01ff-(Inherited)

The four parts of a Security Descriptor

PartWhat it is
OwnerWho owns the object. The owner can always change its permissions, regardless of what the DACL says.
GroupA legacy field carried over for POSIX compatibility. Windows access checks mostly ignore it.
DACLDiscretionary Access Control List — the actual allow/deny permission rules. This is the part people mean by "the permissions."
SACLSystem Access Control List — auditing rules (what gets logged), not shown in this output.

Decoding the ACE — click a piece

ALLOW-Everyone-0x1f01ff-(Inherited)
ACE type
ALLOW

Everyone

0x1f01ff

0x1f01ff decodes to Full Control — read, write, execute, delete, change permissions, and take ownership. It's the broadest grant NTFS has. Other common masks: 0x1301bf Modify, 0x1301a9 Read & Execute, 0x100081 Read-only.
ALLOW means this rule grants access. The other possibility is DENY, which blocks it — and Deny ACEs are always evaluated first, regardless of list order.
Everyone is a built-in security principal matching every user, authenticated or not (on modern Windows, "Everyone" excludes anonymous logons by default). It's the broadest possible trustee.
Inherited means this rule wasn't set directly on this object — it flowed down from the parent folder's permissions. An ACE set explicitly on the object itself would show without this tag.
Plain-English read of the example: This file is owned by Administrators. Everyone has Full Control over it, and that permission wasn't configured here — it was inherited from the parent folder.

An analogy

Think of a DACL as a bouncer's guest list. The Owner is whoever booked the venue and can rewrite the list anytime. The DACL is the list itself. Each ACE is one line on it — "Allow, John, VIP access, written by the venue manager, not the booker." The SACL, not shown here, is the logbook of who the bouncer records as having entered.

§3

NetApp File Handles

ONTAP tracks every file by an internal identifier set, separate from its path — the thing NFS clients actually cache and reference.

ONTAP CLIcluster1::>
cluster1::*> vol file show-filehandle -vserver svm1 -path /vol/window/Q1_Windows/test.txt Vserver Path ---------------------- ------------------------------------- svm1 /vol/window/Q1_Windows/test.txt flags snapid fileid generation fsid msid dsid ------- ------ --------- ---------- ---------- ------------ ------------- 0x0 0 0x63 0x1708fc 0x402 0x80f3bf44 0x402 volume ------------------------------------------------------------------------------ window

The command asks ONTAP: show me the internal NFS/CIFS handle for this exact file. The path is the human-friendly label; everything below is how ONTAP actually identifies the object.

Field by field

flags
0x0
Internal status flags on the handle. Zero means nothing unusual is set.
snapid
0
Snapshot ID. Zero means this is the live, active version — not a copy inside a .snapshot directory.
fileid
0x63 (99)
Unique identifier for the file within its volume — the inode-equivalent.
generation
0x1708fc
Increments if a fileid gets reused by a new file after deletion. Prevents an NFS client's stale cached handle from silently pointing at the wrong file.
fsid
0x402 (1026)
Identifies the specific volume/filesystem instance the file lives in.
msid
0x80f3bf44
Master Set ID — a persistent identity for the volume, tracked across its lifecycle (e.g. FlexClone, SnapMirror relationships).
dsid
0x402
Data Set ID — identifies the actual data container. Here it matches fsid.
volume
window
The volume name the file belongs to — the human label for the container.

Why this matters

This output is mostly pulled during troubleshooting:

ScenarioWhat the handle tells you
Stale NFS handle errors NFS clients cache fileid + generation + fsid. Delete and recreate a file at the same path, and the generation changes — the client's cached handle goes stale until it re-resolves the path.
FlexClone / SnapMirror cases The same path can correspond to different underlying objects across a clone or mirror relationship. msid/dsid let support correlate the exact object, not just the name.
Analogy: the path is a street address. fileid + generation + fsid is more like a social-security-number-plus-issue-date. Two files can share the same "address" over time if one is deleted and another created in its place — but their ID-plus-issue-date combination never collides, which is exactly what the generation field protects against.
